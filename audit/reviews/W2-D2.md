## 1. Retention classification: proof

The candidate query (`lib/server/retention.ts:56-77`) keeps a generation for purging when:

```
money  = Σ(quota_delta + balance_delta)   over kind ∈ {charge, refund}, reference = g.id, user_id = g.user_id
points = Σ(points_delta)                  over the same rows
purge ⇔ status = COMPLETED ∧ files_purged_at IS NULL ∧ finished_at < now()-180d ∧ money ≥ 0 ∧ points < 0
```

**Facts from the code:**
- The only `charge` writer is `enqueueGeneration → chargeInTx` (`jobs.ts:166`), and its reference is always the generation id.
- There is exactly one `charge` row per reference, enforced by UNIQUE `(kind, reference)`. That row carries all three wallet deltas together, each ≤ 0.
- There is at most one `refund` row per reference, also UNIQUE. Its deltas are each between 0 and the matching charge component, because of the `splitRatio` cap `out[i] ≤ parts[i]`.
- `admin_credit`, `admin_debit`, `bonus`, `topup` and `subscription` rows use other references (random UUIDs or provider ids), so they never match `g.id`.
- Nothing reassigns `generations.user_id` or `transactions.user_id` (no account merge).

**Consequences:**
- **Charge took quota or balance (Q+B > 0), with no refund:** money = −(Q+B) < 0, so the document is **kept**.
- **Partial refund of Q+B by r < 1:** the refunded amount is at most Q+B, so money ≤ 0. It is 0 only if the whole Q+B came back, which needs r ≈ 1 (see nit N8). The document is **kept**.
- **Full refund (r = 1):** points = 0, so the document is **kept**. This is also safe on a COMPLETED row.
- **No charge row** (price 0, legacy rows, admin tests): points = 0, so the document is **kept**.
- **Pro quota:** counted in `money`, so the document is **kept**.
- **Admin-credited balance used to pay:** `charge.balance_delta` < 0, so the document is **kept**. Admin-credited *points* count as bonus, which matches the owner rule.

The rule is the exact complement of `spend.ts assertPaidDocument` (`paid > 0`). **A document whose balance or quota payment was not fully returned can never be selected.** False positives are impossible under the current writers.

## 2. Queue TTL money correctness: verified

- **Two housekeepers at once:** `UPDATE … WHERE id=$1 AND status='QUEUED'` serialises on the row lock. The loser re-evaluates the WHERE under READ COMMITTED, gets 0 rows and never calls `refundInTx`. The test covers this deterministically with a lock-blocker plus `pg_stat_activity` wait.
- **Claim vs expire:** `claimJob` selects with `FOR UPDATE SKIP LOCKED`.
  - If expire holds the lock, claim skips the row.
  - If claim wins, expire's UPDATE waits, then sees `IN_PROGRESS` and gets 0 rows.
  - A job **cannot** be both claimed and expired or refunded.
- **Duplicate refund:** there is a double barrier, the `SELECT … kind='refund'` pre-check plus UNIQUE `(kind, reference)`. A UNIQUE violation rolls back the whole transaction, status change included, so the job stays QUEUED and is retried.
- **Ledger:** `users` and `transactions` are updated in the same transaction with the same deltas, so `balance == Σ transactions` holds. Lock order is generations row, then users row, and enqueue only inserts a new generations row, so there is no deadlock cycle.
- **`refundInTx` vs `credits.refundRatio(…, 1)`:** identical for ratio = 1. `splitRatio(parts, 1)` returns `parts` unchanged because `floor(p) = p`, `target = total` and `left = 0`. The wallets, idempotency rule and user lock are the same. This is duplicated code, not divergent code (nit N2).

## 3. Migration 022: acceptable

- The rollback in the header is correct, including the `schema_migrations` row.
- `ADD COLUMN` with no default is metadata-only, but it needs a short ACCESS EXCLUSIVE lock (nit N4).

  - At today's row count this is seconds.
  - The comment "kichik jadval — baytlar boshqa jadvalda" is only half true: `doc_json`, `html` and `live_json` live in `generations` but are TOASTed, so the heap scan stays small.
  - `CONCURRENTLY` is impossible inside the runner's `BEGIN` (`db.ts:121`). This is correctly noted.

## 4. Worker resilience and heartbeat: acceptable

- **`unhandledRejection` → log and continue.** Rejections are event-driven, not looped. If the DB is permanently down:
  - `tick` throws, is caught, and the loop sleeps 5 s. There is no tight loop.
  - The heartbeat stops (only written when `healthy`), so the container turns unhealthy.
  - A stuck job whose promise rejected is picked up by `reclaimStaleJobs`, the same as after the old crash, but other in-flight jobs are no longer killed.
- **`uncaughtException` → `exit(1)`:** correct.
- **Pool `error` listener:** exists (`db.ts:46`), so idle-client errors don't go through the guard.
- **`LiveReporter` `.catch`:** leaves the chains resolved. `dirty = true` retries on the next flush, and `stop()` no longer rejects. Nothing downstream depends on `stop()` rejecting.
- **Heartbeat:** written only after a successful `tick`, rate-limited to 10 s, and written again after housekeeping. This matches the w2-contracts rule of at least every 30 s. `tick` is non-blocking because `runJob` is fire-and-forget, so long jobs don't stall it.

## Required changes

### R1 — Stop active game links from breaking mid-class (`lib/server/retention.ts:66-72`). Severity: MEDIUM

`getGameSessionByToken` returns `g.doc_json`, and `/api/o/[token]` (plus `/submit` and `/audio/[assetId]`) returns **404** when `doc` is null.

A teacher who reuses last term's bonus-only quiz can create a fresh 30-day link at day 170. The purge at day 180 then kills that link while students are playing. Nothing crashes, but a classroom session fails. Teachers routinely reuse games across terms, so this case is realistic.

Suggested fix: defer the purge while an unexpired link exists (at most 30 days after the last share).

```sql
        WHERE g.status = 'COMPLETED'
          AND g.files_purged_at IS NULL
          AND g.finished_at < now() - make_interval(days => $1::int)
          AND m.money >= 0
          AND m.points < 0
          AND NOT EXISTS (
            SELECT 1 FROM game_sessions s
             WHERE s.generation_id = g.id
               AND (s.expires_at IS NULL OR s.expires_at > now())
          )
```

Add a test: a bonus-only generation older than 180 days with a live `game_sessions` row is kept. Once its `expires_at` is in the past, it is purged.

### R2 — Clear `preview` on purge (`lib/server/retention.ts:85-87`). Severity: MEDIUM (user-visible)

`preview` is returned in every history-list row (`ROW_COLUMNS`, `jobs.ts:76`). Two of its fields point at deleted assets:
- `preview.url`, which is the first figure or image.
- The images and logo inside `preview.slide.model`.

Both are `/api/generations/{id}/assets/{aid}` URLs (`assets.ts:25`). After the purge, every such history card shows a **broken image**. `preview.lines` also keeps document text that the purge otherwise removes.

Suggested fix:

```sql
          SET doc_json = NULL, html = NULL, doc_prev = NULL, live_json = NULL, preview = NULL,
```

Add `preview IS NULL` to the assertions of the first retention test.

### R3 — Throttle the retention scan (`lib/server/worker.ts:449`, `retention.ts`). Severity: MEDIUM (cost that keeps growing)

Paid generations never get `files_purged_at`, so they stay in `generations_retention_idx` forever. Every `housekeeping()` call, which runs every 60 s on **every** worker replica, walks all COMPLETED rows older than 180 days. For each row it evaluates the LATERAL aggregate, which costs two index probes on `transactions`, only to reject it.

After a year that is hundreds of thousands of probes per minute per worker, on a DB shared with the web app, and it keeps growing without bound. Retention with a 180-day threshold gains nothing from minute-level granularity.

Suggested fix: run the step at most every few hours.

```ts
// worker.ts
const RETENTION_EVERY_MS = 6 * 3600_000;
let lastRetentionAt = 0;
…
  await step("retention", async () => {
    if (Date.now() - lastRetentionAt < RETENTION_EVERY_MS) return;
    lastRetentionAt = Date.now();
    await purgeBonusFiles();
  });
```

A cursor is an alternative: an `ORDER BY finished_at` watermark persisted in memory, which resets on restart. The throttle is enough. Keep the `worker-resilience` test by exporting a test seam or resetting `lastRetentionAt`, since the test asserts that `purgeBonusFiles` is called.

## Optional nits and follow-ups

- **N1: an edit racing with the purge can bring back `doc_json`.**
  - A `PATCH …/doc` that loaded the document before the purge commits waits on the row lock. Its `WHERE doc_version = base` still matches, so it writes `doc_json` back on a purged row, and the next download rebuilds the file with broken asset images.
  - This is very rare, since it needs someone editing a document older than 180 days at the exact moment of the purge.
  - Fix: in the purge UPDATE, set `doc_version = doc_version + 1, file_version = doc_version + 1`. Stale editors then get 409.
- **N2: duplicated refund logic.** `refundInTx` duplicates `credits.refundRatio`. Consider `credits.ts` exporting `refundRatioInTx(client, userId, ref, ratio, note)` and having `refundRatio` wrap it in `transaction(...)`, so there is one implementation.
- **N3: reclaim-dead refunds are not atomic (pre-existing, now more visible next to the atomic TTL path).**
  - `reclaimStaleJobs` commits FAILED, and the refund then runs in a separate transaction.
  - If that refund throws, the job stays FAILED with no refund and is never retried, so the money is lost.
  - Fix: call `refundInTx` inside the `reclaimStaleJobs` transaction for the `dead` rows.
- **N4: migration locking and comment.**
  - Consider `SET LOCAL lock_timeout = '5s';` before the `ALTER TABLE`. Otherwise a long-running transaction can make the ACCESS EXCLUSIVE request queue up and stall all traffic on `generations`.
  - Reword "kichik jadval" in the comment.
- **N5: the purge flag is not exposed.** `files_purged_at` is not in `ROW_COLUMNS` or `GenerationSummary`, so the Wave 3 UI cannot show "Bonus bilan yaratilgan hujjatlar 180 kun saqlanadi". Expose it as `filesPurgedAt`.
- **N6: sharing a purged game still works.** The share route (`game-sessions.ts:130 createGameSession`) creates a link for a purged game that returns 404 immediately. Add `AND g.files_purged_at IS NULL` and give the route a clear 410 or 409 message. This belongs to the games package owner.
- **N7: missing tests.**
  - No claim-vs-expire race test. The SQL reasoning above holds, but a deterministic test like the housekeeper one would lock it in.
  - No test with `admin_credit`/`admin_debit` rows present, to prove they are ignored.
  - No ledger-invariant assertion (`users.balance == Σ transactions.balance_delta`) in the TTL test.
- **N8: rounding edge case in the net-of-refund rule.**
  - Take a mixed charge with a tiny balance part (for example 1 so'm) where `splitRatio` rounding returns that whole part on a partial refund.
  - That generation is classified as bonus-only. This is consistent with `assertPaidDocument`, and the user's net real spend is 0. It is acceptable; mention it in `retention.md`.
- **N9: heartbeat and DB outages.** While `running >= concurrency`, `tick` returns without touching the DB, so the heartbeat stays fresh even during a DB outage. This is self-correcting once the slots fail and free up. Also, the inline web worker writes the same alive file, which is harmless.
