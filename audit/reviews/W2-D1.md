## Trade-offs (acceptable; stating them explicitly)

1. **Exit on fatal boot.**
   - A config problem now crash-loops under `restart: unless-stopped`, with Docker's backoff doubling up to about 1 minute. Before, it sat as a zombie answering 500. `deploy.sh`'s 2-minute health poll fails either way.
   - What changes: the failure is visible (`Restarting`, a log line on every attempt), and it heals by itself once a transient DB outage at boot clears.
   - A permanent misconfiguration is still an outage until `.env` is fixed, the same as before, but no longer silent.
   - This is the desired behaviour.
2. **`stop_grace_period: 60s` on web.**
   - Next 15.5 on SIGTERM calls `server.close()`, which stops accepting new connections at once, then waits for in-flight requests. The 45–60 s edit routes now finish.
   - The cost: the 502 window during a deploy can grow from about 10 s to up to 60 s plus boot time whenever such a request is in flight.
3. **Memory limits** (web 2g, worker 2g × 2, Postgres 1g).
   - These are ceilings. They protect the neighbouring projects, but they add a new failure mode: a cgroup OOM kills the biggest process in the container. That is node, so the container restarts; for Postgres it means crash recovery for every connection.
   - Peak memory per job at 4 slots is unmeasured, as `capacity.md` itself acknowledges. The Phase 5 RSS measurement must happen before 2g is trusted. Each limit can be tuned through `*_MEM_LIMIT`.

## Required changes

1. **`backup.sh`: every failure path must go through `fail()`.**
   - Today only `pg_dump` and the size check call `fail()`. A failure in `docker cp`, `mv`, `mkdir` or `stat` (for example disk-full inside the Postgres container) makes `set -e` exit with no JSON line in `backup.log` and no Telegram alert.
   - For `docker cp` it also leaves the full-size `slaydx-*.dump.tmp` behind. Rotation only matches `*.dump`, so on a failing box these files pile up daily on the shared disk.
   - Fix: add `trap 'fail "kutilmagan xato (satr $LINENO)"' ERR` (guarded against recursion), or `|| fail …` on each call. Also add `trap 'rm -f "$tmp"' EXIT`.
2. **Make the configuration the docs describe actually reach the script, and alert on remote-copy failure.**
   - README and `deploy.md` say to set `BACKUP_REMOTE` "in `.env` or the cron environment", but the script never reads `.env`, and cron starts with an empty environment. The same is true of `BACKUP_TG_CHAT` and `TELEGRAM_BOT_TOKEN`, which are not documented anywhere. As shipped, the off-box copy and the failure alert can only work if the owner guesses to put them on the cron line.
   - Fix: either source an optional dedicated file (for example `[ -f "${BACKUP_ENV_FILE:-/root/slaydx-backup.env}" ] && . "$BACKUP_ENV_FILE"`, mode 600), or document the exact cron-line form. Do not source `/opt/slaydx/.env` itself with bash.
   - Also: a failed `rsync`/`rclone` should call `notify_failure` and exit non-zero. It is currently logged only as `"remote":"failed"`, so the off-box copy can fail silently forever. The design also asks for a size check on the remote copy.
3. **`restore-check.sh`: fix a readiness race and cap the container.**
   - The official image's init step starts a temporary server with `listen_addresses=''`. `pg_isready` over the unix socket can succeed against that temporary server before `POSTGRES_DB` exists or while it is shutting down. `pg_restore` then fails, which is a false weekly alarm.
   - Fix: use `pg_isready -h 127.0.0.1 -U postgres`, which only succeeds against the final server.
   - For the shared box, also add `--network none --memory 1g` to the throwaway `docker run`. The restore needs no network, and nothing currently caps its memory.

## Optional nits

- `onRequestError` logs `request.path`, which in Next includes the query string. That puts `/api/auth/telegram/enter?t=<login token>` (single-use, 5 min) in the logs. Strip `?…`.
- `backup.sh` writes stderr to a predictable `/tmp/slaydx-backup-err.$$` as root on a shared host. Use `mktemp` or `$BACKUP_DIR`.
- `backup.sh` puts `TELEGRAM_BOT_TOKEN` in curl's argv, where `ps` shows it for up to 10 s. Pass it via `-K -`/stdin instead.
- `backup.sh` copies the whole dump into the production Postgres container's `/tmp`, which doubles disk use for a moment. `docker exec -i "$PG_CONTAINER" pg_restore --list < "$tmp"` avoids the copy.
- The restore container is named `slaydx-restore-check-*`. That contradicts the docs ("slaydx-* oilasiga tegmaydi") and the four-container count in `deploy.md` step 6. Rename it to something like `restorecheck-slaydx-$$`.
- The deep-health SQL scans all of `generations`. `WHERE status IN ('QUEUED','IN_PROGRESS')` would use the existing partial indexes.
- The worker's `stop_grace_period: 30s` has no effect today, because `runWorkerProcess` exits after 2 s (INFRA-02 is still open). Make the comment say so.
- `deploy.md`: `exec -T worker` always picks replica 1 (not "ixtiyoriy").
- `scripts/seed-demo.mts:6` still mentions `FILE_TTL_HOURS`.
- The pre-deploy `slaydx-*.sql` dumps in the same directory are never rotated.
- `BACKUP_REMOTE` routing: `host:/path` without `user@` goes to the rclone branch, and a value starting with `-` would be read as an option.
