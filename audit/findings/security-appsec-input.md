### SECB-01 — Quadratic regexes in upload text parsing block the web process event loop (single authenticated request)
- **Severity:** P0
- **Location:** `lib/extract-text.ts:40` (`tidy`: `/[ \t]+\n/g`), `lib/extract-text.ts:46,52,62,64` (`/<w:br\b[^/]*\/>/g`, `/<w:tab\b[^/]*\/>/g`, `/<[^>]+>/g`, `/<a:br\b[^/]*\/>/g`), `lib/generation/translate/plain.ts:51` (`/(?:[ \t]*\r?\n){2,}[ \t]*/g`), `plain.ts:66` and `plain.ts:204` (`/\s*$/`), `plain.ts:117,148` (`inlineOf` backtracking per character). Reached from `app/api/extract/route.ts:36` (`extractFromBuffer`) and `app/api/uploads/source/route.ts:28` → `lib/server/source-upload.ts:330` (`DEFAULT_COUNTER` → `extractSegments`), both executed synchronously inside the **web** process.
- **Evidence:** each of these patterns has a greedy class run followed by a token the class cannot match, so every start position rescans to the end of the run → O(n²). Measured locally with Node 22 on tiny inputs (script below): 10 000 chars ≈ 55–68 ms, 20 000 ≈ 225–265 ms, 40 000 ≈ 0.87–1.07 s (exactly ×4 per doubling) for `tidy`, `<[^>]+>`, `\s*$` and the `txtParts` separator; `<w:br…>` is the same curve at ~1/5 the constant. Extrapolated, a ~1 MB text body costs ≈10 min and an 8 MB body (the `/api/extract` limit) many hours of synchronous CPU. Next.js self-hosted does not enforce `maxDuration`, nginx timing out the client does not stop the regex, and Node is single-threaded — every other request to the `web` container (login, polling, downloads, payment webhooks) stalls for the duration. Upload routes are free (no credit) and rate limits (20/5 min) do not matter because one request suffices. The same functions run again in the worker for translation jobs (`translate/index.ts:82-86`, `applyText`/`applyMd`), where a stalled event loop also freezes both concurrency slots and heartbeats.
- **Reproduction:** regression test (safe, bounded): `for n of [1e4, 2e4, 4e4]` time `extractFromBuffer("a.txt", enc(" ".repeat(n)+"x"))` and `textToSegments(" ".repeat(n)+"x")` from `lib/generation/translate/plain.ts`; assert time(4e4) < 3 × time(2e4) + 20 ms (linear). It fails today (ratio ≈ 4). Probe used: `s=" ".repeat(n)+"x"; s.replace(/[ \t]+\n/g,"\n")` → 68 / 261 / 1035 ms.
- **Proposed fix:** (1) rewrite these helpers without backtracking-prone patterns: trailing-whitespace trim via a manual backward loop (or `trimEnd()` + length arithmetic) instead of `/\s*$/`; `tidy` → split on `\n` and `trimEnd()` each line; tag stripping → a single linear scanner (`indexOf("<")`/`indexOf(">")`), `<w:br…/>` → `/<w:br\b[^/>]*\/>/g` (exclude `>` so a scan can never cross a tag boundary) or reuse `xml-scan.ts scanTags`; `txtParts` → split on `/\r?\n/` and group blank lines in code; `inlineOf` → cap line length and replace lazy `[\s\S]*?` searches with `indexOf` of the closing delimiter. (2) Defence in depth: run all user-file parsing (`extractFromBuffer`, `extractSegments`) in a `worker_threads` worker with a hard timeout (e.g. 20 s, terminate on expiry) so no parser can block the web event loop. (3) Add the linear-time regression test above for each helper.
- **Effort:** M
- **Confidence:** high (timings measured; call path read end-to-end).

### SECB-02 — ZIP "bomb" budget trusts archive metadata; template parsing has no inflate budget at all (memory exhaustion in the web process)
- **Severity:** P1
- **Location:** `lib/extract-text.ts:80-99` (`readEntry`), `lib/generation/translate/xml-scan.ts:233-252` (`openOoxml`), `lib/generation/pptx-template.ts:199-247` (`parsePptxTemplate` — every `zip.file(...).async("string")`, no budget), `lib/generation/render-pptx-template.ts:228,254` (`renderLayoutSheet`/`renderPptxWithTemplate` re-open and re-generate the whole user zip). Web-process entry points: `app/api/extract/route.ts:36`, `app/api/uploads/source/route.ts:28`, `app/api/uploads/template/route.ts:21` (`uploadTemplate` → `parsePptxTemplate` + `rasterizeTemplate`).
- **Evidence:** the guard compares `file._data.uncompressedSize` (a number read from the archive's own central directory) with the budget *before* inflating, and the real length only *after* `file.async("string")` has produced the whole string: `if (typeof declared === "number" && declared > budget) throw …; const text = await file.async("string"); budget -= text.length;`. JSZip 3.10.1 itself only compares actual vs declared length in the stream `end` handler (`node_modules/jszip/lib/compressedObject.js:37-41`), i.e. after every inflated chunk has been accumulated (`stream/StreamHelper.js accumulate`). So the budget does not bound memory for an archive whose metadata understates the entry size; the actual bound is the deflate expansion ratio of an upload of up to 8 MB (`/api/extract`) or 20 MB (source/template). `parsePptxTemplate` has no declared-size check either, for `presentation.xml`, rels, master, theme and every layout. All of this runs in the `web` container, which has no memory limit in `docker-compose.yml` (no `mem_limit`/`deploy.resources`), on a VPS shared with two other projects — a single upload can push the web process (or, via the host OOM killer, a neighbour such as Postgres) over the edge. Inflated `ArrayBuffer` chunks are external memory, so `--max-old-space-size` does not cap them.
- **Reproduction:** regression test with a small fixture whose central-directory `uncompressedSize` for `word/document.xml` is smaller than its real inflated size (e.g. 10 MB of a repeated character, declared as 1 KB): call `extractFromBuffer("x.docx", buf)` / `extractSegments("docx", buf)` / `parsePptxTemplate(buf)` (with a `ppt/` fixture) while sampling `process.memoryUsage().arrayBuffers`; assert the call rejects with «juda katta» and peak `arrayBuffers` growth stays below the budget + a small margin. Today it inflates everything first and only then fails with JSZip's «uncompressed data size mismatch» (or, for `parsePptxTemplate`, succeeds with no limit).
- **Proposed fix:** replace `file.async("string")` for user archives with a streaming inflate that counts output bytes and aborts past the budget — e.g. `file.internalStream("uint8array")` with an `on("data")` counter that calls `.pause()`/throws once `budget` is exceeded, or switch these readers to `fflate`'s streaming `Unzip`/`Inflate` with an explicit output cap. Apply one shared helper (`readZipEntryCapped(zip, name, budget)`) in `extract-text.ts`, `xml-scan.ts openOoxml` and `pptx-template.ts`, and give templates a total budget (e.g. 40 MB of XML). Also cap entry count (e.g. ≤ 5 000 entries) before iterating `zip.files`. Longer term run user-file parsing in a `worker_threads` worker with `resourceLimits` and a timeout, and set a memory limit on the `web` service in compose.
- **Effort:** M
- **Confidence:** medium — the ordering (metadata check → full inflate → length check) is verified in code and in JSZip's source; confirm with the fixture test above (run through `scripts/heavy.sh`, it is bounded to ~10 MB).

### SECB-03 — Viewer image uploads write the asset row before ownership/version is checked
- **Severity:** P3
- **Location:** `lib/server/slide-image.ts:72-75` (`putAssetBytes(id, …)` then `commitDocOps`), `lib/server/resume-photo-commit.ts:45` (`putAssetBytes(genId, …)`, commit at `:78/:97`), `lib/server/assets.ts:166-176` (`putAssets` inserts by `generation_id` only, no `user_id` predicate).
- **Evidence:** `const assetId = await putAssetBytes(id, mime, bytes); … return commitDocOps(id, userId, baseVersion, ops);` — the ownership check lives in `commitDocOps → loadDocForEdit` (`WHERE id=$1 AND user_id=$2`), which runs *after* the 5 MB blob is already inserted into `generation_assets` for whatever generation UUID was in the URL. Consequences: (a) an authenticated user who knows another user's generation UUID (it is in every `/uz/files/<id>` link people paste around) can attach up to 30 × 5 MB/hour of arbitrary PNG/JPEG rows to that generation (not rendered, but stored forever — `011_no_expiry`); (b) for the owner, every 409 (stale `baseVersion`) or 422 leaves an orphaned asset row. This contradicts the project rule "egalik SQL darajasida".
- **Reproduction:** as user B, `POST /api/generations/<A's completed slide generation id>/slides/0/image` with a valid PNG and `baseVersion=0` → response 404 (from `loadDocForEdit`), but `SELECT count(*) FROM generation_assets WHERE generation_id='<A's id>'` increased by one.
- **Proposed fix:** call `loadDocForEdit(id, userId)` (or a cheap `SELECT 1 FROM generations WHERE id=$1 AND user_id=$2 AND status='COMPLETED'`) before `putAssetBytes`, or better, move the asset insert into the same transaction as `updateGenerationDoc` (pass the pending asset through `commitDocOps` so a failed commit rolls it back). Add `user_id` to the `putAssets` insert path via `INSERT … SELECT … FROM generations WHERE id=$1 AND user_id=$2`.
- **Effort:** S
- **Confidence:** high

### SECB-04 — Uploaded PDFs are fully parsed page-by-page in the web request with no page cap
- **Severity:** P2
- **Location:** `lib/generation/translate/pdf.ts:223-256` (`pdfToBlocks` loops `for (let n = 1; n <= pages; n++)` with `page.getTextContent()` and structure reconstruction, no upper bound), reached synchronously from `app/api/uploads/source/route.ts:28` → `lib/server/source-upload.ts:330` (`DEFAULT_COUNTER` → `extractSegments` → `extractPdf` → `pdfToBlocks`). Also `lib/extract-text.ts:133-142` (`extractPdfBuffer` → unpdf `extractText({mergePages:true})`, all pages) from `app/api/extract/route.ts:36`. `lib/server/source-upload.ts:138-148` (`pdfPages`) only counts, but the counting path already ran the full parse.
- **Evidence:** `const pages = doc.numPages; … for (let n = 1; n <= pages; n++) { const page = await doc.getPage(n); … await page.getTextContent(); … }` — `pages` comes straight from the uploaded PDF. A PDF is compact: a ~1–20 MB file (the source-upload limit is 20 MB) can declare tens of thousands of pages, and every page triggers `getPage`+`getTextContent` plus the per-line/header-footer/table reconstruction in `toLines`/`pdfToBlocks`. This runs in the **web** container (uploads are handled there, not the worker) on Node's single thread, so it stalls all other requests while it runs, and only *afterwards* is the "scanned PDF" / char-limit check applied (`source-upload.ts:338`). unpdf's bundled pdf.js has `disableFontFace` and no `isEvalSupported` path (checked: 0 occurrences in `node_modules/unpdf/dist/pdfjs.mjs`), so this is a CPU/latency DoS, not RCE.
- **Reproduction:** build a valid PDF with a very high page count but small byte size (e.g. many empty pages, well under 20 MB); `POST /api/uploads/source` with it and time the response, and concurrently `GET /api/health` — health latency spikes for the duration. Bounded regression test: assert `pdfToBlocks` on an N-page fixture is called with a page cap (e.g. rejects or truncates beyond ~1 000 pages) rather than iterating unboundedly.
- **Proposed fix:** cap `pages` before the loop (e.g. `if (doc.numPages > MAX_PDF_PAGES) throw new ApiError("PDF juda uzun — sahifalarga bo'ling", 422)` with `MAX_PDF_PAGES` ~500, matching the 200 000-char translation ceiling), and enforce it in both `pdfToBlocks` and `extractPdfBuffer`. Combine with the SECB-01 recommendation of running upload parsing in a `worker_threads` worker with a wall-clock timeout so a pathological PDF cannot block the web event loop.
- **Effort:** S
- **Confidence:** medium — the missing cap and the web-process call path are certain from code; the exact page count reachable in 20 MB and the per-page cost should be confirmed with the fixture above (run via `scripts/heavy.sh`).

### SECB-05 — Upload size pre-check is bypassable with chunked uploads (no Content-Length), so the whole body is still buffered
- **Severity:** P3
- **Location:** `app/api/extract/route.ts:22-23`, `lib/server/logo.ts:83-84`, `lib/server/photo.ts:136-137`, `lib/server/source-upload.ts:306-307`, `lib/server/template-upload.ts:196-197`, `lib/server/slide-image.ts:49-50` — all use `const declared = Number(req.headers.get("content-length") ?? 0); if (Number.isFinite(declared) && declared > MAX …) throw 413;` and then call `req.formData()`/`file.arrayBuffer()`.
- **Evidence:** the pre-check the code advertises as "hajm **tahlildan oldin** tekshiriladi" reads only the `Content-Length` header. A client can send `Transfer-Encoding: chunked` with no `Content-Length`; then `declared` is `0`, the guard passes, and `req.formData()` buffers the entire body into memory before the post-parse `file.size` check runs. The effective ceiling is then nginx's `client_max_body_size` (per `source-upload.ts:41` a global ~32 MB), not the per-route 2 MB (logo) / 5 MB (photo) / 8 MB (extract) limits. Combined with the per-user rate limits (e.g. extract 20/5 min, still 20 concurrent 32 MB buffers per user) this is a modest memory-amplification, not an outage — hence P3 — but it defeats the intended defence.
- **Reproduction:** `curl -H "Transfer-Encoding: chunked" -F file=@big.bin https://…/api/extract` with `big.bin` = 20 MB (a real user session) — the request is buffered fully and rejected only at the `file.size > EXTRACT_MAX_BYTES` line, after the 20 MB is in memory, instead of at the header check.
- **Proposed fix:** don't rely on the header. Stream the body through a counting limit and abort past the cap — read via `req.body` (a `ReadableStream`) with a byte counter that throws at `MAX + slack` before buffering, or wrap `req.formData()`/`arrayBuffer()` so the size is enforced during read. Also set an explicit small `client_max_body_size` per upload `location` in nginx as defence in depth (and document it in `.claude/deploy.md`, which currently only mentions `proxy_read_timeout`).
- **Effort:** M
- **Confidence:** medium — the header-only check is certain from code; the exact buffered ceiling depends on the nginx `client_max_body_size` value, which is not in the repo.

## Checked and OK
- **Prototype pollution (edit ops):** every edit parser deep-scans for `__proto__`/`constructor`/`prototype` before use — `lib/generation/slide-edit.ts:1063,1078` (`BAD_KEYS`+`scan`), `article/edit.ts:637,655`, `work/edit.ts:536,553`, `resume/edit.ts:458,474`, `teacher/edit.ts:1034,1060,1166` — and all op `path`s are validated against strict anchored regexes (`WORK_PATH_RE`, `ARTICLE_PATH_RE`, `RESUME_PATH_RE`, `TEACHER_BLOCK_PATH_RE`/`TEACHER_MODEL_PATH_RE`). `teacher/edit.ts modelLeaf` (`:171-197`) additionally walks with `Object.prototype.hasOwnProperty` and numeric-only array indices, so `teacher.__proto__…`/`teacher.constructor…` resolve to `null`. `set`/`setSection`/`blockInsert` rebuild objects from whitelisted fields only (`normalizeSetDoc`, `normalizeBlocks`, `normalizeTeacherBlock`).
- **DocOps body limits:** `DOC_PATCH_MAX_BYTES=300KB` via `readJson`, `MAX_EDIT_OPS=50` (`preParseOps`), per-string `MAX_STR`, depth ≤8, array ≤200 in `scan`. `baseVersion` validated integer.
- **Slide image ops IDOR/SSRF:** `applyDocOps` image ops require the URL to match `ownAssetUrlRe(genId)` (`slide-edit.ts:782,809,843`); the render `resolveImage` (`edit-adapters.ts:52`, `assets.ts assetImageResolver`) only reads assets of the same generation.
- **SQL injection:** all queries use parameter placeholders; the only template-literal interpolations are constant column lists (`payments.ts:178,218`) and integer page-size/offset in admin search (`admin/users/route.ts`), with the user `q` bound as `$1` (`%${q}%`). No dynamic identifiers or ORDER BY from user input. (Minor: admin ILIKE does not escape `%`/`_` in `q`, but it is admin-only and not an injection.)
- **Content-Disposition:** `contentDisposition` (`file/route.ts:22-25`) strips non-ASCII and `"`/`\` for the ASCII fallback and RFC 5987 `filename*=UTF-8''`+`encodeURIComponent` — CR/LF cannot reach the header. Upload filenames are also stripped of `\r\n\t` before storage (`source-upload.ts:324`, `template-upload.ts:226`).
- **Served content-type / stored XSS:** asset routes force an image/audio allow-list and fall back to `application/octet-stream`, with `X-Content-Type-Options: nosniff` and `Content-Security-Policy: default-src 'none'; sandbox` (`assets/[assetId]/route.ts:11-32`, `o/[token]/audio/[assetId]/route.ts:42-53`, `uploads/photo/[assetId]/route.ts:21-29`). Generated file mimes are engine-controlled (docx/pptx/png/pdf/mp3/xlsx/txt/md/csv — no html/svg/xml), and `?inline=1` is served with `nosniff`. No user-uploaded SVG/HTML/XML is served inline from the app origin.
- **XSS in DOM:** only two `dangerouslySetInnerHTML` sites — QR SVG from the `qrcode` lib over a validated token, and KaTeX `renderToString` with default `trust:false` (so `\href`/`\html*` are inert) (`WordViewer.tsx:1225-1230`, `GameSharePanel.tsx:173`). `lib/viewers/from-html.ts` extracts only `textContent`/structure via `DOMParser`. Public game player (`components/game/*`, `/o/[token]`) renders teacher content as React text; the only dynamic `src` is the token-scoped audio asset URL.
- **SVG → PNG:** all figure/infographic/crossword/OMR SVG builders escape every text and attribute via `xmlEscape` (`lib/generation/xml.ts`) and emit no `<image href>`/`<use>`/`file://`/`http://` references, so LLM/user text cannot inject external references into SVG rendered by sharp/librsvg (`figures/svg.ts`, `infographic/svg.ts`, `games/crossword/svg.ts`, `figures/omr.ts`). Translation writeback into OOXML also escapes (`translate/docx.ts:394`, `pptx.ts:262`, `xlsx.ts:148`).
- **SSRF:** research fetches target fixed hosts with encoded params (`research/http.ts withParams`, `crossref.ts`/`openalex.ts` `encodeURIComponent`, `lexuz.ts lexDocId` rebuilds `https://lex.uz/docs/<numeric-id>`), so LLM output cannot redirect them to internal hosts. `slide-research.ts:167` only HEADs URIs containing `vertexaisearch.cloud.google.com` with `redirect:"manual"` (reads `location` only). No import-by-URL for logo/photo/source. (Defence-in-depth: add a private-IP/host allow-list before any of these fetches.)
- **Image sniffing:** uploads validated by magic bytes, never Content-Type — `sniffImageType` (PNG/JPEG only, `slide-images.ts:130`), `sniffSourceKind` (ext+ZIP marker / `%PDF` / null-byte reject, `source-upload.ts:94`), `looksLikePptx` (`template-upload.ts:47`). `imageDims` PNG/JPEG parsers are bounded (`slide-images.ts:94-119`). sharp is only run on server-generated SVG, never on uploaded image bytes.
- **LLM JSON parsing:** `lib/generation/json.ts` uses only `JSON.parse` with a bounded manual scanner/repair — no `eval`/`new Function`/`vm`.
- **LibreOffice/pdftoppm command exec:** `execFile` (not shell) with fixed binary paths and argument arrays; the only user-influenced arg is a temp path the server itself creates via `mkdtemp` (`pdf.ts:44-73`, `template-upload.ts:90-95`, `thumb.ts`), with `timeout`/`maxBuffer` set and temp dirs removed in `finally`. No user string reaches the argv.
- **Public game scoring:** answers scored server-side (`lib/game/score.ts`), correct answers never sent to the client, `checkOrigin`+IP rate limit+token-shape on submit (`o/[token]/submit/route.ts`).
