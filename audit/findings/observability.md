### OBS-01 — No external error tracking/alerting integration anywhere; no `onRequestError` hook, so server-side page-render errors are invisible outside the browser that hit them
- **Severity:** P1
- **Location:** `instrumentation.ts` (whole file, no `onRequestError` export); `app/error.tsx:19` and `app/global-error.tsx` (both `"use client"`); `package.json` (no `@sentry/*` or APM dependency)
- **Evidence:** `grep -rn "onRequestError\|Sentry\|@sentry\|unhandledRejection\|uncaughtException" lib/ app/ scripts/ instrumentation.ts` → zero matches. Next.js 15's instrumentation hook supports exporting `onRequestError(err, request, context)` specifically to capture render/route errors server-side with request context — not implemented. I verified the actual consequence by reading both error boundaries: `app/error.tsx:19` runs `console.error("[ui]", error.message, error.digest ?? "")` inside a `useEffect` in a `"use client"` component — this executes **in the user's browser**, not on the server; `app/global-error.tsx` (also client-only) shows the same `error.digest` to the user with no corresponding server-side capture. Next.js does generate a `digest` for server render errors and display it to the user (a genuinely good, already-in-place correlation token), but nothing on the server logs "digest `X` = this stack trace," so the code shown to the user is currently a dead end for the owner — they'd have to guess/grep Next's own default stdout output, which is not tied to the digest in a structured, searchable way. Note this is narrower than API-route errors: 38 of 43 `app/api/*/route.ts` files already go through `lib/server/api.ts`'s `handler()` wrapper, which does log every route error server-side (see OBS-03/Checked and OK) — the gap here is specifically Server Component / page-render errors, which use a different Next.js error path that isn't hooked up.
- **Reproduction:** Trigger any uncaught throw inside a Server Component during render (e.g. temporarily throw in a page) — the user sees the styled error screen with a `digest` code; `docker compose logs web` at that moment would show whatever Next.js's default internal handler prints (not attributable to the digest without manual correlation), and nothing external (Sentry, email, Telegram) fires.
- **Proposed fix:** Add `export function onRequestError(err, request, context) { console.error(JSON.stringify({ts: new Date().toISOString(), level: "error", msg: "request_error", digest: (err as any)?.digest, path: request.path, err: err instanceof Error ? err.message : String(err), stack: err instanceof Error ? err.stack : undefined})); }` to `instrumentation.ts` — this alone makes the digest shown to users actually correlatable to a server log line. For real alerting (not just better logs), wire a free-tier Sentry or self-hosted GlitchTip DSN and call `Sentry.captureException(err)` in the same hook plus in `lib/server/api.ts`'s `serverError()` — this is the single highest-leverage change in this audit for "can the owner find out quickly," since right now finding out requires already being logged into the server tailing output.
- **Effort:** S (onRequestError + digest correlation) / M (external Sentry-equivalent wiring)
- **Confidence:** high

### OBS-02 — No structured logging and no correlation id threading web request → generation → worker job; ~300 free-text `console.*` call sites, tagged by module scope but not by job/user/request id
- **Severity:** P1
- **Location:** representative verified sites: `lib/server/worker.ts:298` (`` console.error(`[worker] job ${job.id} failed:`, message) ``), `lib/server/api.ts:29` (`serverError`: `` console.error(`[${scope}]`, message) `` — `scope` is a route name like `"generations"`, not a request/job id), `app/api/payments/click/route.ts:146` (`console.error("[click]", ...)` — no order id, no user id in the log line itself, only in the return payload), `app/api/telegram/webhook/route.ts:44`, `lib/server/db.ts:47` (`` console.error("[db] idle client error:", err.message) ``)
- **Evidence:** `grep -rn "console\.\(log\|warn\|error\|info\)" --include="*.ts" --include="*.mts" lib/ app/ scripts/ instrumentation.ts | wc -l` → **300** call sites, confirmed by direct count (not estimated). The codebase does have a consistent *module-scope* tagging convention (`[worker]`, `[click]`, `[payme]`, `[telegram/webhook]`, `[db]`, `[gemini]`, `[gemini-image]`, `[config]`) which is better than "pure free text" and does let an operator `grep '\[worker\]'` — this is worth crediting. But none of these tags are machine-parseable fields, and critically **no request id exists anywhere**: nothing is generated in a route handler, nothing threaded into the `generations` row, nothing echoed to the client. Concretely: `lib/server/worker.ts:298` *does* interpolate `job.id` (the generation UUID) directly into the log message string — this is the best case in the codebase — but `lib/server/api.ts:29`'s `serverError(scope, e)` (used by 38/43 routes) logs only `[scope] message`, with **no user id, no generation id, no request id**, even though the route handler that caught the error typically has a `user.id` in scope. So: the chain "user reports issue at 2pm → find their HTTP request → find which generation it touched → find the worker's LLM-provider calls for that generation" has no shared machine-readable key at any hop; `grep`ing the raw UUID through `docker compose logs` and hoping every relevant line happens to mention it is the actual state of the art today.
- **Reproduction:** `grep -n "console.error" lib/server/api.ts` → confirms `serverError()` logs `[scope] message` only, no structured fields. `grep -n "requestId\|reqId\|X-Request-Id" app/ lib/ next.config.ts` → zero matches anywhere in the app.
- **Proposed fix:** Add `lib/server/log.ts` exporting `log(level, msg, fields?)` emitting one JSON line (`{ts, level, msg, ...fields}`) to stdout (still Docker json-file, now `jq`-able). Thread `jobId`/`userId`/`toolId` through `lib/server/worker.ts` and `lib/server/jobs.ts` (highest value — the money/job path), and pass `user.id` into `serverError(scope, e, {userId: ctx.user?.id})` at each of the 38 `handler()`-wrapped call sites (mechanical, one extra arg). Generate a per-request id in a thin wrapper (or `crypto.randomUUID()` at the top of `handler()` itself, since every route already funnels through it) and echo as `X-Request-Id` response header. Not necessary to convert all 300 sites in one pass — start with `worker.ts`, `jobs.ts`, `payments.ts`, `credits.ts`, `api.ts`'s `serverError`.
- **Effort:** M (helper + the ~6 highest-value files) / L (whole codebase)
- **Confidence:** high

### OBS-03 — Stack traces are systematically discarded; every catch block logs `err.message` (or a bare string) only, never `err.stack` — confirmed codebase-wide, not an isolated spot
- **Severity:** P1
- **Location:** `lib/server/worker.ts:242,298,364,378` (all `e instanceof Error ? e.message : e`), `lib/server/api.ts:28` (`serverError`: `` const message = e instanceof Error ? e.message : String(e) ``), `app/api/payments/click/route.ts:146`, `app/api/payments/payme/route.ts:226`, `app/api/telegram/webhook/route.ts:44`, `lib/server/db.ts:47` (`err.message` even for the pool-level error listener) — pattern verified at 9 independent call sites across 6 different files, all following the identical `e instanceof Error ? e.message : ...` idiom
- **Evidence:** Every error-logging call site read this pass, without exception, extracts only `.message` (a one-line human string) and discards `.stack` (the actual call-site/line-number trail needed to find *where* in a 274-file, ~81k-line generation engine (per scout `generation.md`) something broke). Example, `lib/server/worker.ts:296-298`: `` } catch (e) { const message = e instanceof Error ? e.message : "Yaratishda xatolik"; console.error(`[worker] job ${job.id} failed:`, message); ``. For a shallow error (a thrown `new Error("Fayl bo'sh chiqdi")`, itself visible at `worker.ts:229`) the message alone is enough. For a deep error surfacing from inside the LLM/render pipeline (JSON parse failure, a library exception inside `render-pptx.ts`/`render-docx.ts`, a `sharp`/LibreOffice child-process failure), the message alone often will NOT say which of the ~15-35 LLM calls or which rendering step failed (per scout `generation.md` §6's worst-case call counts) — the operator is left re-reading source to guess, instead of reading a stack trace that would point at the exact throw site.
- **Reproduction:** `grep -rn "instanceof Error ? e.message" lib/server/*.ts app/api/**/*.ts | wc -l` reproduces the count directly; inspect any one hit to confirm `.stack` is never referenced alongside it (`grep -n "\.stack" lib/server/*.ts app/api/**/*.ts` → zero matches project-wide in the files read this pass).
- **Proposed fix:** In the same `log()` helper proposed in OBS-02, accept the raw `Error` object and always include `stack: err instanceof Error ? err.stack : undefined` in the emitted JSON (stdout only — never returned to the client, which already correctly happens per `serverError`'s prod/dev branching at `api.ts:33`). This is a pure addition (one field), zero behavior change, and turns every one of the 9+ call sites above into a debuggable trace instead of a one-line guess.
- **Effort:** S
- **Confidence:** high

### OBS-04 — No alerting of any kind: `/api/health` is pull-only and nothing polls it; Docker has no `healthcheck:` on `web`/`worker`; worker-dead, queue-stuck, DB-down and provider-storm scenarios all fail silently until a user complains
- **Severity:** P1
- **Location:** `docker-compose.yml` (healthcheck block present only for `postgres:`, absent for `web:` and `worker:`); `app/api/health/route.ts` (exists, correctly reports `db`/`queue`/`problems`, but is never called by anything automated); `.claude/deploy.md` §3 (the only place `/api/health` is invoked — once, manually, right after a deploy)
- **Evidence:** `docker-compose.yml`, read in full: `postgres:` has a `healthcheck:` stanza (`pg_isready`, 10s interval); `web:` and `worker:` have none. This means Docker's `restart: unless-stopped` only fires on hard process *crash*, never on "process alive but degraded" — precisely the scenario `audit/00-baseline.md` already demonstrated for boot-time config (missing `TELEGRAM_BOT_TOKEN` → process stays up, answers 500/`/api/health` included, forever, because it never crashes). That baseline finding is the boot-time special case; this finding is the general-case root cause: even post-boot, a DB connection that starts failing, a queue that stops draining, or a worker whose `loop()` throws past its own top-level catch (see OBS-05) leaves the container marked healthy by Docker indefinitely, because nothing is wired to `/api/health` at all — not Docker, not an external uptime check, not a cron. `grep -rn "healthcheck\|curl.*health" docker-compose.yml Dockerfile .claude/deploy.md scripts/` confirms the only hit is the one-time manual `curl` in the deploy runbook.
- **Reproduction:** `docker-compose.yml` inspection alone is definitive (no prod access needed): `web:`/`worker:` blocks contain `build`, `restart`, `depends_on`, `environment`, `ports`/nothing-extra — no `healthcheck:` key.
- **Proposed fix:** S: add `healthcheck: { test: ["CMD", "curl", "-f", "http://localhost:3000/api/health"], interval: 30s, timeout: 5s, retries: 3 }` to `web:` in `docker-compose.yml` (the route already returns 503 on DB-down, matching Docker's contract exactly — zero app-code change). M: a small script (host crontab, or inside the `worker` container which already runs scheduled housekeeping per `lib/server/worker.ts`'s `housekeeping()`) that polls `/api/health` with the `CRON_SECRET` bearer token every 1–5 minutes and posts to the owner's Telegram via the already-working `sendMessage()` in `lib/server/telegram.ts:49` on any non-"ok" status. This single script is the answer to "worker dead," "queue stuck" (once combined with OBS-08's proposed `oldestQueuedAgeSec`), and "DB down" simultaneously.
- **Effort:** S (compose healthcheck) + M (Telegram polling cron)
- **Confidence:** high

### OBS-05 — If `refund()` itself throws after `failJob()` already succeeded, the failure is swallowed into a generic catch-all with no job-specific signal — a real "user paid, job failed, refund silently didn't happen" path
- **Severity:** P1
- **Location:** `lib/server/worker.ts:296-303` (the `runJob` catch block) and `lib/server/worker.ts:316-317` (`tick()`'s outer catch)
- **Evidence:** Quoting the exact code:
  ```
  } catch (e) {
    const message = e instanceof Error ? e.message : "Yaratishda xatolik";
    console.error(`[worker] job ${job.id} failed:`, message);
    if (await failJob(job.id, WORKER_ID, message)) {
      await refund(job.userId, job.id, `Xatolik: ${message}`.slice(0, 200));
    }
  } finally { ... }
  ```
  This block is **not** individually try/caught around the `refund()` call. If `failJob()` succeeds (job correctly marked `FAILED`, per `lib/server/jobs.ts:462-473`) but the subsequent `refund()` call then throws (e.g. a transient DB error, pool exhaustion, or the `transaction()` wrapper's `SELECT ... FOR UPDATE` timing out — all realistic under the audit's target load of 2 000 concurrent / 10× bursts, exactly when DB connection pressure is highest), that exception propagates out of `runJob()` entirely. It is then caught only by `tick()`'s generic handler (`worker.ts:316-317`): `` .catch((e) => console.error("[worker] unexpected:", e)) `` — a single undifferentiated log line with **no job id, no user id, no indication this was specifically a failed-refund** (contrast with `runJob`'s own catch, which *does* include `job.id`). The net effect: the generation is correctly `FAILED` (visible to the user), the user was correctly charged at enqueue time (per `chargeInTx`, per `server.md` §5), but the refund that should have reversed that charge silently did not happen, and the only trace is one generic `"[worker] unexpected:"` line indistinguishable from any other unexpected worker error — exactly the "I paid and got nothing" scenario the audit brief opens with, and it would not be found by grepping for the job id since the id isn't in that particular log line.
- **Reproduction:** Sketch: mock `refund()` to throw on its second internal query (simulating a pool-exhaustion mid-transaction failure) while `failJob()` succeeds normally; call `runJob(job)` and assert (a) `generations.status = 'FAILED'` for that id, (b) no `transactions` row with `kind='refund'` and `reference=job.id` exists, (c) the only log output is the generic `tick()` line with no `job.id` field — demonstrating the gap is real and that the existing tests (per `tests/document.test.mts` and friends) do not currently cover "refund call itself fails."
- **Proposed fix:** Wrap the `refund()` call in its own try/catch inside `runJob`'s catch block, so a refund failure logs its own specific, job-id-tagged line (e.g. `` console.error(`[worker] job ${job.id}: REFUND FAILED after fail — manual credit needed`, refundErr) ``) distinguishable by an alerting script (OBS-04) via a fixed substring like `REFUND FAILED`. Longer-term (ties to OBS-06): write this case into a queryable place (e.g. a `needs_manual_review` flag on the row, or reuse the `error` column with a distinguishable prefix) so a daily summary script (OBS-13) can list "generations FAILED with no matching refund transaction" as a standing reconciliation query — this is exactly the kind of drift the brief asks support to be able to answer.
- **Effort:** S (try/catch + distinct log line) / M (queryable flag + reconciliation query)
- **Confidence:** high — code path and control flow directly verified by reading `worker.ts:162-322` in full; the *likelihood* of `refund()` throwing under load is reasoning (DB pressure at target scale), not a measurement, but the code-level gap itself (no inner try/catch around this specific call) is not in doubt.

### OBS-06 — Several genuinely silent (`.catch(() => {})`, no logging at all) catch blocks, plus one on the health/monitoring path itself
- **Severity:** P2
- **Location:** `lib/server/worker.ts:108` (`heartbeat(...).catch(() => {})`), `:115` (`setProgress(...).catch(() => {})`), `:185` (`setProgress(...).catch(() => {})`), `:270-271` (`deleteGenerationFile(...).catch(() => {})`, `deleteAssets(...).catch(() => {})`); `app/api/health/route.ts:60` (`queueDepth().catch(() => null)`)
- **Evidence:** Five confirmed truly-empty catches (verified by direct read, not grep pattern-matching alone). Three are low-stakes by design: `:108/115/185` are heartbeat/progress-bar writes that fire every 2 seconds (`progressTicker`'s `setInterval`, `worker.ts:104-116`) — a single dropped write is harmless because the next tick retries, and `reclaimStaleJobs()` (per `server.md` §3) independently catches true staleness via `locked_at` age, so this pair is reasonable to leave silent (noted, not flagged as a fix target). The `:270-271` pair (cleanup of file/asset rows when a job's lock was lost to a competing worker/reclaim, `worker.ts:265-272`) is lower-stakes too (worst case: an orphaned `generation_files`/`generation_assets` row for a result nobody will ever fetch — storage waste, not money/correctness) but is worth a one-line log since it's the kind of thing that, aggregated, explains unexplained storage growth. The one that matters most: `app/api/health/route.ts:60`, `` queue = await queueDepth().catch(() => null); `` — this is on the **detailed health-check path itself**, the exact endpoint an alerting script (OBS-04's proposed fix) would poll. If the queue-depth query throws (DB blip, lock contention), the response silently shows `queue: null` with **`status` still computed from `db` alone** (`app/api/health/route.ts`'s `healthy` variable), so `status: "ok"` can coexist with a broken queue-depth query and nobody would know — the one place in the codebase where a silent catch directly undermines observability tooling that this audit is recommending be built.
- **Reproduction:** All five confirmed by direct source read (`worker.ts` lines cited; `health/route.ts:60` quoted in full above). For the health-route case specifically: simulate `queueDepth()` throwing (e.g. a lock-timeout on the aggregate query under load) — response would show `{"status":"ok" or "degraded" (based on db only), "queue": null, ...}` with no `queueError` field to distinguish "empty queue" from "broken query."
- **Proposed fix:** For `worker.ts:270-271`, add a one-line `console.warn` on rejection (cheap, aids storage-drift forensics). For `health/route.ts:60`: `` queue = await queueDepth().catch((e) => { console.error("[health] queueDepth failed:", e instanceof Error ? e.message : e); return null; }); `` and add `queueError: boolean` to the JSON response so a polling alert script can distinguish the two cases.
- **Effort:** S (all five)
- **Confidence:** high

### OBS-08 — Job forensics: `generations.error` is a single free-text column overwritten on every attempt; no stage/provider/attempt-history breakdown survives a retry
- **Severity:** P2
- **Location:** `lib/server/jobs.ts:462-473` (`failJob`), `:341-366` (`claimJob`, increments `attempts` as a bare counter)
- **Evidence:** Quoting `failJob` in full:
  ```
  export async function failJob(id: string, workerId: string, message: string): Promise<boolean> {
    const rows = await query<{ id: string }>(
      `UPDATE generations
          SET status = 'FAILED', progress = 100, step = 'Xatolik',
              error = $3, finished_at = now(), locked_by = NULL, locked_at = NULL,
              live_json = NULL
        WHERE id = $1 AND locked_by = $2 AND status = 'IN_PROGRESS'
        RETURNING id`,
      [id, workerId, message.slice(0, 500)],
    );
    return rows.length > 0;
  }
  ```
  `error` is set with a plain `UPDATE` (not appended), so if attempt 1 fails with message A and — per `reclaimStaleJobs()`'s "max 2 attempts" policy (`server.md` §3) — attempt 2 fails with message B, only B survives; A is gone from the database entirely and exists only in worker logs (if at all, and only correlatable by grepping the raw job id per OBS-02). There is also no `stage` (outline/body/render/image) or `provider` (which LLM/image provider was active) column — `failJob`'s only input beyond identity is the one `message` string. Combined with OBS-03 (stack traces dropped) and OBS-02 (no log correlation), reconstructing "why did my job fail" beyond whatever that one final string says requires the owner to already know Uzbek-language conventions well enough to interpret it correctly (e.g. `reclaimStaleJobs`'s own failure message is the fixed string `"Ish vaqti tugadi"` — accurate but generic; it doesn't say the job was on attempt 2 of a translation vs. a coursework, or which provider was mid-call when the timeout hit).
- **Reproduction:** `grep -n "error = \$3\|UPDATE generations" lib/server/jobs.ts` confirms the plain overwrite; no `error_history` or `error_detail` table/column exists (`grep -n "error_history\|error_detail\|error_stage" lib/server/migrations/*.sql` → no matches).
- **Proposed fix:** Additive migration `NNN_error_detail.sql` adding `error_detail JSONB` to `generations`, written by `failJob()` (extend its signature to accept `{stage?, provider?, attempt}` alongside `message`) with `{stage, provider, attempt, message, ts}` — leaves the existing `error TEXT` column untouched for display compatibility, follows the same non-invasive pattern as the project's own `cost_json`/`delivered_json` additions (migrations 010/020 per `server.md`'s schema history).
- **Effort:** M (migration + threading `stage`/`provider` through worker.ts's catch and each engine's top-level error path)
- **Confidence:** high (failJob's exact SQL and signature directly read)

### OBS-09 — Click/Payme webhook raw request bodies are never persisted; `payment_orders` stores only derived fields, so a disputed amount/state can't be re-verified against what the provider actually sent
- **Severity:** P2
- **Location:** `lib/server/payments.ts:178-179` (`COLS` — the full column list for `payment_orders`, no raw-payload field), `:231-259` (`attachTransaction`), `:276-311` (`settleOrder`), `:313-325` (`cancelOrder`) — all take specific scalar params (`orderId`, `txn`, `createTime`, `performTime`, `reason`), never the full parsed webhook body
- **Evidence:** Read `payments.ts` in full: the `COLS` constant (`id, user_id, provider, purpose, amount_soum, state, provider_txn, create_time, perform_time, cancel_time, cancel_reason, prepare_id, created_at`) is exactly what the app needs to run its state machine and idempotency check — not a transcription of the webhook. `attachTransaction`/`settleOrder`/`cancelOrder` each take a handful of scalars extracted by the route handler (`app/api/payments/click/route.ts`/`payme/route.ts`), and neither route logs nor stores the full `p`/`params` object anywhere except inside a generic catch-all error log (`console.error("[click]", ...)`/`console.error("[payme]", ...)`) that only fires on exceptions, not on the normal path. So for the normal "webhook arrived, everything parsed fine, but the amount/state Click's own dashboard shows later doesn't match" dispute, there is no stored artifact to diff against — only the derived columns, which are correct *if* the parsing logic was correct, but a parsing bug or provider protocol edge case would be invisible in hindsight since the triggering input wasn't kept.
- **Reproduction:** `grep -n "raw\|payload\|body" lib/server/payments.ts` → no matches; the full `COLS` list (quoted above) is definitive — confirmed by direct read, not inference.
- **Proposed fix:** Add a `payment_webhook_log` append-only table (safer than a column on `payment_orders`, since it captures **every** webhook call including retries/duplicates, not just the row's current state) — one `INSERT` at the top of both `app/api/payments/click/route.ts POST` and `app/api/payments/payme/route.ts POST`, storing the full parsed body verbatim plus timestamp. - **Effort:** S (one table + one insert per webhook route)
- **Confidence:** high (upgraded from an earlier draft that had not yet read `payments.ts` — now directly verified against the full file)

### OBS-10 — No log rotation configured for the Docker `json-file` driver on any service; logs accumulate unbounded on a box already shared with two other projects
- **Severity:** P2
- **Location:** `docker-compose.yml` (no `logging:` key on any of `postgres`/`web`/`worker`)
- **Evidence:** `grep -n "logging:\|max-size\|max-file" docker-compose.yml` → zero matches. Docker's default `json-file` driver, unconfigured, retains the entire stdout/stderr history for a container's lifetime with no automatic rotation (`/var/lib/docker/containers/<id>/<id>-json.log` grows unbounded). Per `.claude/deploy.md` §2, `docker compose -p slaydx build && up -d` recreates containers on each deploy (which incidentally resets each log file), so this is bounded by deploy frequency in the common case — but between deploys, and especially during an incident where something is crash-looping or retrying loudly (e.g. a provider outage causing `withRetry`'s repeated 429/5xx retries across every in-flight job, per scout `generation.md` §3), log volume is uncapped exactly when it spikes most. Per `.claude/deploy.md`'s own warning, the box also runs `nodavlattalim` (4 containers) and `mser` — disk pressure from SlaydX's logs can starve unrelated projects on the same host, and `/api/health` has no disk-space check to surface this before it becomes an outage.
- **Reproduction:** Direct inspection of `docker-compose.yml` is definitive without prod access — absence of the `logging:` key on `web`/`worker`/`postgres` confirmed by full read.
- **Proposed fix:** Add `logging: { driver: "json-file", options: { max-size: "10m", max-file: "5" } }` to each service in `docker-compose.yml` — caps retained logs at 50 MB/service, zero code change, standard Compose hygiene.
- **Effort:** S
- **Confidence:** high

### OBS-12 — `queueDepth()` returns only counts, not oldest-queued age or last-worker-heartbeat age — `/api/health` can't distinguish a healthy burst from a dead worker
- **Severity:** P2
- **Location:** `lib/server/jobs.ts:523-531` (`queueDepth`, full function quoted below); `app/api/health/route.ts:60`
- **Evidence:** Full function:
  ```
  export async function queueDepth(): Promise<{ queued: number; running: number }> {
    const row = await queryOne<{ queued: string; running: string }>(
      `SELECT
         count(*) FILTER (WHERE status = 'QUEUED')::text      AS queued,
         count(*) FILTER (WHERE status = 'IN_PROGRESS')::text AS running
       FROM generations`,
    );
    return { queued: Number(row?.queued ?? 0), running: Number(row?.running ?? 0) };
  }
  ```
  Two raw counts, no timestamps. `queued=12` is indistinguishable between "burst of normal traffic, clearing in 30s" and "worker died an hour ago, jobs piling up" — exactly the ambiguity an on-call owner needs resolved in the first 10 seconds of looking at `/api/health`. The primitive already exists nearby: `reclaimStaleJobs()` (`server.md` §3) already compares `locked_at` against a budget-derived timeout internally — the same `generations.created_at`/`locked_at` columns this function already reads are sufficient to compute "oldest QUEUED age" and "oldest IN_PROGRESS age" with one extra `MIN()` each.
- **Reproduction:** Function body quoted above, directly read — no aggregate age/timestamp field is computed or returned.
- **Proposed fix:** Extend `queueDepth()` to also return `oldestQueuedAgeSec` (`SELECT EXTRACT(EPOCH FROM (now() - MIN(created_at))) FROM generations WHERE status='QUEUED'`) and `oldestRunningAgeSec` similarly for `IN_PROGRESS`; surface both in `app/api/health/route.ts`'s existing `queue` object. Matches the audit brief's own suggested fix verbatim.
- **Effort:** S
- **Confidence:** high

### OBS-14 — `transactions.reference` overloads one `TEXT` column with two different meanings (generation UUID for charge/refund, `"provider:providerTxn"` composite string for topup/subscription) — reconstructing "which payment funded this transaction" needs string-parsing, not a join
- **Severity:** P3
- **Location:** `lib/server/payments.ts:284` (`` const reference = `${order.provider}:${order.providerTxn ?? order.id}`; ``, then passed into `topUp`/`activatePro`); contrast with `lib/server/worker.ts` (`refund(job.userId, job.id, ...)` — `job.id` used directly as `reference`, a bare generation UUID)
- **Evidence:** Confirmed directly: for a `charge`/`refund` transaction, `reference` = the generation's UUID (usable as a direct FK-style join against `generations.id`). This is workable — the `UNIQUE(kind, reference)` index still gives correct idempotency regardless of which shape `reference` takes — but a support query written to "reconstruct a user's money history with a reference to the job/payment" (the audit brief's own phrasing) has to branch on `kind` to know which table/parsing rule applies, and a future third `kind` that doesn't fit either shape would silently break that branch.
- **Reproduction:** Directly read: `payments.ts:284` (composite-string construction) vs. `worker.ts`'s plain `job.id` usage in `refund()`/`refundPartial()` calls — the asymmetry is confirmed by code, not inferred.

- **Effort:** S
- **Confidence:** high (both code paths directly read this pass)

## Checked and OK
- **Worker crash resilience is actually solid, contrary to an initial hypothesis**: `runJob()` wraps the whole per-job pipeline in try/catch (`worker.ts:188-307`, routes failures to `failJob`+`refund`); `tick()` wraps `runJob()`'s promise in a second catch (`:316-317`); `loop()`'s per-tick call is wrapped (`:375-381`); and the standalone worker container's entry point, `scripts/worker.ts`, wraps `runWorkerProcess()` with `` .catch((e) => { console.error("[worker] fatal:", e); process.exit(1); }) `` — this logs the **full error object** (not just `.message`) and exits with a non-zero code, which correctly triggers Docker's `restart: unless-stopped`. Since production sets `WORKER_INLINE=false` (`docker-compose.yml` `worker:` service), this is the code path actually used in prod. The weaker in-process fatal handler in `startInlineWorker()` (`worker.ts:397-401`, logs but does not exit) only applies to the inline-worker code path, which production's `web:` service explicitly disables (`WORKER_INLINE: "false"`) — so it's a dev-only weakness (dev's `.env.local` defaults to `WORKER_INLINE=true`), not a production one. Correcting an earlier draft of this audit that assumed the worse case without reading the code.
- **38 of 43 API routes already funnel every error through a shared handler**: `lib/server/api.ts`'s `handler(scope, fn)` wrapper (`:172-190`) catches everything, converts `ApiError` to its intended status code, and routes anything else through `serverError(scope, e)` which logs `` console.error(`[${scope}]`, message) `` and returns a generic 500 to the client (never leaking internals in prod — `env.isProd` branch at `api.ts:33`). The 5 routes that don't use this shared wrapper (`health`, `telegram/webhook`, `payments/click`, `payments/payme`, `auth/telegram/enter`) were individually read and confirmed to each have their own equivalent try/catch with `console.error` logging — none of the five silently swallow an error to the client without at least a server-side log line.
- **No API-key leakage into logs via query-string URLs**: hypothesized in an earlier draft of this audit, then directly checked and refuted — `lib/generation/llm.ts` and `lib/generation/image-provider-gemini.ts` both authenticate Gemini via the `x-goog-api-key` HTTP **header** (`llm.ts:260,405,621`; `image-provider-gemini.ts:189`), never a `?key=` query parameter, and every error-log call site in both files logs only `res.status` and the provider's own `data.error?.message` (a description string), never the request URL, headers, or body. No prompt/document text is logged at any of these sites either.
- **No OTP codes, phone numbers, or session tokens found in server-side logs**: `grep`ed `lib/server/auth.ts`, `lib/server/session.ts`, `lib/server/telegram.ts`, and `app/api/auth/otp/route.ts` for `console.*` calls — the few that exist (`telegram.ts:39,44`) log only the Telegram Bot API's own error description or a generic "network error" string, never a token/code/phone value. (Separate, out of this auditor's scope: `app/api/auth/otp/route.ts:60` returns the OTP code directly in the HTTP **response body** when in a dev-login path — a response-body/auth-bypass concern for the security auditor, not a logging concern, so not written up here as an OBS finding.)
- **Payment idempotency is a data-integrity control that already works, independent of the observability gaps above**: `transactions(kind, reference)` UNIQUE and `payment_orders(provider, provider_txn)` UNIQUE (confirmed via `payments.ts`'s `attachTransaction`/`topUp`'s own duplicate-check `SELECT` before insert) mean a replayed webhook cannot double-credit. The realistic failure mode this audit worries about is "webhook silently never arrives or never gets processed and nothing notices" (OBS-04's alerting gap), not "webhook double-processed" (already guarded, verified directly in code).
- **Rate-limited requests are self-documenting to the caller**: `lib/server/api.ts`'s `limit()` throws an `ApiError` with a 429 status and `Retry-After` header directly to the client — not a forensics gap, since the client-visible response is the signal, and `rate_limits` remains a queryable table if aggregate analysis is ever needed.
