### BEA-01 — `priceFor` prices unknown/untrimmed package values at the cheapest tier, while the engines trim/clamp them up to the largest package
- **Severity:** P1
- **Location:** `lib/tools.ts:1392-1468` (`priceFor`: essay 1408-1413, referat/mustaqil-ish 1414-1424, coursework 1425-1439, glossary 1460-1463); engines: `lib/generation/work/registry.ts:383-386` (`normalizeWorkPages` — `.trim()` + default `"20-25"`), `lib/generation/essay/input.ts:76-82` (`pagesOf` — `Number()` + clamp 1..5), `lib/generation/teacher/input.ts:103-106,213-215` (`num` — clamp 10..40 for glossary); server gate `app/api/generations/route.ts:94-103` (only `missingRequired` + `preflightError`, neither validates `pages`/`termCount`).
- **Evidence:** price is an exact-string table lookup with a cheap fallback:
  `{"10-15":12000,…,"40-45":24000}[pages] ?? tool.basePrice` (coursework, basePrice 12000), `{…"25-30":6000}[pages] ?? 3000` (referat/mustaqil-ish), `{"1":2000,…,"5":4000}[pages] ?? 2000` (essay), `{"10":6000,"20":9000,"40":15000}[n] ?? tool.basePrice` (glossary, 6000).
  The engines read the same field leniently: `normalizeWorkPages` does `String(raw).trim()` and falls back to `"20-25"`; essay `pagesOf` does `Number(raw)` and clamps to 1..5; glossary `num()` accepts any integer 10..40. So values the price table does not recognise are billed at the minimum but produced at full size:
  | tool | value sent | charged | produced (list price) |
  |---|---|---|---|
  | coursework | `"40-45 "` (trailing space) | 12 000 | 40-45 pages (24 000) |
  | coursework | `"zzz"` | 12 000 | 20-25 pages (16 000) |
  | referat / mustaqil-ish | `"25-30 "` | 3 000 | 25-30 pages (6 000) |
  | essay | `"5 "`, `"99"`, `"4.6"` | 2 000 | 5 pages (4 000) |
  | glossary | `"39"` | 6 000 | 39 terms (≈15 000) |
  No server check rejects these (`missingRequired` only tests "filled"; `preflightError` validates article types and translation langs but not `pages`/`termCount`). This breaks the project rule "Narx serverda hisoblanadi" — any logged-in user can buy the largest packages for 40-50 % of list price by editing one field in DevTools. Per the cost model in `lib/tools.ts:106-112` (≈4 000 so'm COGS for a 10–15 page article) COGS of long documents is a sizeable fraction of price, so the discounted jobs can be near or below cost.
- **Reproduction:** logged-in session cookie, then
  `curl -X POST https://<host>/api/generations -H 'Content-Type: application/json' -H 'Origin: https://<host>' -b 'slaydx_session=…' -d '{"slug":"coursework","values":{"topic":"Iqtisodiyot asoslari","university":"TDIU","author":"Ali Valiyev","pages":"40-45 "}}'` → `202 {"price":12000}`; the finished DOCX is a 40-45 page work. Unit test sketch: `assert.equal(priceFor(TOOL_BY_ID.coursework, {pages:"40-45 "}), priceFor(TOOL_BY_ID.coursework, {pages:"40-45"}))` fails today (12000 vs 24000); same for `essay {pages:"5 "}` and `glossary {termCount:"39"}`.
- **Proposed fix:** make price and engine read ONE normalised value: in `priceFor` call the same normalisers the engines use (`normalizeWorkPages(kind, values.pages)`, essay `pagesOf`, teacher `num`/`nearest` against `limits.terms`) before the table lookup; additionally reject non-listed values in `preflightError` (400 "Noma'lum hajm") so the fallback path is never billed. Add the table above as a parametrised test in `tests/pricing.test.mts`.
- **Effort:** S
- **Confidence:** high

### BEA-06 — `GET /api/generations` has no pagination (items beyond the newest 100 become unreachable) and reads `values_json` (up to ~400 KB/row) for every row, while the home page polls it every 3 s
- **Severity:** P1
- **Location:** `app/api/generations/route.ts:14-18`, `lib/server/jobs.ts:72-76` (`ROW_COLUMNS` includes `values_json` and `preview`), `lib/server/jobs.ts:196-205` (`listGenerations(userId, limit = 100)`, no cursor), `lib/server/jobs.ts:110-136` (`rowToSummary` drops `values_json`), client `lib/api-client.ts:274-276`, `components/home/HomeFiles.tsx:36-43` (`setInterval(refreshGenerations, 3000)` while any job is QUEUED/IN_PROGRESS).
- **Evidence:** (a) Correctness: generations are kept forever (`011_no_expiry.sql`, "MUDDATSIZ"), but the only list API returns `ORDER BY created_at DESC LIMIT 100` with no `before`/`page` parameter and the client never pages. A teacher/student with >100 documents can no longer see, open, download or delete anything older from the UI (the only entry point is this list). (b) Cost: `SELECT ${ROW_COLUMNS}` pulls `values_json` for every row although `rowToSummary` discards it. `values_json` carries `sourceText` for every text-mode translation and every "Fayl asosida" job (≤200 000 chars ≈ 400 KB UTF-8, `validate.ts:31,85`) and 24 000-char JSON fields for resume/article forms. A user with a few dozen such rows makes each list call read and transfer tens of MB out of Postgres (TOAST detoast), and node-postgres `JSON.parse`s every `values_json` on the single web event loop before `rowToSummary` throws it away. The same projection is used by `getGeneration`, so the viewer's 1–4 s poll of a text-mode translation re-reads its ~400 KB `values_json` on every tick. (c) Amplification: `HomeFiles` re-runs this query every 3 s for as long as any job is queued/running; with `WORKER_CONCURRENCY=2` queues are long exactly at peak, so at ~500 users watching a queued job that is ≈170 list queries/s × (100 rows incl. `values_json` + `preview`). This is the dominant read path under the brief's peak (exam season) and will saturate the single shared Postgres/VPS I/O well before 2 000 concurrent users.
- **Reproduction:** as a user with >100 generations: `GET /api/generations` → exactly 100 items, no cursor; the 101st is invisible in the UI. Load: seed one user with 50 translation jobs whose `values_json.sourceText` is 150 000 chars, then `EXPLAIN (ANALYZE, BUFFERS) SELECT <ROW_COLUMNS> FROM generations WHERE user_id=$1 ORDER BY created_at DESC LIMIT 100` → tens of MB of shared/TOAST buffers per call; `autocannon -c 50 -d 30 /api/generations` with that cookie shows DB-bound throughput.
- **Proposed fix:** add a `LIST_COLUMNS` without `values_json` (and a trimmed `preview`) for `listGenerations`; add keyset pagination (`?before=<created_at>,<id>` + `limit ≤ 50`) and a "load more" in `HomeFiles`; poll only the running items (`GET /api/generations/[id]`, which already exists) instead of the whole list; also drop `values_json` from `getGeneration`'s projection (it is not returned to the client either).
- **Effort:** M
- **Confidence:** high for the missing pagination and the discarded `values_json` read; medium for the exact saturation point — confirm with `pg_stat_statements` (mean `shared_blks_hit`/`temp` for the list query) and the distribution of `pg_column_size(values_json)` in production.

### BEA-20 — `GET /api/generations/[id]/file?format=pdf` spawns an unbounded number of LibreOffice processes (no rate limit, no concurrency cap, no memory limit) on the shared VPS
- **Severity:** P1
- **Location:** `app/api/generations/[id]/file/route.ts:61-93` (no `limit()` anywhere in the route; every `?format=pdf` → `toPdf`), `lib/server/pdf.ts:165-209` (fresh `soffice --headless` with its own `-env:UserInstallation` profile per call, `timeout: 90_000`, no semaphore), compare `lib/server/thumb.ts:36,81-93` (thumbs DO use a 2-slot limiter); `lib/server/template-upload.ts:86-87` (same `toPdf`, only a per-user 5/10 min limit); `Dockerfile:48` (LibreOffice in the web image), `docker-compose.yml` (no `mem_limit`/`deploy.resources` for `web`).
- **Evidence:** each PDF view/download starts a separate LibreOffice instance (≈150–300 MB RSS, CPU-bound for 2–30 s on a 40-page DOCX, up to 90 s) inside the single web container, and nothing bounds how many run at once: the thumbnail path learned this lesson (`MAX_PARALLEL = 2`), the PDF path did not. At exam-season peak, a few dozen students pressing "PDF" (or merely opening the Tarjimon "Fayl" tab, whose iframe loads `?format=pdf&inline=1` on every view — `components/viewers/TranslationViewer.tsx:187`, and BEA-07 prevents any browser caching) within the same minute means a few dozen `soffice` processes → several GB of RAM and all cores on a VPS shared with two other projects and Postgres; one logged-in user can do the same deliberately with `for i in $(seq 50); do curl … &; done` on any of their own DOCX. Likely outcome: the kernel OOM-killer picks the largest process (often Postgres or the Node server) → outage for every project on the box; the containers are not memory-capped, so the damage is not contained to `web`.
- **Reproduction:** with a session cookie and one completed DOCX id: `seq 40 | xargs -P40 -I{} curl -s -o /dev/null -b 'slaydx_session=…' "https://<host>/api/generations/<id>/file?format=pdf"` and watch `docker stats` / `ps -C soffice.bin | wc -l` → 40 concurrent LibreOffice processes.
- **Proposed fix:** route every `toPdf` through the same process-wide semaphore as thumbs (e.g. 2–3 slots, bounded queue with a wait timeout → 503 "PDF navbatda, birozdan keyin urinib ko'ring"); add `limit(pdf:${user.id}, 10, 300)` to the PDF branch; cache the last PDF per `(generation_id, file_version)` (asset row) so repeated views do not reconvert; set `mem_limit` on `web` so a spike cannot take Postgres down.
- **Effort:** S
- **Confidence:** high (code path is direct; per-process RSS is LibreOffice's typical footprint — confirm with the reproduction under `scripts/heavy.sh` limits)

### BEA-02 — Lone UTF-16 surrogates (and NUL) in user text make JSONB/TEXT writes throw → unhandled 500; `.slice()` truncation in client and server creates them from normal emoji text
- **Severity:** P2
- **Location:** client producers: `components/forms/TranslationForm.tsx:93` (`topic: sourceText.trim().slice(0, 48)`), `components/forms/ImageStudio.tsx:72` (`prompt.slice(0, 72)`), `components/forms/ResumeComposer.tsx:572` (`v.slice(0, 400)`); server producers: `lib/server/validate.ts:87` (`value.replace(/\0/g,"").slice(0, limit)`), `lib/generation/slide-limits.ts:117-119` (`clipTo` → `t.slice(0, n - 1)`), `app/api/extract/route.ts:50` (`out.text.slice(0, EXTRACT_MAX_CHARS)` → becomes `sourceText`); JSONB sinks: `lib/server/jobs.ts:187` (`values_json`), `lib/server/jobs.ts:576` (`doc_json` via `updateGenerationDoc`), `lib/server/form-draft.ts:139`, `lib/server/game-sessions.ts:256`; NUL sinks with no stripping: edit ops (`lib/generation/slide-edit.ts:1149-1228` → `doc_json`/`html`), `app/api/o/[token]/submit/route.ts:41` (`player_name` TEXT), `lib/server/source-upload.ts:175-181` (`source_uploads.text` TEXT; TXT sniff only checks the first 64 KB for 0x00, `source-upload.ts:116-117`).
- **Evidence:** `JSON.stringify` (ES2019 well-formed) emits a lone surrogate as the escape `\ud83d`; Postgres `jsonb` input rejects it (`invalid input syntax for type json — Unicode low surrogate must follow a high surrogate`, SQLSTATE 22P02). `\u0000` is rejected by `jsonb` (22P05) and a raw NUL by `text` (22021). None of these are mapped to 4xx — they escape `handler()` as a generic 500 "Ichki xatolik". Only `sanitizeValues` strips NUL, and it then *creates* a lone surrogate itself when `.slice(0, limit)` cuts a pair. Realistic triggers:
  1. Tarjimon text mode: the client sets `topic = sourceText.trim().slice(0,48)`. If code unit 47 is the first half of an emoji/astral character (common in pasted Telegram posts, math italics from PDFs), every "Tarjima qilish" click returns 500 and nothing tells the user why.
  2. Viewer edits: `clipTo` cuts an over-long field at `n-1`; an emoji straddling the cut yields `"…\ud83d…"` → `updateGenerationDoc` throws → 500 → `useDocEdit.save` discards the WHOLE queued batch (`components/files/useDocEdit.ts` catch → `queueRef.current = []`, `reload()`), i.e. the user's unsaved edits are lost.
  3. "Fayl asosida": `/api/extract` truncates at 200 000 code units; the same cut lands in `values_json` → persistent 500 on create.
  4. Any direct/public request with `\u0000` in an edit op value, a game player name (`/api/o/[token]/submit`, unauthenticated) or a >64 KB TXT source with a late NUL → 500.
  5. `buildPreview` (`lib/server/preview.ts:57,88,109,116,132`) cuts the first paragraphs at 160 code units and is written to the `preview` JSONB by `completeJob` (`jobs.ts:432`) and on EVERY `commitDocOps`/`restoreDoc`/`commitPolishedDoc`. A translated Telegram post (emoji-rich) whose first long paragraph has an emoji straddling unit 160 makes the finished job fail in `completeJob` (refund + the raw PG message shown as the job error, see BEA-09); an edited document in that state rejects every subsequent save/rewrite/polish with 500.
- **Reproduction:** `node -e 'const {Pool}=require("pg");new Pool({connectionString:process.env.DATABASE_URL}).query("SELECT $1::jsonb",[JSON.stringify({topic:("a".repeat(47)+"😀").slice(0,48)})]).catch(e=>console.log(e.code,e.message))'` → `22P02 invalid input syntax for type json`. HTTP (user with balance ≥ price, else 402 fires first): `POST /api/generations {"slug":"translation","values":{"language":"en","sourceText":"Salom, bu sinov matni","topic":"\ud83d"}}` → 500 (expected 202). Public: `POST /api/o/<token>/submit {"name":"A\u0000B","answers":{}}` → 500.
- **Proposed fix:** one helper `cleanText(s) = s.toWellFormed().replace(/\u0000/g, "")` (Node ≥20 has `String.prototype.toWellFormed`) applied (a) in `sanitizeValues` AFTER the slice, (b) in `clipTo`/`clipNotes`, `buildPreview`'s `.slice(0,160)` calls and every edit-op string in `parseDocOps`/`parseResumeOps`/`parseArticleOps`/…, (c) in `addResult` for `playerName`, (d) in `putSource` for `text`/`name`. Make client slices code-point safe (`Array.from(s).slice(0,n).join("")`). Optionally map PG codes 22P02/22P05/22021 to 400 in `handler()`.
- **Effort:** S
- **Confidence:** high (Postgres jsonb surrogate/NUL rejection is documented behaviour; the translation `topic` path is deterministic once code unit 47 is a high surrogate)

### BEA-03 — Slide-image and resume-photo uploads write asset bytes BEFORE ownership/status/version checks → orphaned BYTEA rows on every rejected upload (and writes into other users' generations)
- **Severity:** P2
- **Location:** `lib/server/slide-image.ts:72-75`, `lib/server/resume-photo-commit.ts:160-173`, `lib/server/assets.ts:166-189` (`putAssets`/`putAssetBytes` — no `user_id` check), ownership only later in `lib/server/slide-commit.ts:81-83` (`loadDocForEdit`).
- **Evidence:** `const assetId = await putAssetBytes(id, mime, bytes); … return commitDocOps(id, userId, baseVersion, ops);` — the INSERT into `generation_assets` happens first, with the path `id` as `generation_id` and no ownership predicate. `commitDocOps` then throws 404 (foreign/unknown id), 409 (`status` not COMPLETED, stale `baseVersion` — normal with two tabs), 409 `legacy`, or 422 (index out of range / layout without image slot), but the up-to-5 MB row (two rows for the resume photo: cropped + original) is never removed. Generations never expire (`011_no_expiry.sql`), so these rows live forever; nothing references them. For an unknown id the FK violation surfaces as a 500 instead of 404. For another user's generation id the attacker's bytes are attached to the victim's generation (requires knowing the UUID).
  Budget: `imgup:${user.id}` allows 30 uploads/h → up to 150 MB/h/user (300 MB/h via resume photos) of unreferenced BYTEA in the shared Postgres.
- **Reproduction:** two tabs on the same deck; in tab A save an edit (doc_version 0→1); in tab B upload a slide image (`POST /api/generations/<id>/slides/0/image`, form `file=<png>`, `baseVersion=0`) → 409; then `SELECT count(*) FROM generation_assets WHERE generation_id='<id>'` has grown by 1 and the new `asset_id` appears in no `doc_json`. Or `POST …/slides/999/image` (422) repeatedly with different PNGs.
- **Proposed fix:** load and authorize first: call `loadDocForEdit(id, userId)` (and the `baseVersion` compare) before `putAssetBytes`; better, move the asset INSERT into the same transaction as `updateGenerationDoc` (pass the `PoolClient` to `putAssets`), so a 409/422 rolls the bytes back. Make `putAssets` insert via `INSERT … SELECT … FROM generations WHERE id=$1 AND user_id=$2` so it can never write into a foreign generation.
- **Effort:** M
- **Confidence:** high

### BEA-04 — Refunds are a separate, non-retried step after the status change: one DB error (e.g. pool-connect timeout under load) permanently loses the user's refund
- **Severity:** P2
- **Location:** `app/api/generations/[id]/route.ts:62-71` (cancel → refund → delete), `lib/server/worker.ts:296-303` (`failJob` → `refund`), `lib/server/worker.ts:324-334` (`reclaimStaleJobs` → loop of `refund`), `lib/server/credits.ts:176-214` (`refundRatio` opens its own transaction), `lib/server/db.ts:117-139` (`connectionTimeoutMillis: 10_000`).
- **Evidence:** every refund path first COMMITs the terminal status and only then calls `refund()` in a new transaction:
  - DELETE: `cancelGeneration` sets `REVOKED`; if `refund()` then throws, the route returns 500. The user retries DELETE → `cancelGeneration` matches 0 rows (already REVOKED) → `deleteGeneration` (allows `REVOKED`) removes the row → response `{ok:true, refunded:false}`; the charge is never returned.
  - worker failure: `if (await failJob(...)) await refund(...)` — a throw from `refund` is only logged by `tick()`'s `.catch`; the row is `FAILED` and nothing ever looks at it again.
  - stale jobs: `reclaimStaleJobs()` commits `FAILED` for all dead ids, then `for (const id of dead) await refund(...)` inside one `try`; the first throwing refund aborts the loop, and every later id in `dead` is `FAILED` without refund forever (they no longer match `status='IN_PROGRESS'`).
  There is no reconciliation that finds "`FAILED`/`REVOKED` generation with a `charge` row and no `refund` row". At the target load (bursts 10×, pool max `DATABASE_POOL_MAX`, 10 s connect timeout, 30 s statement timeout) `pool.connect()` timeouts in exactly these post-failure paths are plausible — and failures cluster precisely when the system is overloaded (LLM timeouts → mass `failJob` → mass refunds competing for the same pool).
- **Reproduction:** test sketch with the existing test seams: stub `transaction` (or make `refundRatio`'s `SELECT … FOR UPDATE` fail once) and call the DELETE handler for a QUEUED job → 500; call DELETE again → 200 `{refunded:false}`; assert `SELECT count(*) FROM transactions WHERE kind='refund' AND reference=<id>` = 0 while the `charge` row exists. For the worker: make `refund` throw for the first id returned by `reclaimStaleJobs` with 2 dead jobs → the second job is never refunded.
- **Proposed fix:** (1) do status change + refund in ONE transaction: give `refundRatio` an optional `PoolClient` and call it inside the `cancelGeneration`/`failJob`/`reclaimStaleJobs` transaction (`UPDATE … RETURNING` then refund in the same tx); (2) in `housekeeping`, wrap each refund in its own try/catch; (3) add an idempotent sweep in `housekeeping`: `SELECT g.id, g.user_id FROM generations g JOIN transactions c ON c.kind='charge' AND c.reference=g.id::text LEFT JOIN transactions r ON r.kind='refund' AND r.reference=g.id::text WHERE g.status IN ('FAILED','REVOKED') AND r.id IS NULL` → `refund()` (already idempotent via `transactions_ref_idx`); (4) `deleteGeneration` should refuse or refund-first a `REVOKED` row that has no refund.
- **Effort:** M
- **Confidence:** high

### BEA-05 — Payme Merchant API state machine deviates from the protocol: no 12-hour transaction timeout, "order busy" reported as `allow:true`/-31008, paid-order cancel path not guarded
- **Severity:** P2
- **Location:** `app/api/payments/payme/route.ts:93-101` (CheckPerformTransaction), `:103-129` (CreateTransaction), `:131-147` (PerformTransaction), `:149-165` (CancelTransaction), `:75-77` (auth error before body parse); `lib/server/payments.ts:313-325` (`cancelOrder` — no state predicate); no tests of the RPC state machine (`tests/payments.test.mts` covers only signature/auth/tiyin).
- **Evidence:** compared with the Payme Merchant API contract:
  1. **Timeout (12 h = 43 200 000 ms) is not implemented anywhere** (`grep 43200000` → nothing). The spec requires CreateTransaction to reject `params.time` older than 12 h with -31008, and Create (repeat) / PerformTransaction on a state-1 transaction older than 12 h to cancel it with `reason: 4` and return -31008. Today a stale pending transaction can still be performed and credited.
  2. **Order that already has a pending transaction:** CheckPerformTransaction returns `{allow:true}` for `state='pending'` **and** `state='cancelled'` orders (only `paid` is rejected); CreateTransaction with a new `params.id` then fails with -31008 (`order.state !== "created"`). The protocol expects an account error (-31050…-31099, `data:"order_id"`) at CheckPerform/Create for a single-payment order that is busy/closed; the -31050 reply here never carries `data`.
  3. `cancelOrder` updates `WHERE id = $1` with no `state` guard, and `settleOrder` credits in one transaction then marks `paid` in a separate statement (`payments.ts:286-309`). A Perform/Cancel interleaving (or a Click `Complete` with `error<0` arriving for an already-paid order, `click/route.ts:131-133`) can leave the order `cancelled` while the credit stays — Payme then refunds the customer.
  4. Auth failure replies `id: null` because the body is not parsed yet (`route.ts:75-77`); `ChangePassword` is unimplemented (-32601).
  5. Click `Complete` for an already-paid order returns `error: 0` (re-runs `settleOrder`) where the Click SHOP-API table specifies `-4 Already paid` (`click/route.ts:135-141`).
  6. Neither webhook checks `order.provider`: `findOrder(merchant_trans_id)` / `findOrder(account.order_id)` accept an order created for the other provider. A Payme order paid through a hand-built Click URL is credited and then appears in Payme `GetStatement` (`WHERE provider='payme' AND provider_txn IS NOT NULL`) with a Click transaction id; a Click order attached by Payme `CreateTransaction` can never be performed (`findOrderByTxn("payme", …)` filters by provider → -31003) and is then stuck `pending` for Click ("Buyurtma band"). Reconciliation with both providers breaks.
  Payme/Click run sandbox acceptance tests on exactly these branches before enabling a merchant, so the integration is likely to be rejected or to misbehave on the first stuck/abandoned checkout.
- **Reproduction:** with `PAYME_TEST_KEY` set, POST JSON-RPC sequences to `/api/payments/payme` (Basic `Paycom:<key>`): (a) `CreateTransaction {id:"t1", time: Date.now()-13*3600e3, amount, account:{order_id}}` → returns `state:1` (expected -31008); (b) `CreateTransaction t1` then `CheckPerformTransaction` for the same order → `{allow:true}` (expected -31050…-31099); (c) `CreateTransaction t2` for the same order → -31008 (expected account error "order is awaiting payment"); (d) `CreateTransaction t1`, wait/patch `create_time` 13 h back, `PerformTransaction t1` → credited (expected cancel reason 4 + -31008).
- **Proposed fix:** add `PAYME_TIMEOUT_MS = 43_200_000` and implement the documented branches in CreateTransaction/PerformTransaction (cancel with reason 4 via a guarded `cancelOrder`); return -31050 with `data:"order_id"` for `pending`/`cancelled`/`paid` orders in CheckPerform and for Create on a busy order; make `cancelOrder` `… WHERE id=$1 AND state IN ('created','pending')` and do the `paid` UPDATE inside the same transaction as `topUp`/`activatePro`; parse `id` before auth; return -4 for duplicate Click Complete; reject orders whose `provider` differs from the webhook (Click -5 / Payme -31050). Add an RPC state-machine test that replays the Payme sandbox scenarios.
- **Effort:** M
- **Confidence:** medium — the 12 h timeout and "busy order" rules are from the public Payme Merchant API docs; confirm by running the Payme sandbox (test.paycom.uz) against a staging URL.
