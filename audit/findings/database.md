### DB-01 — Every generated file and image is kept forever as `bytea` in the one Postgres on a shared VPS disk; images are stored twice; the only backup is a manual plain `pg_dump` to the same disk
- **Severity:** P1
- **Location:** `lib/server/migrations/011_no_expiry.sql:6-13` (expiry removed; "HECH QANDAY so'rov ular bo'yicha tozalamaydi"); `lib/server/migrations/001_init.sql:102-112` (`generation_files.bytes BYTEA`); `lib/server/migrations/002_assets.sql:8-17` (`generation_assets.bytes BYTEA`); `lib/server/storage.ts:17` (`MAX_FILE_BYTES = 25 MB`); `lib/server/worker.ts:249-256` (the file is saved, then every `data:` image is saved again as an asset); `lib/server/assets.ts:48-176`; `lib/server/thumb.ts:115` (a thumbnail is a third copy); `lib/server/worker.ts:335-362` (housekeeping purges only sessions, game links, rate limits, tickets, sources, photos); `docker-compose.yml:2-18` (one `pgdata` volume, stock `postgres:16-alpine` config); `.claude/deploy.md:39-47` (backup = `pg_dump ... > /root/slaydx-backups/slaydx-$ts.sql`).
- **Evidence:** `011_no_expiry.sql` stops all expiry: "barcha yaratilgan hujjatlar endi MUDDATSIZ saqlanadi". `enqueueGeneration` no longer sets `expires_at` (`jobs.ts:172-176`). No code deletes `generation_files` or `generation_assets` rows except a user's own delete. For slide decks the images are kept twice: once inside the PPTX in `generation_files`, and again as `generation_assets` rows made by `extractAssets` (`worker.ts:249-256`). The project's own measurements: a pro deck is "1K JPEG ≈ 0.9 MB × 21 rasm ≈ 19 MB" (`docs/AUDIT-9.md:119`), so about 38 MB of `bytea` per pro deck. An ordinary deck with stock photos is 5–8 MB (`docs/AUDIT-10.md` table), which doubles with the assets. Production dumps are already 332 MB (2026-09-10) to 377 MB (2026-09-17) with almost no users (`docs/AUDIT-15.md:58`, `docs/AUDIT-22.md:850`).
  **Scale:** assume 50 000 users, 20 % of them active each month, 5 decks each, about 10 MB per deck including the asset copies. That is about 500 GB of new `bytea` per month, and none of it is ever deleted. A shared VPS disk (typically 200–400 GB, also used by the two other projects' databases) fills within weeks to a few months. When the disk is full, Postgres cannot write WAL. Every write fails (enqueue, charge, session). The other projects on the box are hit too.
  **Backups get worse as the data grows.** Plain-format `pg_dump` writes `bytea` as hex, which is 2× the raw size. It is uncompressed and goes to the same disk (`/root/slaydx-backups`), and a new dump is added on every deploy. At 100 GB of data, one dump is about 200 GB. It needs hours of I/O, and taking it can itself fill the disk. There is no schedule, no off-box copy and no WAL archiving or PITR. A lost disk means every file and the whole credit ledger are gone. The default `shared_buffers=128MB` also means that serving large TOAST values pushes the hot queue and session pages out of cache.
- **Reproduction:** on a prod-like copy: `SELECT pg_size_pretty(pg_total_relation_size('generation_files')) files, pg_size_pretty(pg_total_relation_size('generation_assets')) assets, pg_size_pretty(pg_database_size(current_database())) db;` then `SELECT date_trunc('day', created_at) d, pg_size_pretty(sum(size_bytes)) FROM generation_files GROUP BY 1 ORDER BY 1 DESC LIMIT 14;` to get the daily growth. Compare it with `df -h /var/lib/docker`. For the backup, run `time pg_dump -U slaydx slaydx | wc -c` against `pg_database_size`. The ratio is about 2× for `bytea`-heavy data.
- **Proposed fix:** (1) Move file, asset and upload bytes out of Postgres into object storage (an S3-compatible bucket, or at least a separate volume). Keep only the key, size and mime in the tables. Serve files by a signed or streamed URL. (2) Keep images once. The PPTX/DOCX can be re-rendered from `doc_json` + assets (`rebuildFile` already does this), so either drop the stored file bytes after N days and rebuild on demand, or drop the asset copy. (3) Add a retention policy, for example remove the bytes of files not opened for 180 days while keeping the row. (4) Backups: a nightly `pg_dump -Fc` (compressed) or pgBackRest/WAL-G, copied off the box, with a restore test. Add disk-usage alerting.
- **Effort:** L
- **Confidence:** high. The growth path and the missing retention are certain. The monthly volume is an estimate from the project's own size measurements. Confirm it with the two queries above on production.
- **Cross-ref:** FILE-01 (files never purged) and INFRA-05 (backups) cover parts of this. This finding adds three points: the images are stored twice, a plain `pg_dump` of `bytea` is 2× the size, and there is shared-VPS disk-full coupling.

### DB-02 — Upload tables have no per-user quota: one free account can write about 5 GB/hour of `bytea`, and logos and templates are never deleted
- **Severity:** P1
- **Location:** `app/api/uploads/source/route.ts:25-28` (20 uploads per 10 min) + `lib/server/source-upload.ts:44,170-183` (20 MB each, one new row per distinct content hash); `app/api/uploads/template/route.ts:18-22` (5 per 10 min) + `lib/server/template-upload.ts:38,136-138` (20 MB, never purged); `app/api/uploads/photo/route.ts:18` (20 per 5 min) + `lib/server/photo.ts:22,158-166` (5 MB crop + 5 MB original per upload, purged only after 90 days); `app/api/uploads/logo/route.ts:18` (10 per 5 min) + `lib/server/logo.ts:17,28-38` (2 MB, never purged); `lib/server/ratelimit.ts:45-48` (the limiter fails open on DB errors).
- **Evidence:** every upload table has `PRIMARY KEY (user_id, asset_id)`, where `asset_id` is the SHA-256 of the bytes (`012`, `016`, `017`, `019`). A user can therefore store any number of rows by changing one byte. No code counts rows or bytes per user. The only brake is the per-user rate limit. Maximum sustained write rate for one ordinary account (free signup, no plan check on any upload route): sources 20×20 MB per 10 min = 2.4 GB/h; photos 20×10 MB per 5 min = 2.4 GB/h; templates 5×20 MB per 10 min = 0.6 GB/h; logos 10×2 MB per 5 min = 0.24 GB/h. That is about **5.6 GB/hour per account**. The data is already compressed (zip, JPEG, PNG), so TOAST cannot shrink it. Templates and logos are kept forever, sources for 30 days and photos for 90 days. A handful of Telegram accounts can fill the shared VPS disk in hours, with the same outage as DB-01 (Postgres stops accepting writes and the co-hosted projects are hit too). If the DB is under stress, `rateLimit` returns `ok: true` (`ratelimit.ts:45-48`), which removes the only brake.
- **Reproduction:** a plain TXT file does not work here, because more than 200 000 characters is rejected. A DOCX with a large media part and a few hundred characters of text passes (`chars` counts only translatable text). Build 20 unique files: `python3 -c "import zipfile,os
for i in range(20):
  z=zipfile.ZipFile(f's{i}.docx','w',zipfile.ZIP_STORED); z.writestr('word/document.xml','<w:document xmlns:w=\"http://schemas.openxmlformats.org/wordprocessingml/2006/main\"><w:body><w:p><w:r><w:t>Salom '+str(i)+' '+'matn '*60+'</w:t></w:r></w:p></w:body></w:document>'); z.writestr('word/media/pad.bin',os.urandom(19_500_000)); z.close()"`. Then upload them against a local instance: `for i in $(seq 0 19); do curl -s -b "slaydx_session=$TOK" -F "file=@s$i.docx" http://127.0.0.1:3000/api/uploads/source; done`. Every call returns 200 with a new `assetId`, and each one adds an about 19.5 MB row. Check with `SELECT count(*), pg_size_pretty(sum(size_bytes)) FROM source_uploads WHERE user_id=$1;`. Repeat every 10 minutes (and the same for templates, photos and logos). Nothing stops the growth.
- **Proposed fix:** in each `put*` function, inside the insert transaction, enforce a per-user cap. Either keep the newest K rows (`DELETE FROM logo_uploads WHERE user_id=$1 AND asset_id NOT IN (SELECT asset_id FROM logo_uploads WHERE user_id=$1 ORDER BY created_at DESC LIMIT 5)`, and the same for templates with K≈10, photos K≈10, sources K≈20), or reject with 413 when `sum(size_bytes)` for the user is over a per-user budget (e.g. 200 MB). Add a purge for templates and logos not used for 180 days. Make `rateLimit` fail closed for upload buckets.
- **Effort:** S
- **Confidence:** high (limits and rate limits read from code; the arithmetic follows directly).

### DB-03 — List and poll queries read `values_json` (up to about 1 MB per row), then throw it away, and the list is polled every 3 s while any job is queued
- **Severity:** P2
- **Location:** `lib/server/jobs.ts:72-76` (`ROW_COLUMNS` contains `values_json`); `jobs.ts:196-205` (`listGenerations`, LIMIT 100, up to 300); `jobs.ts:213-232` (`getGeneration`, the poll endpoint); `jobs.ts:110-136` (`rowToSummary` never reads `values_json`); `lib/api-client.ts:248` (the client type omits `values`); `lib/server/validate.ts:17,33,31,62,85` (80 keys × 4 000 chars, `sourceText` 200 000 chars, JSON fields 24 000 each); `app/api/generations/route.ts:42,79` (1.2 MB bodies accepted; in text mode `sourceText` stays in `values`); `components/home/HomeFiles.tsx:37-44` (list re-fetched every 3 s while any generation is QUEUED or IN_PROGRESS); `lib/api-client.ts:366-405` + `:299-302` (item poll every 1–5 s, 1.2 s while live).
- **Evidence:** `SELECT ${ROW_COLUMNS} FROM generations WHERE user_id = $1 ORDER BY created_at DESC LIMIT $2` detoasts every row's `values_json`. node-pg then `JSON.parse`s it, and `rowToSummary` drops it. It never reaches the response. For most tools the value is 1–30 KB (resume and article JSON fields go up to 24 000 chars each). For any text-mode source (translation text mode, "Fayl asosida" text) it holds the pasted text, up to 200 000 chars (about 400 KB of JSONB for Cyrillic), and it stays on the row forever. The poll endpoint pays the same cost on every tick.
  **Mechanism under load:** the worker runs 2 jobs at a time, so a 10× burst builds a queue that takes tens of minutes to drain. During that time every waiting user's browser polls `GET /api/generations` every 3 s and `GET /api/generations/{id}` every 1–5 s. Example: 500 waiting users × 100-row lists × a modest 3 KB unused `values_json` is about 50 MB/s of detoast + JSON parse that is thrown away. Users with text-mode rows in their history multiply this by 10–100×. It all lands on the single Node web process's event loop (JSON.parse is synchronous), so latency rises for every request, including payment webhooks.
- **Reproduction:** as a test user, create 20 translation jobs in text mode with a 150 000-char `sourceText`. Then run `EXPLAIN (ANALYZE, BUFFERS) SELECT <ROW_COLUMNS> FROM generations WHERE user_id=$1 ORDER BY created_at DESC LIMIT 100;`. Compare the buffers and time with the same query without `values_json`. In Node, time `listGenerations(userId)`: the response JSON is a few KB, while `pg` parses several MB per call.
- **Proposed fix:** split the column list. `SUMMARY_COLUMNS` = `ROW_COLUMNS` minus `values_json`, used by `listGenerations`, `getGeneration` and `rowToSummary` callers. Read `values_json` only in `claimJob` (it already does). Optionally make the list poll cheaper too: poll only the ids that are running (`WHERE user_id=$1 AND status IN ('QUEUED','IN_PROGRESS')`), and use the existing `(user_id, created_at DESC)` index with LIMIT 30 plus pagination for the full list.
- **Effort:** S
- **Confidence:** high that the column is read and discarded. The throughput figure is an estimate: confirm with the EXPLAIN above on a production-sized history.
- **Cross-ref:** same root cause as SCALE-03 and FE-07. Merge them.

### DB-04 — A refund is not in the same transaction as the FAILED/REVOKED status change, so any error or exit in between loses the user's credits for good
- **Severity:** P2
- **Location:** `lib/server/worker.ts:162-168` (unknown tool: `failJob` then `refund`); `worker.ts:296-303` (failure path: `failJob` commits, then `refund`; if `refund` throws inside the `catch`, the error escapes to `runJob(...).catch(console.error)` at `worker.ts:316-320` and is never retried); `worker.ts:324-334` (`reclaimStaleJobs` commits `FAILED` in its own transaction, then a loop does `SELECT user_id` + `refund` per id; one throw ends the loop and skips all later housekeeping); `worker.ts:409-413` (SIGTERM → `process.exit(0)` after 2 s, even in the middle of the loop); `app/api/generations/[id]/route.ts:62-67` (`cancelGeneration` commits `REVOKED`, then `refund`); `lib/server/credits.ts:176-214`.
- **Evidence:** each of these paths commits the terminal status first and calls `refund()` afterwards, in a separate pooled transaction. Nothing ever reconciles: no code looks for FAILED/REVOKED generations that have a `charge` transaction but no `refund`. A pool acquire timeout (`connectionTimeoutMillis: 10_000`, `db.ts:31`), a statement timeout, a Postgres restart or the worker exit between the two steps therefore loses the refund permanently. The user-cancel path is the worst. If `refund` throws, the client gets a 500. When the user retries DELETE, `cancelGeneration` returns false (the row is already REVOKED), `deleteGeneration` deletes the row (`jobs.ts:234-243`), and the response is `{ok:true, refunded:false}`. The charge stays and the evidence is gone. Amounts range from 2 000 to 60 000 tanga per job. Refunds are idempotent (`transactions_ref_idx`), so a later retry would be safe. There is just no retry.
- **Reproduction:** node:test sketch with a real test DB. (1) Enqueue a job for a user (balance drops by the price). (2) Monkey-patch `credits.refund` to throw once, as a DB timeout would. (3) Call the DELETE handler: it returns 500. (4) Restore `refund` and call DELETE again: 200 `refunded:false`. (5) Assert `SELECT count(*) FROM transactions WHERE kind='refund' AND reference=$id` = 0 while the charge row exists. This fails today. The same test with `failJob` + throwing `refund` covers the worker path. A detector for production: `SELECT g.id, g.user_id, g.price FROM generations g WHERE g.status IN ('FAILED','REVOKED') AND EXISTS (SELECT 1 FROM transactions c WHERE c.kind='charge' AND c.reference=g.id::text) AND NOT EXISTS (SELECT 1 FROM transactions r WHERE r.kind='refund' AND r.reference=g.id::text);`
- **Proposed fix:** make the status change and the refund one transaction. Add `refundInTx(client, ...)` (the body of `refundRatio`). Then `failJob`, `cancelGeneration` and the dead branch of `reclaimStaleJobs` each do `UPDATE ... RETURNING user_id` and `refundInTx` inside the same `transaction()`. As a safety net, add a housekeeping step that runs the detector query above and refunds the rows it finds; this is idempotent thanks to the unique `(kind, reference)` index.
- **Effort:** S
- **Confidence:** high (sequence read from code; the failure needs an error between two statements, which is rare, but the loss is permanent).
- **Cross-ref:** same root cause as BEA-04, CONC-05 and OBS-05. Merge them.

### DB-05 — A worker restart (every deploy) leaves its jobs "IN_PROGRESS" with a fresh heartbeat; they are only requeued after the whole job budget (up to about 11.5 min) and each restart uses up one of the 2 attempts
- **Severity:** P2
- **Location:** `lib/server/worker.ts:408-416` (`shutdown`: `stopWorker()` + `setTimeout(process.exit, 2000)`; running jobs are neither released nor failed); `worker.ts:104-116` (heartbeat every 2 s keeps `locked_at` fresh until the process dies); `lib/server/jobs.ts:481-521` (`reclaimStaleJobs` treats a job as dead only after `budget_ms/1000 + 30 s`); `jobs.ts:356` (`attempts = attempts + 1` at claim); `lib/server/env.ts:91` (`DEFAULT_JOB_TIMEOUT_MS = 660_000`); `.claude/deploy.md:61-62` (every deploy runs `docker compose ... up -d`, which recreates the worker).
- **Evidence:** "the worker is dead" and "the job is too slow" are measured with the same clock, `locked_at` against the job budget. A dead worker's last heartbeat is less than 2 s old, so its jobs look healthy for the job's full budget plus 30 s. Only then are they requeued (`attempts < 2`) or failed with "Ish vaqti tugadi" (`attempts >= 2`). The result: on every deploy, crash or OOM kill, each in-flight job shows a frozen progress bar for up to about 11.5 minutes, then starts again from zero, so the LLM and image spend is paid twice. A job that lives through two restarts (two deploys close together, or a worker that keeps crashing) fails even though nothing was wrong with it. With WORKER_CONCURRENCY=2 and a queue always present at the target load, every deploy hits some users.
- **Reproduction:** start the worker, enqueue a slide job, wait until `status='IN_PROGRESS'`, then `docker compose -p slaydx restart worker`. `SELECT status, locked_at, attempts, budget_ms FROM generations WHERE id=$1` stays `IN_PROGRESS` and is only requeued at about `locked_at + budget_ms/1000 + 30 s` (log line «Qayta navbatga qo'yildi»). Restart again during the second run: the job becomes `FAILED 'Ish vaqti tugadi'`.
- **Proposed fix:** (1) On SIGTERM, stop claiming, give jobs a short grace period, then release them: `UPDATE generations SET status='QUEUED', locked_by=NULL, locked_at=NULL, run_after=now(), attempts=GREATEST(attempts-1,0), live_json=NULL WHERE locked_by=$WORKER_ID AND status='IN_PROGRESS'`. Set compose `stop_grace_period` to match. (2) Separate the two checks. Stale = `locked_at < now() - interval '30 seconds'`, since the heartbeat runs every 2 s. Too slow = `started_at + budget_ms` exceeded. Then a crashed worker's jobs return to the queue within about 30 s.
- **Effort:** S
- **Confidence:** high
- **Cross-ref:** same root cause as CONC-03 and INFRA-02. Merge them. The DB-side part is the stale test: `locked_at` compared against the budget.

### DB-06 — Files and assets are read whole from `bytea` into the web process as hex text, using about 5× the file size in memory per request, with no streaming and no Range support
- **Severity:** P2
- **Location:** `lib/server/storage.ts:69-86` (`getGenerationFile` selects `f.bytes`); `app/api/generations/[id]/file/route.ts:52,115` (`new Uint8Array(file.bytes)`, a full copy); `lib/server/assets.ts:225-238` + `app/api/generations/[id]/assets/[assetId]/route.ts` (every slide image, full size); `app/api/o/[token]/audio/[assetId]/route.ts` (public audio, `Accept-Ranges` not honoured); `lib/server/thumb.ts:108-114`; `node_modules/postgres-bytea/index.js:6-9` (`Buffer.from(input.substr(2), 'hex')`); `docker-compose.yml:20-98` (no `mem_limit` on web).
- **Evidence:** node-pg uses the text protocol, so a `bytea` arrives as a hex `\x…` string twice the file's size. The whole DataRow is buffered, decoded into a JS string, hex-decoded into a Buffer, and the route then copies it into a new `Uint8Array`. For a 25 MB file (`MAX_FILE_BYTES`) that is about 50 + 50 + 25 + 25 MB, roughly 150 MB of short-lived memory, plus about 50–100 ms of synchronous hex decoding on the event loop. A pro deck (about 19 MB, `docs/AUDIT-9.md:119`) costs about 100 MB per download. The audio route advertises `Accept-Ranges: bytes` but ignores `Range`, so each seek in the `<audio>` element reads the whole file from Postgres again. Opening a pro deck in the viewer triggers 21 image requests of about 0.9 MB each, and the "Mening fayllarim" grid of up to 100 cards loads each slide card's full-size first image from Postgres, because there is no small card variant.
  **Scale:** about 40 concurrent downloads of 19–25 MB files (a plausible exam-night burst at 2 000 active users × 10) is about 4–6 GB of transient memory in one Node process. The web container has no memory limit, so the host OOM killer decides which process dies, and that can be Postgres or one of the two co-hosted projects. Meanwhile each such read evicts `shared_buffers` (128 MB by default) and holds one of the 10 pool connections for its whole transfer.
- **Reproduction:** seed one 20 MB `generation_files` row, then `autocannon -c 40 -d 20 -H "Cookie: slaydx_session=$TOK" http://127.0.0.1:3000/api/generations/$ID/file` while watching `docker stats slaydx-web-1`. RSS climbs by several GB and p99 latency of `/api/health` rises (run it through `scripts/heavy.sh` on a throwaway stack only).
- **Proposed fix:** long term, keep bytes outside Postgres and stream them (DB-01). Short term: (a) read `bytea` in binary format (`pool.query({ text, values, binary: true })`) or in chunks with `substring(bytes FROM $off FOR $len)` and stream a `ReadableStream`; chunked reads also make HTTP Range possible for audio. (b) Drop the extra copy: `new Response(file.bytes)`, since a Buffer is already a Uint8Array. (c) Add a small in-process semaphore, for example 8 concurrent file reads. (d) Store a small card-sized JPEG for slide cards instead of serving the full image.
- **Effort:** M
- **Confidence:** high on the mechanism (node-pg code read); medium on the exact concurrency that triggers OOM, which depends on host RAM. Confirm with the autocannon run.
- **Cross-ref:** SCALE-01 (a global `no-store` header) makes this worse: every page view re-reads every image through this path.

### DB-07 — Migration runner: every file in one transaction with the pool's 30 s `statement_timeout` and no `lock_timeout`, so any migration on a large table either blocks all `generations` traffic or fails the deploy, and a failed migration leaves the web as a 500-zombie
- **Severity:** P2
- **Location:** `lib/server/db.ts:27-44` (every pooled connection: `statement_timeout: 30_000`, no `lock_timeout`); `db.ts:102-136` (`migrate`: `pg_advisory_lock` on a pooled client, then `BEGIN; <whole file>; INSERT schema_migrations; COMMIT` per file); `db.ts:138-148` (`ensureMigrated` retried on every request after a failure); `instrumentation.ts:28-35` (in prod a migration error is re-thrown from `register()`); `scripts/worker.ts:12-15` (worker `exit(1)` → Docker restart loop); `lib/server/migrations/018_slide_visual_pin.sql:9-22` (an example of a full-table `doc_json` rewrite inside one migration); `.claude/deploy.md:103-114` (no down-migrations; rollback = restore the dump).
- **Evidence:** (1) Wrapping each file in `BEGIN…COMMIT` makes `CREATE INDEX CONCURRENTLY` impossible. Every new index on `generations`, `transactions` or `generation_assets` (including the ones this audit recommends) takes a SHARE lock and blocks enqueue, heartbeats and `completeJob` for as long as the build runs. (2) The migration connection comes from `pool()`, so it inherits `statement_timeout = 30 s`. A backfill like 018 (rewriting `doc_json` for every deck) or an index build on a table of millions of rows goes over 30 s at the target data size, is cancelled and rolls back. The deploy then cannot finish. (3) There is no `lock_timeout`. An `ALTER TABLE generations …` waits for ACCESS EXCLUSIVE behind any running reader, such as a list query, a 25 MB file read that joins `generations`, or a `pg_dump` (its ACCESS SHARE lasts the whole dump, DB-01). While it waits, it blocks **every** later query on `generations` in the lock queue for up to 30 s. That covers polls, lists, enqueues and worker heartbeats. (4) On failure the web's `register()` throws in prod, and the process keeps running and serves 500 to everything, the same zombie state as INFRA-01. The worker exits and Docker restarts it, re-running the failing migration every few seconds. The advisory-lock wait also counts against the 30 s timeout, so a second process that boots while the first is still migrating fails too.
- **Reproduction:** on a scratch DB with a large `generations` table (e.g. `INSERT … SELECT generate_series(1,3e6)` of synthetic rows), add `lib/server/migrations/022_test.sql` with `CREATE INDEX generations_status_idx ON generations(status);` and start the worker. It logs `Migratsiya xatosi (022_test.sql): canceling statement due to statement timeout` and restarts forever. For the lock-queue effect: in psql, `BEGIN; SELECT count(*) FROM generations;` (keep it open), then deploy a migration with `ALTER TABLE generations ADD COLUMN x int;`. From a third session, `SELECT 1 FROM generations WHERE id = '<uuid>'` hangs until the ALTER times out at 30 s.
- **Proposed fix:** in `migrate()`, on the migration client run `SET statement_timeout = 0; SET lock_timeout = '5s';` (retry the file with backoff on a lock timeout). Support a per-file opt-out of the wrapping transaction, for example a first-line marker `-- no-transaction`, so that `CREATE INDEX CONCURRENTLY` can be used. Run migrations as a separate one-shot step (`npm run db:migrate`, already present in `scripts/migrate.ts`) before `up -d` instead of lazily inside the web and worker. Make `register()` call `process.exit(1)` on failure (see INFRA-01). Write large backfills as batched, resumable jobs, not as migrations.
- **Effort:** S
- **Confidence:** high (behaviour follows from the pool config and PostgreSQL lock semantics). No migration in the repo is dangerous today. The risk is the next one that touches a large table.

### DB-08 — DB capacity config is fixed and stock: the web pool is 10 connections (compose does not forward `DATABASE_POOL_MAX`), Postgres runs with default memory settings and no slow-query visibility, and saturation turns into 10 s waits followed by 500s, with rate limiting failing open
- **Severity:** P2

### DB-09 — Payment order state changes are check-then-act under READ COMMITTED with no row lock; the credit and the `state='paid'` update are separate transactions, and `cancelOrder` has no state predicate
- **Severity:** P2
- **Location:** `lib/server/payments.ts:276-311` (`settleOrder`: `findOrder` with no lock, then `activatePro`/`topUp` in their own transaction, then a separate `UPDATE … SET state='paid' … WHERE state <> 'cancelled'`); `payments.ts:313-325` (`cancelOrder`: `UPDATE payment_orders SET state='cancelled' … WHERE id = $1`, whatever the current state); `lib/server/credits.ts:254-272` (`activatePro`: quota credited in one transaction, `plan`/`plan_expires_at` in another, and skipped entirely when the credit already exists); `app/api/payments/payme/route.ts:131-165`; `app/api/payments/click/route.ts:129-137`.
- **Evidence:** in the Payme handlers, `PerformTransaction` and `CancelTransaction` both read the order without `FOR UPDATE`. Interleaving: Perform reads `pending`, Cancel reads `pending`, Perform's `topUp` commits the credit, Cancel's unguarded `UPDATE` sets `cancelled`, and Perform's `UPDATE … WHERE state <> 'cancelled'` matches 0 rows. `settleOrder` still returns `ok:true`, so Perform answers `state:2` while the order row says cancelled. The user keeps the credit and the payer is refunded by Payme. The Click `Complete` with `error<0` path likewise cancels an order that is already `paid`, because only `cancelled` is checked (`click/route.ts:101,131-133`). For Pro, a crash between `topUp` and the plan `UPDATE` leaves the quota granted but `plan='free'` forever, because on retry `topUp` returns `false` and `activatePro` returns before updating the plan. Double credit is not possible: `transactions_ref_idx` blocks a second `topup`/`subscription` row, and a concurrent duplicate fails with a unique violation. So the realistic loss is credit kept on a cancelled order. It needs Payme to send Cancel while our Perform is still running, which is most likely exactly when the server is slow under load.
- **Reproduction:** node:test against a test DB. Create an order and `attachTransaction`. Run `Promise.all([settleOrder(id, Date.now()), cancelOrder(id, Date.now(), 4)])` with a hook that delays after `topUp` (or repeat 1 000 times). Assert that there is never a row with `state='cancelled'` together with a `transactions` row `kind='topup' AND reference='payme:<txn>'`. It fails intermittently today.
- **Proposed fix:** do everything in one transaction keyed by the order. `settleOrder` = `transaction(c => { SELECT … FROM payment_orders WHERE id=$1 FOR UPDATE; if state in ('cancelled') return; if state='paid' return idempotent; topUpInTx(c,…); UPDATE … SET state='paid' })`. `cancelOrder` = the same lock plus `WHERE id=$1 AND state IN ('created','pending')`, returning a distinct error when the order is already paid. `activatePro` should run the plan `UPDATE` inside the same transaction as the credit (or apply it idempotently even when the credit already exists).
- **Effort:** S
- **Confidence:** medium. The code path is certain. How often it happens depends on Payme retry and cancel timing.
- **Cross-ref:** CONC-02 and BEA-05 cover the same area. Merge them.

## Checked and OK
- **Enqueue is atomic and cannot overspend:** the charge and the `INSERT generations` run in one transaction (`lib/server/jobs.ts:159-193`), and the wallet row is locked `FOR UPDATE` before the balance check (`lib/server/credits.ts:38-46,99-116`). Concurrent enqueues by one user serialize on that row. `CHECK (points/quota/balance >= 0)` (`001_init.sql:13-15`) is the backstop.
- **Ledger idempotency is enforced by the DB, not only by code:** `UNIQUE (kind, reference) WHERE reference IS NOT NULL` (`001_init.sql:130-131`). If `refundRatio`/`topUp` race past their pre-check (`credits.ts:176-251`), the second INSERT fails with a unique violation and rolls back its wallet UPDATE. There is no double credit or double refund. Partial and full refunds share one key, so a job is refunded at most once. The charge `reference` is not an FK, so ledger rows survive a generation delete.
- **Queue claim:** `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED)` (`jobs.ts:351-367`) never double-claims. A user cancel and a claim resolve correctly: cancel requires `status='QUEUED'` (`jobs.ts:246-255`), and the claim skips locked rows. `completeJob`/`failJob`/`setProgress`/`setLive`/`setCost`/`heartbeat` are fenced by `locked_by = $worker AND status = 'IN_PROGRESS'` (`jobs.ts:263-322,405-473`). Two workers running `reclaimStaleJobs` at once are safe (row locks + READ COMMITTED re-check), and the refunds are idempotent.
- **Hot lookups are indexed:** session by `token_hash` UNIQUE (`001:41`) joined to the `users` PK (`session.ts:219-227`); `last_seen_at` is written at most once an hour and is not indexed, so the write is HOT (`session.ts:230-234`); generation by PK + `user_id` (`jobs.ts:221-227`); user list by `generations_user_idx(user_id, created_at DESC)` + LIMIT (`001:93`, `jobs.ts:196-205`); queue by the partial `generations_queue_idx` and reclaim by the partial `generations_stale_idx` (`001:95-98`); rate limits by PK (`001:159`); transactions by `(user_id, created_at DESC)` (`001:127`); payment orders by `(provider, provider_txn)` and `prepare_id` (`001:151`, `005:22`); game link by `token` UNIQUE (`021:50`), results by `(session_id, created_at DESC)` (`021:77`); every upload table by its `(user_id, asset_id)` PK; drafts by PK.

Deleting a generation cascades through indexed paths.
- **No transaction holds a connection across network, LLM or render work:** `rebuildFile` renders before the transaction (`slide-commit.ts:233-259`), `commitDocOps`/`restoreDoc` render before theirs (`slide-commit.ts:141-151,184-187`), polish runs the LLM before `commitPolishedDoc` (`doc-polish.ts:422-457`), and the payment and auth transactions contain only SQL. `idle_in_transaction_session_timeout: 60 s` and `statement_timeout: 30 s` are set on every connection (`db.ts:34-37`), and the `pool.on('error')` handler exists (`db.ts:46-48`).
- **Connection count:** web 10 + worker 10 (+10 for an ad-hoc `docker exec … tsx` script) stays far below `max_connections=100`, and the `globalThis` pool singleton prevents HMR leaks (`db.ts:15-51`).
- **Concurrent boot of web and worker** is safe: a session advisory lock, then `schema_migrations` is re-read after the lock is acquired, and each file commits atomically with its `schema_migrations` row (`db.ts:102-136`). The existing migrations are idempotent (`IF NOT EXISTS`, guarded UPDATEs).
- **Account uniqueness is enforced in the DB:** `users.telegram_id` UNIQUE, the partial unique on `local_id`/`phone` (`001:6`, `006:20`, `008:12`). Concurrent first logins (`auth.ts:108-137,220-240`) end in one unique-violation 500, never in duplicate accounts or a duplicate signup bonus (`signup:<id>` reference).

Heavy columns (`doc_json`, `html`, `doc_prev`, `live_json`) are not in list queries (`jobs.ts:72-76`). `live_json` is returned only while IN_PROGRESS and only when `live_seq > since` (`jobs.ts:222-231`).
