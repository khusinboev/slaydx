### DEPS-01 — Production server IP, root-SSH access pattern, other tenants' infra layout, and owner's real phone number committed and live on the public GitHub repo
- **Severity:** P0
- **Location:** `.claude/deploy.md` (currently tracked, present at `origin/main` HEAD `76ddf91e992b4b48b8855df7e4ae4d318ef76f6d`, 2026-09-22; added in commit `50ba83d793392b269b24fe49b91f90555a4e3eb7`, 2026-09-11). Also tracked (checked, contents benign): `.claude/structure.md`, `.claude/holat.md`, `.claude/actions/2026-09-11-03-pause.md`, `.claude/actions/2026-09-11-04-resume.md`.
- **Evidence:** `.gitignore` has `/CLAUDE.md` and `/.claude/` (added later, commit history shows the ignore rule postdates the file additions), but `.claude/deploy.md` was `git add`-ed before/despite that rule and is **currently** in `git ls-files` and in `origin/main`'s tree — i.e. it is live on `github.com/khusinboev/slaydx` right now, not just a historical leak. Contents include:
  - Production host IP and the fact root-SSH is the deploy access method (`ssh root@<IP>`), real production domain, exact deploy path (`/opt/slaydx`) and backup path (`/root/slaydx-backups`).
  - Full infra topology of **two unrelated third-party projects** sharing the same box (their directory paths and container names) — this project's repo is disclosing operational details of tenants who never agreed to be named in *this* public repo.
  - The admin/owner's account: `username=adkhambek_4 (id=2), phone=+998…` (masked here per brief rule 4; full 12-digit number is in the file at `.claude/deploy.md:143`) — a real phone number tied to a real username and internal user id. This is PII, permanently published, reachable by anyone with a browser (no auth). Note this is a **different** number from the one hardcoded in `lib/server/admin-phones.ts` — see DEPS-08.
- **Reproduction:** `curl -s https://raw.githubusercontent.com/khusinboev/slaydx/main/.claude/deploy.md` (not run — no network per brief rule 3 — but `git ls-tree -r origin/main --name-only | grep '^\.claude/'` from the local clone confirms the file is in the tree GitHub serves for `main`).
- **Proposed fix:**
  1. Rotate/harden immediately regardless of history cleanup: treat the server IP as burnt (already was somewhat guessable, but this confirms root-SSH is live there — review `sshd_config` for key-only auth, fail2ban, and consider a non-root deploy user) and tell the two other tenants (`nodavlattalim`, `mser`) their layout was exposed via a third party's public repo.
  2. Remove `.claude/deploy.md` (and the other 4 tracked `.claude/*` files, to be safe/consistent with the stated gitignore intent) from **history**, not just HEAD — `git rm --cached`, a history rewrite (`git filter-repo`/BFG) on every branch/tag, force-push, and ask collaborators to re-clone. A plain new commit that deletes the file is **not sufficient**: brief's rule 5 — anything ever committed to a public repo is compromised/must be treated as such, and `git log --all --diff-filter=A` will still show it forever.
  3. Decide whether the owner's phone number needs a compliance/notification step independent of git (it has been publicly readable since 2026-09-11).
  4. Add `.claude/` and `CLAUDE.md` to a pre-commit/CI check (e.g. a `git diff --cached --name-only | grep -q '^\.claude/'` guard) so this class of mistake can't recur silently.
- **Effort:** S (fix + rotation advice) / M (full history rewrite + coordinating force-push across branches, given 33 refs including many `worktree-agent-*` branches that also need to be handled or discarded)
- **Confidence:** high — verified directly via `git ls-files`, `git ls-tree -r origin/main`, and `git rev-parse main origin/main` (identical, dated 2026-09-22, i.e. current).

### DEPS-08 — Admin-authorization phone number hardcoded in source, public on GitHub — identifies the exact account to attack for full admin access
- **Severity:** P0
- **Location:** `lib/server/admin-phones.ts:15` (`const ADMIN_PHONES = ["+998…"]` — masked here per brief rule 4, full 12-digit number is in the file), currently tracked, present at `origin/main` HEAD (same commit state verified for DEPS-01).
- **Evidence:**
  ```ts
  const ADMIN_PHONES = ["+998…"]; // full number in file; masked here
  ```
  Per the file's own comment, admin status is intentionally **not** a DB flag but this hardcoded list — `session.ts` and `admin.ts` both check `isAdminPhone()` against it. This is a *different* real phone number than the one in `.claude/deploy.md` (DEPS-01) — checked full history of this file (`git log --all -p`), it has never changed, so this is the one and only admin phone since the file was added.
  - Impact is different from a typical infra-recon leak: this number **is** the de-facto authorization credential for the highest-privilege role in the app (Telegram login as this phone ⇒ full admin). Publishing it doesn't let an attacker log in directly (Telegram's own auth widget/HMAC with the bot token still gates that), but it hands any attacker the exact, singular target for phishing / SIM-swap / Telegram-account-takeover to obtain full SlaydX admin — instead of having to guess which of 50,000 users is the admin, the repo tells them.
- **Reproduction:** Read `lib/server/admin-phones.ts` from the public GitHub tree (`origin/main`, confirmed present via the same `git ls-tree -r origin/main` check as DEPS-01).
- **Proposed fix:** Move the admin allowlist out of source (e.g. an env var read once at boot via `lib/server/env.ts`, or a small out-of-repo config file mounted into the container, `/opt/slaydx/.env`-style) so it never needs to be in git at all; the file's own stated goal ("changing admin requires a deploy, so a DB compromise can't self-promote") can be kept with an env-var approach — it still requires a deploy/restart to change, it just isn't public. Also rewrite history to remove this file/line (same history-rewrite caveat as DEPS-01 — a superseding commit is not enough on a public repo).
- **Effort:** S (code change) / M (coordinated with the DEPS-01 history rewrite)
- **Confidence:** high — read directly from the tracked file and confirmed present on `origin/main`.

### DEPS-02 — `ipHash()` in game-sessions.ts bypasses the validated env accessor and falls back to a hardcoded, guessable salt
- **Severity:** P2
- **Location:** `lib/server/game-sessions.ts:78`
- **Evidence:**
  ```ts
  export function ipHash(ip: string): string {
    return createHash("sha256").update(`${process.env.SESSION_SECRET ?? "slaydx"}:${ip}`).digest("hex").slice(0, 32);
  }
  ```
  This reads `process.env.SESSION_SECRET` directly instead of the centralized, validated `env.sessionSecret` (from `lib/server/env.ts`, used correctly by the near-identical function in `lib/server/session.ts:163`, and by `lib/server/auth.ts:146` / `lib/server/telegram.ts:87`). `env.ts`'s `sessionSecret()` (lines 52-64) throws in prod (`isProd && !isBuildPhase`) if `SESSION_SECRET` is unset or <32 chars, but that check only fires when `env.ts` is imported/evaluated; `game-sessions.ts` never imports it, so this one function has its own silent, hardcoded fallback (`"slaydx"` — the brand name, i.e. guessable) instead of crashing loudly like the rest of the app. The comment directly above (line 74) says this salt exists specifically so the IP hash resists dictionary attack given the small IPv4 space — a guessable salt defeats that purpose.
  - `docker-compose.yml` does gate `SESSION_SECRET` for both `web` and `worker` services via `${SESSION_SECRET:?SESSION_SECRET kerak}`, and both set `NODE_ENV=production` in the Dockerfile, so in the **documented** docker-compose deploy path this fallback should not currently be reached (the container won't even start without the var, and if it started, `env.ts`'s own throw would already have killed the process before `ipHash` could run, since some other module almost certainly imports `env.ts` first). It is a real bypass and defense-in-depth gap for any deployment that doesn't go through this exact compose file (bare `next start`/`tsx worker.ts`, a different orchestrator, `.env` edited to remove just this one var while others stay).
- **Reproduction:** In a prod-mode process with `SESSION_SECRET` unset, call `ipHash("1.2.3.4")` before any code path imports `lib/server/env.ts` — it returns `sha256("slaydx:1.2.3.4")` instead of throwing. (Not run — would require starting the app, excluded by brief rule 2.)
- **Proposed fix:** Change `game-sessions.ts:78` to import and use `env.sessionSecret` (from `lib/server/env.ts`), matching `session.ts:163`, so a missing/weak secret fails loudly in prod instead of silently degrading to a guessable salt.
- **Effort:** S
- **Confidence:** medium — the vulnerable line and the inconsistency with the safe sibling function are confirmed by reading the code; full runtime reachability (whether `env.ts` is guaranteed to load before any route can reach `ipHash`) was not proven by execution, per the no-heavy-commands rule.

### DEPS-03 — `sharp@0.34.5`: 2 high-severity libvips/libheif CVEs; one real (narrow) runtime call path
- **Severity:** P2
- **Location:** `lib/generation/figures/png.ts:47-49` (only live call site); `next.config.ts` (`images: { unoptimized: true }`, confirms the OTHER call path — Next's built-in image optimizer — is disabled)
- **Evidence:** `npm audit --omit=dev --json`: `sharp` high, installed `0.34.5`, vulnerable range `<=0.35.4-rc.0`, `fixAvailable: {"name":"sharp","version":"0.35.4","isSemVerMajor":true}` (declared range is `^0.34.5`, which for a 0.x package means 0.35.4 is a breaking bump per npm/semver). Two advisories: GHSA-f88m-g3jw-g9cj (libvips, "CVE-2026-33327/33328/35590/35591", fixed `<0.35.0`) and GHSA-rgj7-g3m4-5g8c (libheif, fixed `<0.35.4`).

    1. Next.js's `/_next/image` optimizer — verified in `node_modules/next/dist/server/next-server.js:255` (`if (imagesConfig.loader !== 'default' || imagesConfig.unoptimized) { await this.render404(...); return true; }`) that when `images.unoptimized: true` (set in `next.config.ts`, with a comment already citing this exact GHSA as the reason), the route 404s **before** any `sharp` call. The SVG buffer is built by `lib/generation/figures/svg.ts` from structured chart data (not a raw user-uploaded file), but does embed LLM-generated labels/text, so it is topic/prompt-influenced, not purely static.
  - Could not confirm from `npm audit`'s advisory titles alone whether the "libvips inherited vulnerabilities" (GHSA-f88m-g3jw-g9cj) touch the SVG/librsvg loader specifically or only the ICNS/HEIF/JXL-style decoders named in the sibling advisory — fetching the GHSA text is out of scope (brief rule 3: no network beyond npm/registry).

- **Proposed fix:** Bump `sharp` to `^0.35.4` in `package.json` (semver-major per npm — needs `npm install sharp@^0.35.4` to update the lockfile) and re-run the project's own figures/diagram tests (`tests/figures-png.test.mts`) plus a live check per `CLAUDE.md`'s 3-stage testing standard (mutation + live + visual), since this is exactly the code path it exercises.
- **Effort:** M
- **Confidence:** medium — code paths and the Next.js mitigation are verified by reading source; whether the specific libvips CVEs are reachable via the SVG loader is unconfirmed (would need the GHSA advisory text).

### DEPS-04 — `npm audit` flags 1 critical + 3 more high findings; all confirmed NOT reachable in this deployment (patch anyway, it's free)

- **Effort:** S
- **Confidence:** high for the reachability analysis (verified against actual shipped source, not just advisory titles).

### DEPS-05 — Docker base images unpinned (tag only, no digest)
- **Severity:** P3
- **Location:** `Dockerfile:5,15,26` (`FROM node:22-alpine` ×3 stages), `docker-compose.yml:3` (`image: postgres:16-alpine`)
- **Evidence:** All four `FROM`/`image:` lines use a mutable tag with no `@sha256:...` digest. `node:22-alpine` and `postgres:16-alpine` are re-pushed by upstream regularly (patch releases, base OS updates); a rebuild on two different days can silently pull different underlying images, so `deploy.sh`'s `docker compose -p slaydx build` is not fully reproducible/pinned, and a compromised or yanked upstream tag would be pulled automatically on next build with no diff to review.
- **Reproduction:** N/A — static config read.
- **Proposed fix:** Pin with a digest alongside the tag for readability, e.g. `FROM node:22-alpine@sha256:<digest>`, `image: postgres:16-alpine@sha256:<digest>`; update the digest deliberately (and re-test) when a base-image bump is wanted, same as any other dependency bump.
- **Effort:** S
- **Confidence:** high.

### DEPS-06 — Worker image ships ~430 devDependency packages (`npm ci --include=dev`) into production
- **Severity:** P3
- **Location:** `Dockerfile` worker stage (`RUN npm ci --include=dev && npm cache clean --force`)
- **Evidence:** `package-lock.json` has 570 total packages, 432 reachable only via `devDependencies`. The Dockerfile comment explains this is deliberate: `tsx` (needed to run `scripts/worker.ts` and admin scripts like `topup.mts`/`seed-demo.mts`) lives in `devDependencies`, and NODE_ENV=production without `--include=dev` previously caused the worker to fall back to `npx tsx` fetching `tsx` from the registry **at container start** — a real prior outage ("BARCHA generatsiya navbatda abadiy qotib qoladi" if the registry is unreachable) that this flag fixed. That reasoning is sound and this is **not a mistake** — but the fix is broader than necessary: it drags in `eslint`, `eslint-config-next`, `tailwindcss`, `jsdom`, `@testing-library/*`, `typescript`, etc. (none ever executed by the worker at runtime) alongside the one package actually needed (`tsx`). This enlarges the worker's attack surface (any future RCE-class bug in an unused dev tool is one `require()` away from anything that already achieves code execution in the worker) and image size/pull time, for no functional benefit.
- **Reproduction:** N/A — `Dockerfile`/`package.json` read; `node -e` count against `package-lock.json` above.
- **Proposed fix:** Move `tsx` from `devDependencies` to `dependencies` in `package.json` (the only thing the worker image actually needs beyond prod deps), then change the worker stage back to plain `npm ci` (no `--include=dev`). This keeps the exact fix for the original outage (tsx is always present, no network fetch at container start) while dropping the ~430 unrelated dev-only packages.
- **Effort:** S
- **Confidence:** high — the tradeoff and its cause are explicit in the Dockerfile's own comment; the narrower fix (`tsx` as a prod dep) directly addresses the documented root cause.

### DEPS-07 — License review: one LGPL-3.0 direct dependency, low practical risk (short, per brief scope)
