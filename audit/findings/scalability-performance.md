### SCALE-01 — Global `/api/:path*` header rule forces `Cache-Control: private, no-store` onto every image/thumbnail/audio route, so every page load re-reads every image from Postgres through the single Node process
- **Severity:** P1
- **Location:** `next.config.ts:106-110` (`source: "/api/:path*"` → `Cache-Control: private, no-store`); overridden route headers: `app/api/generations/[id]/assets/[assetId]/route.ts:29` (`private, max-age=86400, immutable`), `app/api/generations/[id]/thumb/route.ts:27` (`private, max-age=86400`), `app/api/o/[token]/audio/[assetId]/route.ts:48` (`public, max-age=86400, immutable`), `app/api/uploads/photo/[assetId]/route.ts:25`; Next merge rule `node_modules/next/dist/server/send-response.js:46-52` and `node_modules/next/dist/server/lib/router-server.js:305-307`; eager full-size images on list cards `components/home/FilePreview.tsx:45-47,126-160` + `components/viewers/SlideCanvas.tsx:170-174` (no `loading="lazy"`, no thumbnail size); design intent `lib/server/migrations/002_assets.sql:3-7` ("brauzer keshlaydi").
- **Evidence:** Next 15.5.23 applies `next.config` `headers()` to the Node response **before** the route runs (`router-server.js:305` `res.setHeader(key, resHeaders[key])`). When the route handler's `Response` is copied out, `send-response.js:49-50` only appends a header `if (… || !isHeaderPresent)`. So the config value wins and the route's own `Cache-Control` is silently dropped. The project already hit this exact mechanism for CSP ("Konfiguratsiya sarlavhalari marshrut o'zi qo'ygan sarlavhani USTIDAN yozadi (prodda `thumb` ning o'z CSP'si yo'qolgani shundan)" — `next.config.ts:116-118`, `docs/AUDIT-16.md:107`), but the `/api/:path*` rule still sets `Cache-Control` for the whole API tree. No test checks the header after the config merge: the only cache assertion, `tests/game-routes.test.mts:299` (`assert.match(res.headers.get("cache-control"), /public/)`), calls the audio handler directly, so it passes while production serves `private, no-store`.
  Consequence: the browser never caches content-addressed images. Each asset request = 1 session query + 1 `generation_assets` JOIN query returning the BYTEA. node-postgres uses the text protocol, so a 0.9 MB JPEG crosses the socket as a 1.8 MB hex string, is decoded into a Buffer and then copied again by `new Uint8Array(asset.bytes)` (`assets/[assetId]/route.ts:24`). Rough cost: 4–6 CPU-ms and ~3.6 MB of heap churn per 0.9 MB image on the one web event loop.
  Bytes per page load, using the project's own sizes (`docs/AUDIT-9.md:119`: pro deck = 21 × ~0.9 MB JPEG ≈ 19 MB; ordinary deck 5–8 MB, `docs/AUDIT-10.md`): opening a pro deck = ~21 asset requests / ~19 MB, **every time**. The home page ("Mening fayllarim") renders a `SlideThumb` for every slide deck in the list (up to 100 rows, `listGenerations` default) and each one loads the **full-resolution** first-slide image eagerly — a user with 20 decks pulls ~6–18 MB per home-page load, again on every load.
  **Scale:** `no-store` defeats the HTTP cache on every full document load — each Telegram Mini App open, reload, new tab or link from the bot (within one SPA session the browser's in-memory image list may reuse some images; that is browser-dependent and not a cache). At 2 000 active users with one full load per user every 5–10 min (≈3–7 loads/s) and ~10–20 images per load, the web process re-serves ~30–140 BYTEA images/s ≈ 30–120 MB/s: **15–70 % of its only core** at steady target, and **1.5–7 cores' worth in a 10× burst** — the image path alone then saturates the single web process and every poll, login and download on the site queues behind it (~200 images/s per core at ~5 CPU-ms each). With caching working as designed, repeat loads cost nothing and this load drops by the repeat-view ratio (typically 80–95 %).
- **Reproduction:** with any session cookie and a completed slide deck:
  `curl -s -D - -o /dev/null -b "slaydx_session=$TOK" "$APP/api/generations/$ID/assets/$ASSET" | grep -i cache-control` → expected `private, max-age=86400, immutable`, actual `private, no-store`. Same for `/api/generations/$ID/thumb` and `/api/o/$TOKEN/audio/$A`. Regression test sketch (runs against `next start`, not the bare handler): boot the standalone server, request an asset, `assert.match(res.headers.get("cache-control"), /max-age=86400/)`. Load proof for the orchestrator: k6/autocannon script that logs in N virtual users, each loads `/api/generations` then GETs every `preview.slide.model` image URL in a loop; watch web CPU and `pg_stat_activity` — then repeat with the header fixed.
- **Proposed fix:** Stop setting `Cache-Control` for the whole `/api/:path*` tree in `next.config.ts`. Either (a) set `private, no-store` in `json()`/`fail()`/`handler()` in `lib/server/api.ts` (every JSON response goes through them) and keep the route-level headers on binary routes, or (b) narrow the config rule with a negative-lookahead source that excludes `/api/generations/:id/assets/*`, `/thumb`, `/api/o/:token/audio/*`, `/api/uploads/photo/*`. Add `ETag` (the asset id is already a SHA-256 prefix) so revalidation is a 304. Separately give list cards a real small thumbnail (e.g. store a ~30 KB JPEG of the first slide image alongside `preview`) and add `loading="lazy"` to `SlideCanvas` `<img>` when used in cards.
- **Effort:** S (header) / M (card thumbnails)
- **Confidence:** high on the mechanism (Next source + the project's own recorded CSP incident); medium on the saturation numbers — confirm with the curl above and the load script.

### SCALE-02 — Generation capacity is ~30–50 jobs/hour; the target needs ~1 200–2 400 jobs/hour (50–160 concurrent job slots), and raising the slot count runs into three unguarded ceilings (per-job memory, provider quota, DB connections)
- **Severity:** P1
- **Location:** `docker-compose.yml:155` (`WORKER_CONCURRENCY:-2`), `lib/server/env.ts:200` (default 2), `lib/server/worker.ts:310-322` (`tick` — one process, `running < concurrency`), `lib/generation/budget.ts:33-365` (per-tool budgets), `lib/server/jobs.ts:341-380` (`claimJob`, FIFO), `lib/api-client.ts:367-408` (`pollGeneration`, 20-min client deadline), `lib/server/auth.ts:15,129` (`SIGNUP_BONUS_POINTS = 3000` for every new account), `lib/tools.ts:1399-1425` (a ≤20-slide deck or a 10–15-page referat costs 3 000 → free for every new user), `lib/server/db.ts:29` (`DATABASE_POOL_MAX` 10 per process).
- **Evidence:** Same root as INFRA-03 (no backpressure); this block adds the numbers the brief asks for and what breaks when the fix (more slots) is applied.
  *Service time per job* (budget formula → the project's own live measurements in `budget.ts` comments): essay 1 p. budget 249 s / real ~40–60 s; referat 15 p. 375 s / ~150 s; coursework 45 p. 645 s / ~420 s (measured); slide 10 → 230 s / ~90–120 s; slide 20 → 340 s / ~150–200 s; pro-slide 30 → 630 s / ~340–570 s (AUDIT-9 X-1 estimate); translation 200 k chars 560 s / ~450 s; article 15 p. 480 s; test 30 q. 255 s / ~200 s; image 90 s / ~30–70 s. A plausible mix averages **~150–240 s per job**.
  *Supply:* 2 slots × 3 600 s ÷ 150–240 s = **30–48 jobs/hour** (0.5–0.8 per minute).
  *Demand at target:* 2 000 active users, 10–20 % start a job within 10 min → 200–400 per 10 min = **1 200–2 400 jobs/hour, 25–80× supply**. Little's law: slots needed = λ·S = (0.33–0.67 jobs/s) × (150–240 s) ≈ **50–160 concurrent slots** steady, ×10 in a burst. The free 3 000-point signup bonus turns a Telegram-post burst of new accounts almost 1:1 into jobs (each can immediately run a 20-slide deck or a referat).
  *Queue behaviour:* a 10-minute burst at 20–40 jobs/min leaves ~200–400 jobs queued; draining at 0.5–0.8/min takes **4–13 hours**. `claimJob` is plain FIFO; nothing expires a `QUEUED` row (`reclaimStaleJobs` only touches `IN_PROGRESS`), every job is already charged (`enqueueGeneration` charges in the same tx), and every waiting tab polls every ~5 s until `pollGeneration` gives up at 20 min (FE-02/UX-05 cover the UI side). 400 waiting tabs ≈ 80 polls/s ≈ 160 queries/s of pure waiting.
  *Ceilings once slots are raised* (jobs are mostly I/O-bound, so one Node worker could run 10–20 at a time CPU-wise):
  1. **Memory per job** — pro deck holds 21 base64 images (~1.2 MB each) + `LiveReporter` `structuredClone` copies + 19 MB PPTX + 19 MB `extractAssets` Buffers ≈ 100–150 MB; a 20 MB translation source is unzipped and re-zipped in memory ≈ 200–400 MB. 50 slots ≈ 5–15 GB on a VPS shared with two other projects and no container limits (INFRA-04).
  2. **Provider quota** — 50–160 jobs × `mapPool(3–5)` ≈ 150–500 concurrent LLM/image requests of 25–40 s each ≈ 250–1 000+ RPM on one API key, with no shared limiter (SCALE-06). Past the key's RPM/TPM, jobs fail and are refunded instead of waiting.
  3. **DB connections** — every process opens a pool of 10 (`db.ts:29`); stock `postgres:16-alpine` has `max_connections=100` → at most ~8 worker/web processes before `too many connections`, i.e. the horizontal path tops out around 8 processes without PgBouncer.
  Adding worker replicas is otherwise safe: `claimJob` uses `FOR UPDATE SKIP LOCKED`, `reclaimStaleJobs` runs in one transaction, and duplicated `housekeeping` purges are idempotent. Scale-in/deploy is not safe (INFRA-02: jobs killed after 2 s).
- **Reproduction:** (1) Real service times from prod: `SELECT tool_id, count(*), percentile_cont(0.5) WITHIN GROUP (ORDER BY extract(epoch FROM finished_at-started_at)) p50, percentile_cont(0.9) WITHIN GROUP (ORDER BY extract(epoch FROM finished_at-started_at)) p90 FROM generations WHERE status='COMPLETED' AND finished_at > now()-interval '30 days' GROUP BY 1;` → capacity/h = `3600 × WORKER_CONCURRENCY / weighted mean`. Queue wait today: `SELECT percentile_cont(0.9) WITHIN GROUP (ORDER BY started_at-created_at) FROM generations WHERE created_at > now()-interval '7 days';`. (2) Synthetic, under `scripts/heavy.sh` on a scratch DB with `WORKER_INLINE=false`: stub `buildArtifact` to `await sleep(180_000)`, enqueue 300 jobs at 30/min through `enqueueGeneration`, record `started_at - created_at` → expect it to grow linearly to hours; client-side, every tab stops polling at 20 min.
- **Proposed fix:** (1) Measure per-job p95 RSS per tool, then raise `WORKER_CONCURRENCY` (e.g. 12–16) with a `mem_limit` sized to concurrency × p95 RSS, and run `--scale worker=N`; raise `DATABASE_POOL_MAX` only together with PgBouncer (transaction mode) or a raised `max_connections`. (2) Admission control in `POST /api/generations` **before** `chargeInTx`: estimate wait = queued × mean service ÷ total slots; if above ~15 min return 503 + `Retry-After` (no charge) and show queue position/ETA. (3) Add a `QUEUED` TTL in `reclaimStaleJobs` (e.g. 30 min → `FAILED` + refund). (4) Per-user in-flight cap (SCALE-05) and a provider limiter (SCALE-06). (5) Consider not granting the signup bonus as immediate queue capacity during overload (e.g. bonus jobs get lower priority).
- **Effort:** L
- **Confidence:** high on mechanism and order of magnitude (from code budgets and the project's measured times); medium on the exact numbers — confirm with the two SQL queries on prod.

### SCALE-03 — Both hot read paths (`GET /api/generations/[id]` poll and the 3-second `GET /api/generations` list poll) read `values_json` — up to ~200 000 chars per row — and throw it away
- **Severity:** P2
- **Location:** `lib/server/jobs.ts:72-76` (`ROW_COLUMNS` includes `values_json`), `lib/server/jobs.ts:196-205` (`listGenerations`, `LIMIT 100`), `lib/server/jobs.ts:213-232` (`getGeneration`: `ROW_COLUMNS, html, doc_json, live_json`), `lib/server/jobs.ts:110-136` (`rowToSummary` never reads it); size source `lib/server/validate.ts:31,85` (`sourceText` ≤ `MAX_SOURCE_CHARS` = 200 000, `lib/tools.ts:1087`) and 80 keys × 4 000 chars; senders of `sourceText`: `components/forms/WorkComposer.tsx:261`, `components/forms/teacher/common.tsx:210`, `components/forms/GameComposer.tsx:352`, `components/forms/TranslationForm.tsx:93`, `components/forms/ToolWorkspace.tsx:293`; pollers `components/home/HomeFiles.tsx:40-44` (list every 3 s while any job runs), `components/providers.tsx:24` (list on every page load), `lib/api-client.ts:367-408` (detail every 1.2–5 s).
- **Evidence:** `ROW_COLUMNS` = `id, user_id, …, values_json, file_name, …`. `rowToSummary` builds the response without `values_json`, and `ResultView.toLegacyShape` sets `values: {}` — the column is never sent to the browser. Every file-based generation (coursework/referat/teacher/game «Fayl asosida», translation text mode) stores the extracted text in `values.sourceText`, up to 200 000 chars (≈400 KB UTF-8 for Cyrillic/Uzbek) in JSONB. Postgres must detoast and pglz-decompress it, send it, and node-pg `JSON.parse`s it on the web event loop, per row, per request.
  Per request: detail poll of one file-based job ≈ 0.4 MB extra; list of a teacher/student with 30 file-based rows ≈ 12 MB extra (≈25–60 CPU-ms of parse on the event loop plus similar decompression time in the Postgres backend), repeated **every 3 s** while any of their jobs is queued or running (and on every page load). Ordinary short forms cost ~2 KB/row, i.e. ~200 KB per list call — tolerable.
  **Scale:** ~50 heavy file-mode users sitting on the home page with a job queued (which under SCALE-02 lasts up to 20 min) ≈ 17 list calls/s × 12 MB ≈ 200 MB/s of JSON through one Node process — the event loop saturates, and every other request on the site slows with it. With the queue backed up (SCALE-02) the number of such waiting users is exactly what grows.
- **Reproduction:** on a scratch DB, create one user with 30 generations whose `values_json` holds a 200 000-char Cyrillic `sourceText`; then `autocannon -c 20 -d 30 -H "Cookie: slaydx_session=$TOK" $APP/api/generations` and compare p99 latency / web CPU with the same run after dropping `values_json` from `ROW_COLUMNS`. Prod prevalence: `SELECT tool_id, count(*), avg(octet_length(values_json::text))::int avg_b, max(octet_length(values_json::text)) max_b FROM generations GROUP BY 1 ORDER BY 3 DESC;`.
- **Proposed fix:** Split `ROW_COLUMNS` into a `SUMMARY_COLUMNS` without `values_json` for `listGenerations` and `getGeneration` (select `values_json` only in `claimJob`/share paths that need it). Make the home-page poll lighter: poll only the running ids (`GET /api/generations?ids=…` returning `id,status,progress,step`) instead of the full 100-row list every 3 s, and paginate the list (e.g. 24 per page with a `created_at` cursor).
- **Effort:** S
- **Confidence:** high on the mechanism; medium on prevalence — confirm with the SQL above.

### SCALE-04 — Document re-rendering (PPTX/DOCX/poster) runs inside web request handlers on the single event loop; the download path `GET …/file` triggers it with no rate limit
- **Severity:** P2
- **Location:** `app/api/generations/[id]/file/route.ts:50` (`ensureFreshFile` before every download, no `limit()` in the route), `lib/server/slide-commit.ts:218-289` (`rebuildFile`: `loadDocForEdit` → `adapter.render` → 1 tx writing the whole file), `lib/server/edit-adapters.ts:80-92,106-219` (`renderPptx` / `renderPptxWithTemplate` / `renderDocx` in the web process), `lib/generation/render-pptx.ts:48-57,193-208` (per image `resolveImage` → `getAsset` BYTEA → base64 string; `pptx.write`), `lib/generation/render-pptx-template.ts:213` (`generateAsync({compression:"DEFLATE"})` of a deck built from a ≤20 MB user template read by `getTemplate`), `lib/server/doc-polish.ts:69-87,447` (`renderGameFile` DOCX, `renderPosterFile` sharp/librsvg poster inside `POST …/polish`), `app/api/generations/[id]/rebuild/route.ts:30` (`rebuild:${user.id}` 30/h — the only limiter), `app/api/generations/[id]/doc/route.ts:32` (`edit` 120/min).
- **Evidence:** `rebuildFile` renders the whole deck/document in the Next.js process: for a pro deck it reads ~21 image rows (~0.9 MB each, hex-decoded), turns each into a ~1.2 MB base64 string for pptxgenjs, zips ~19 MB (JSZip base64-decode + CRC32 in JS), then writes the 19 MB BYTEA in one transaction. Custom-template decks additionally load a ≤20 MB template zip and re-DEFLATE it in pure JS. The worker budgets 12 s just for assembling a 30-slide pro deck (`budget.ts:66` "yig'ish 12 s"), so a web-side rebuild is plausibly **~0.5–3 s of CPU per call**, most of it on the one event loop (JSZip yields between chunks, so it does not freeze the process, but it takes the core that every poll, login and download shares).
  Triggers: the client's «Saqlash» (`useDocEdit.save` → PATCH + `POST /rebuild`, 30/h per user), polish of games/posters, and **every `GET …/file` when `file_version < doc_version`** (`ensureFreshFile`) — which has no rate limit. One user alternating a trivial `PATCH …/doc` (allowed 120/min) with `GET …/file` forces up to ~60 renders/min ≈ one full core, on a free 20-slide deck from the signup bonus. Two concurrent downloads of the same stale file both render (the advisory lock only guards the write, `slide-commit.ts:239`).
  **Scale:** at target, ~5 % of 2 000 active users editing and saving every 1–2 min ≈ 1–2 rebuilds/s × 0.5–3 s CPU ≈ 0.5–6 cores wanted from a process that has one → the web tier saturates at roughly **50–100 concurrent editors** (or a handful of deliberate users), and all requests queue behind rendering.
  Web-side heavy work, and where it should run:
  | Path | Work | Limit today | Should be |
  |---|---|---|---|
  | `POST …/rebuild`, `GET …/file` (stale), polish of games/posters | PPTX/DOCX/PNG render | 30/h (rebuild only) | worker job or `worker_threads` pool with global concurrency |
  | `GET …/file?format=pdf` | LibreOffice | none (FILE-03) | converter queue + cached PDF per `file_version` |
  | `GET …/thumb` | LibreOffice + pdftoppm | 2 per process (SCALE-07) | generated once by the worker at completion |
  | `POST /api/uploads/template` | LibreOffice + 2× pdftoppm (up to 90+60+30 s) | 5/10 min per user | background job |
  | `POST /api/extract`, `/api/uploads/source` | pdf.js / JSZip + regex on ≤8/20 MB | 20 per 5/10 min per user (FILE-04, SECB-01) | `worker_threads` with a timeout |
- **Reproduction:** measure the render cost (orchestrator, under `scripts/heavy.sh`): a script that builds a 30-slide pro `AcademicDoc` with 21 × 0.9 MB JPEG assets in a scratch DB and times `rebuildFile()` with `node --cpu-prof`; report CPU-ms and peak RSS. Then the abuse loop on a scratch server: `V=$(current docVersion); for i in $(seq 60); do curl -s -X PATCH -H 'content-type: application/json' -H "Origin: $APP" -b "$C" -d '{"baseVersion":'$((V+i-1))',"ops":[{"op":"notes","index":0,"value":"x'$i'"}]}' $APP/api/generations/$ID/doc >/dev/null; curl -s -o /dev/null -b "$C" $APP/api/generations/$ID/file; done` while a second client measures `GET /api/auth/session` latency (op shape: `DocOp` in `lib/generation/slide-edit.ts:33`).
- **Proposed fix:** (1) Call the same `rebuild:${userId}` limiter (shared bucket with `POST …/rebuild`) inside `ensureFreshFile` or make `GET …/file` return 409 `{code:"stale"}` and let the client call `/rebuild`. (2) Move rendering off the web event loop: enqueue a high-priority `render` job for the worker (the client already polls), or run `adapter.render` in a small `piscina` pool (size = cores − 1) with a global queue limit and 503 when full. (3) Coalesce concurrent rebuilds of the same id (in-flight map or take the advisory lock before rendering).
- **Effort:** M
- **Confidence:** medium — the code path and the missing limit are certain; the CPU-ms per render is inferred (the worker's own 12 s assembly budget) and must be measured with the script above.

### SCALE-05 — Queue is strict global FIFO with no per-user in-flight cap: one user (or one teacher batch) can hold every worker slot
- **Severity:** P2
- **Location:** `lib/server/jobs.ts:360-366` (`SELECT id FROM generations WHERE status='QUEUED' AND run_after <= now() ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED`), `app/api/generations/route.ts:33-34` (`gen:burst` 5/min, `gen:hour` 60/h per user — the only limits), `lib/server/worker.ts:310-322`.
- **Evidence:** The claim query has no notion of user. A single account may enqueue 5 jobs in one minute and 60 per hour. With `WORKER_CONCURRENCY=2`, five 45-page courseworks (~420 s each) submitted back-to-back occupy **both** slots for ~17 min, and every other user's job waits behind them. After the capacity fix (SCALE-02) the same thing happens proportionally: 60 jobs/h from one teacher generating a test per class, or a handful of accounts spending signup bonuses, take a fixed share of all slots and push everyone else's p90 wait up. There is also no cap on how many `QUEUED` rows one user may hold.
- **Reproduction:** scratch DB, `WORKER_CONCURRENCY=2`, stubbed `buildArtifact` sleeping 120 s: user A enqueues 5 jobs, then user B enqueues 1; record `started_at - created_at` for B → ≈ 2.5 × 120 s instead of ≤120 s. A test in `tests/queue.test.mts` style can assert that after A holds `cap` running jobs, `claimJob` returns B's job.
- **Proposed fix:** Make `claimJob` skip users already at a per-user in-flight cap (a soft cap — two workers claiming at the same instant can exceed it by one, which is fine), e.g.
  `… WHERE g.status='QUEUED' AND g.run_after <= now() AND (SELECT count(*) FROM generations r WHERE r.user_id=g.user_id AND r.status='IN_PROGRESS') < $cap ORDER BY g.created_at LIMIT 1 FOR UPDATE SKIP LOCKED` (add an index on `(user_id) WHERE status='IN_PROGRESS'`). Also reject new enqueues when a user already has N `QUEUED` rows (before charging).
- **Effort:** S
- **Confidence:** high

### SCALE-06 — No shared rate limiter for LLM/image providers; retries are too short to ride out a 429, so more workers means more failed/refunded jobs, not more throughput
- **Severity:** P2
- **Location:** `lib/generation/llm.ts:120-136` (`withRetry`: 3 attempts, sleeps 500 ms then 1 s, ignores `Retry-After`) used by slides, translation, resume, image studio, `write-llm` (`grep llmComplete`); `lib/generation/llm/chain.ts:60-90` (per-call ≤3 attempts, honours `retryAfterMs`) used by article/work/teacher/games/audio/polish; `lib/generation/image-provider-gemini.ts:96-99,214-219` (429 → `"rate"` failure, no retry); `lib/generation/slide-images.ts:69-70,349` (`PRO_IMAGE_LANES = 5`, `IMAGE_LANES = 3` per job); `lib/generation/*` `mapPool(3)`/`POOL = 4` per job; web-side callers sharing the same keys: `app/api/outline/route.ts:42`, `app/api/article/udk/route.ts:27`, `lib/server/doc-polish.ts:420`, `lib/server/article-rewrite.ts:99`.
- **Evidence:** Concurrency toward a provider is `jobs × lanes`, bounded only per job. Nothing counts requests across jobs, worker processes and the web process, which all use one `GEMINI_API_KEY`. When the key's RPM/TPM is exceeded the provider answers 429: the `llm.ts` path gives up after ~1.5 s of backoff (a per-minute quota needs up to 60 s), the image path does not retry at all, and the chain path moves to the next spec after 3 tries. A failed section/image then fails the job (full refund) or ships short (`delivered < want` → partial refund, `worker.ts:273-294`).
  **Scale:** in-flight provider calls ≈ concurrent jobs × 3–5. With the 50–160 slots SCALE-02 needs, that is ~150–500 concurrent calls; at 25–40 s per call ≈ 250–1 000+ requests/min and, at ~5–10 k tokens per call, several million tokens/min — above typical single-key quotas, and far above typical image-model RPM for pro decks (each pro job fires 5 image calls at once, ~21 per deck). The break point is `key RPM ≈ 60 × concurrent calls ÷ mean latency`; past it the refund rate climbs while the queue stays long.

- **Evidence:** The `OR` on the unindexed `revoked_at` forces a sequential scan of `sessions`, which gains a row per login (Mini App auto-login creates one each time a user arrives without a cookie) and keeps rows 30 + 7 days. At 50 000 users that is plausibly 10⁵–10⁶ rows, scanned once per minute **per worker**; `game_sessions` and `login_codes` are scanned the same way. After scaling to N workers (SCALE-02) the same purge runs N times a minute and the claim loop pauses while each worker's housekeeping is awaited. Small today, linear in users × workers.
- **Reproduction:** `EXPLAIN DELETE FROM sessions WHERE expires_at < now() - interval '7 days' OR (revoked_at IS NOT NULL AND revoked_at < now() - interval '7 days');` → `Seq Scan on sessions`.
- **Proposed fix:** Run housekeeping in one place only (take `pg_try_advisory_lock` at its start and skip if held), split the sessions purge into two index-backed deletes (add a partial index `ON sessions(revoked_at) WHERE revoked_at IS NOT NULL`), and index `game_sessions(expires_at)` / `login_codes(expires_at)`.
- **Effort:** S
- **Confidence:** high
