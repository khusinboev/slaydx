### BEB-01 — Astral-character truncation corrupts `doc_json`, making `completeJob` throw AFTER the file is already stored: the job ends FAILED + fully refunded, yet the finished file stays downloadable (free product + guaranteed refund)
- **Severity:** P0
- **Location:** truncation that can split a UTF-16 surrogate pair: `lib/generation/meta.ts:245` (`position: … .slice(0, 80)`), `:194` (`sourceText … .slice(0, SOURCE_TEXT_LIMIT)`), `:250` → `lib/generation/slide-params.ts:137` (`splitCsv … .slice(0, itemMax)`), and the pervasive `clip()`/`str()`/`arr()` helpers on LLM output (`lib/generation/slide-write.ts:53-55`). The corrupted meta is copied verbatim into the stored doc (`lib/generation/work/engine.ts:308-316` `{ ...meta }`, `article/engine.ts:475`, `teacher/engine.ts:227`; slides carry `meta` at `slide-write.ts:925/989`). Write order in the worker: `lib/server/worker.ts:251` `putGenerationFile` and `:256` `putAssets` run BEFORE `:258` `completeJob`; the failing serialization is `lib/server/jobs.ts:430` `JSON.stringify(result.doc)` into `doc_json JSONB`. Failure handling: `lib/server/worker.ts:296-303` catch → `failJob` + full `refund`, with NO cleanup of the already-stored file/assets (cleanup only runs on the lock-lost `won===false` branch, `:265-272`). Download path ignores status: `lib/server/storage.ts:73-85` `getGenerationFile` filters only `g.user_id`, and `app/api/generations/[id]/file/route.ts:50` `ensureFreshFile` no-ops for non-COMPLETED (`lib/server/slide-commit.ts:285`).
- **Evidence:** `.slice(0, n)` cuts by UTF-16 code unit. If code unit `n-1` is a high surrogate and unit `n` its low half (e.g. text ending in an emoji / CJK-extension / any U+10000+ glyph at the boundary), the result holds a lone high surrogate. `JSON.stringify` does NOT throw on this — verified it emits the escaped literal `\ud83d` (a 6-char ASCII sequence): `JSON.stringify({meta:{position:("a".repeat(79)+"😀").slice(0,80)}})` succeeds and ends `…\ud83d"}}`. Postgres JSONB rejects that escape on parse (`ERROR: invalid input syntax for type json — Unicode low surrogate must follow a high surrogate`), so the `completeJob` UPDATE throws. The throw is caught at `worker.ts:296`; `failJob` (which writes no `doc_json`) succeeds, `refund` returns the full price. But `putGenerationFile` at `:251` already committed the real DOCX/PPTX/PNG bytes and is never deleted on this branch. Net effect: user is charged, then fully refunded (net zero credits), and the completed file remains fetchable at `GET /api/generations/{id}/file`. An attacker repeats this for unlimited free documents at zero net cost. It also fires on ordinary traffic whenever legitimate LLM text or a user field ends on an astral glyph at a fixed-length cut — a paid job silently FAILs.
- **Reproduction:**
  1. DB-level proof of the reject: `node -e "const {Pool}=require('pg');new Pool({connectionString:process.env.DATABASE_URL}).query(\"SELECT '\\\"\\ud83d\\\"'::jsonb\").then(()=>console.log('accepted')).catch(e=>console.log('REJECTED:',e.message))"` → prints `REJECTED: invalid input syntax for type json`.
  2. End-to-end: enqueue any doc tool (e.g. `resume`, `coursework`, or `pro-slide`) with a field that maps to `meta.position` set to a 79-character string followed by one emoji (so the 80-char slice keeps the high half only), e.g. `position` = `"A"×79 + "😀"`. The worker builds the file, stores it, then `completeJob` throws; the row ends `FAILED` with a full refund transaction, but `GET /api/generations/{id}/file` returns the document.
  3. Unit sketch: `assert.equal((("a".repeat(79)+"😀").slice(0,80)).isWellFormed(), false)` then assert a JSONB round-trip of `{meta:{position: that}}` rejects.
- **Proposed fix:** Make truncation surrogate-safe (a shared `truncate(str,n)` that drops a trailing lone surrogate) and use it in `meta.ts`, `slide-params.ts` and the `clip/str/arr` helpers; OR strip/replace lone surrogates centrally right before persistence (add `.toWellFormed()` / replace `[\uD800-\uDFFF]` in `sanitizeValues` at `lib/server/validate.ts:87` and in a `serializeDoc` helper used by `completeJob`/`updateGenerationDoc`). Additionally, `completeJob` should run before or atomically with `putGenerationFile`, or the catch branch in `worker.ts:296-303` must delete the stored file+assets so a FAILED job is never downloadable; and `getGenerationFile` should refuse non-COMPLETED rows.
- **Effort:** M
- **Confidence:** high — mechanism verified in JS (stringify emits escaped lone surrogate; slice splits the pair). The one live check is Postgres rejecting the escape, which is standard documented JSONB behavior (repro step 1 confirms in seconds).

### BEB-02 — No AbortSignal is plumbed to the running generation, so a job that overruns its budget keeps executing (and spending on LLM/image calls) while `reclaimStaleJobs` requeues a second copy
- **Severity:** P1
- **Location:** `lib/server/worker.ts:189` (`deadline = Date.now() + jobDeadlineMs(job)`) — a plain epoch number, no `AbortController`; `lib/generation/index.ts:498` `buildArtifact(tool, values, { deadline, … })` and every engine only *poll* `remainingMs(deadline)` (`lib/generation/quality.ts:126`) between steps; individual `fetch`es use their own fixed 40 s timeout (`lib/generation/llm.ts:249-256`, `llm/chain.ts:41-45`), not the job deadline. Reclaim requeues at `lib/server/jobs.ts:492-505` once `locked_at < now() - (budget/1000 + 30 s)`.
- **Evidence:** The deadline is purely cooperative. When an engine is inside a long/parallel LLM or image batch (e.g. `mapPool` over sections/slides, `quality.ts:131`) it does not observe the deadline until the current step returns; nothing cancels the in-flight `fetch`es. Meanwhile `reclaimStaleJobs` (housekeeping, 60 s cadence) flips the still-running job back to `QUEUED` and a second worker claims it. The original `runJob` continues to occupy one of only `WORKER_CONCURRENCY=2` slots and continues to bill the LLM/image providers with no cost cap (scout `generation.md` §3: "No per-user / global cost caps"). Its eventual `completeJob` is correctly rejected by the `locked_by` guard (`jobs.ts:424`), so results are not double-written — but the slot, memory and money are wasted, and under load (exam-season burst, 2 000 concurrent) two workers doing 1× useful work each halves effective throughput and doubles spend on every overrun. At ~10× burst this compounds: overruns become common, both slots get tied up by zombie executions, and the queue backs up.
- **Reproduction:** Enqueue a max-size `coursework`/`pro-slide` whose real runtime exceeds `budget_ms`. Log timestamps in `withRetry`/`mapPool`: observe LLM calls from the first execution continuing after `reclaimStaleJobs` has already requeued the job and a second worker has started it (two overlapping sets of provider calls for one `generation_id`). A test can stub `buildArtifact` to sleep past the deadline and assert the AbortSignal is never fired.
- **Proposed fix:** Create an `AbortController` in `runJob` fired at `jobDeadlineMs`, pass `signal` through `BuildOptions` into every `fetch` (`llm.ts`, image providers, research `http.ts`, TTS) so an overrun actually cancels outstanding network work; alternatively cap concurrent LLM fan-out and shorten per-call timeouts by `remainingMs`. At minimum, reclaim should not requeue while the original worker is provably alive (extend heartbeat semantics) to avoid overlapping executions.
- **Effort:** L
- **Confidence:** high (deadline-is-a-number, no signal) for the "not aborted / overlapping execution" claim; medium on the load-throughput magnitude (depends on how often real runtime exceeds budget in production).

### BEB-03 — The standalone worker process installs no `unhandledRejection` / `uncaughtException` handler, so one leaked rejection crashes the whole container (all IN_PROGRESS jobs drop to reclaim)
- **Severity:** P2
- **Location:** `scripts/worker.ts:12-15` (only the top-level `loop()` promise is caught) and `lib/server/worker.ts:408-417` (`runWorkerProcess` registers only `SIGTERM`/`SIGINT`). No `process.on('unhandledRejection'|'uncaughtException')` anywhere in the repo (grep: only `SIGTERM`/`SIGINT` in `worker.ts` and `scripts/bot.mts`).
- **Evidence:** The web process is shielded because Next's server installs its own `unhandledRejection` handler (`node_modules/next/dist/server/next-server.js:193`), but the production worker container (`Dockerfile` `worker` target → `node_modules/.bin/tsx scripts/worker.ts`, `WORKER_INLINE=false`) has none. Node 22 defaults to `--unhandled-rejections=throw`, so any promise that rejects without a catcher terminates the process. Most worker paths are guarded (`void …catch(()=>{})`, `LiveReporter.stop()` awaits its `assetQueue`/`writeChain`), but the surface is large (per-tool engines, research, TTS) and one un-awaited rejection anywhere brings the container down. `restart: unless-stopped` restarts it and `reclaimStaleJobs` eventually recovers jobs, but every crash abandons all in-flight jobs for up to `budget_ms + 30 s` and a reproducible input becomes a crash-loop that empties the queue repeatedly.
- **Reproduction:** In a scratch worker, throw asynchronously from a path that is fire-and-forgotten (e.g. reject inside a `void`-ed promise not chained into `stop()`); observe the process exit instead of logging and continuing. A test can assert `process.listenerCount('unhandledRejection') > 0` after `runWorkerProcess` starts — today it is 0.
- **Proposed fix:** In `runWorkerProcess` add `process.on('unhandledRejection', e => console.error('[worker] unhandledRejection:', e))` and `process.on('uncaughtException', e => { console.error(...); /* let current job fail, keep looping or exit cleanly */ })`, mirroring what Next gives the web process.
- **Effort:** S
- **Confidence:** high.

### BEB-04 — Housekeeping refunds dead jobs in a second query after `reclaimStaleJobs` commits; if the user deletes the now-FAILED row in that window, the refund is skipped and the charge is kept (money not returned)
- **Severity:** P2
- **Location:** `lib/server/worker.ts:326-334` (reclaim returns ids, then a separate `SELECT user_id … WHERE id=$1` + `refund`); `lib/server/jobs.ts:507-519` marks jobs `FAILED` and returns ids inside its own transaction; `lib/server/jobs.ts:234-243` `deleteGeneration` permits deleting rows whose status is `FAILED`.
- **Evidence:** `reclaimStaleJobs()` commits the `FAILED` update and returns the id list; only afterwards does housekeeping loop and, per id, `SELECT user_id` then `refund`. Between the reclaim commit and that SELECT, the row is already `FAILED`, so a `DELETE /api/generations/{id}` succeeds and removes the row (files/assets cascade). The subsequent `SELECT user_id` then returns `null`, `refund` is never called, and the original `charge` transaction remains — the user paid for a timed-out job and gets nothing back. The window is small (sub-second, once per 60 s housekeeping cycle) but it is real money loss with a plausible trigger: a user watching a stuck job hits "delete" exactly as the reclaimer fails it.
- **Reproduction:** Force a job to `attempts>=2` and stale; between `reclaimStaleJobs()` returning and the refund SELECT, delete the generation; assert no `refund` transaction exists for that reference while the `charge` remains.
- **Proposed fix:** Refund inside the reclaim transaction: have the FAILED `UPDATE … RETURNING id, user_id` and perform the refund from those rows (still idempotent via the `transactions(kind,reference)` unique index), instead of re-SELECTing after commit. Or forbid deleting a `FAILED` row until its refund is settled.
- **Effort:** S
- **Confidence:** high on the mechanism; the money-loss outcome is certain if the delete lands in the window.

### BEB-05 — A reclaimed job re-runs `buildArtifact` in full, doubling LLM/image spend with no cost cap; only asset writes are deduplicated
- **Severity:** P3
- **Location:** `lib/server/jobs.ts:481-521` (requeue path, `attempts < 2`), `lib/server/worker.ts:216-226` (`buildArtifact` re-invoked on the second claim). Asset idempotency: `lib/server/assets.ts:166-176` (`ON CONFLICT (generation_id, asset_id) DO NOTHING`, content-hash id).
- **Evidence:** On requeue the whole generation runs again from scratch — all writer/judge/research/image calls repeat, and `cost_json` telemetry is overwritten, not summed, so the true spend of a retried job is under-reported. No per-job or per-user cost ceiling exists (scout `generation.md` §3). Side effects that *are* idempotent: generated assets dedupe by SHA-256 (`putAssetBytes`/`putAssets`), and there is no completion Telegram notification (confirmed: `lib/server/worker.ts`/`index.ts` send nothing), so no double-notify. So the only non-idempotent cost is money/tokens. Bounded to 2 attempts, hence P3, but at scale each timeout roughly doubles that job's provider bill.
- **Reproduction:** Instrument `CostMeter`; force one timeout+requeue on a paid tool and observe two full sets of provider calls for one `generation_id`, with `cost_json` reflecting only the last run.
- **Proposed fix:** Accumulate `cost_json` across attempts (add, don't replace) so spend is visible; consider a per-user daily spend guard given the audit's cost-telemetry roadmap.
- **Effort:** M
- **Confidence:** medium (cost overlaps EXT/abuse scope; flagged here because it is a retry-lifecycle side effect).

### BEB-06 — Generated files/assets/rows are never purged (migration 011 removed the TTL and nothing replaced it); at target scale the Postgres BYTEA store grows without bound
- **Severity:** P2
- **Location:** `lib/server/migrations/011_no_expiry.sql` (drops NOT NULL and nulls all `expires_at`); `lib/server/worker.ts:324-366` `housekeeping()` purges sessions/game-sessions/rate-limits/tickets/sources(30d)/photos(90d) but **not** generations, `generation_files` or `generation_assets`; no `purgeExpiredGenerations` exists anywhere (grep). `enqueueGeneration` inserts with `expires_at` left NULL (`jobs.ts:172-190`).
- **Evidence:** Every DOCX/PPTX/PNG/MP3 and every extracted asset is stored as `BYTEA` inside Postgres and kept forever by design (011 comment + project memory: "muddatsiz"). This is an explicit product decision, so it is not a bug — but at the audit's target (50 000 users, bursts) it is an unbounded-growth capacity risk on a single shared VPS: a coursework DOCX is ~1–3 MB and slide decks carry image assets, so a few hundred thousand generations is hundreds of GB in one Postgres volume, degrading backups (`pg_dump` before every deploy per `.claude/deploy.md`), autovacuum and eventually filling the disk shared with two other projects → outage. The old 90-day row retention that would have bounded this was removed.
- **Reproduction:** N/A (design/capacity). Estimate: `SELECT pg_size_pretty(sum(size_bytes)) FROM generation_files;` growth over time; project against expected generation volume.
- **Proposed fix:** Reintroduce a bounded retention that respects the "keep my work" intent — e.g. keep `doc_json`/`preview` (small) indefinitely but purge the heavy `generation_files.bytes`/`generation_assets.bytes` after N days (regenerable on demand), or move blobs off-Postgres. Even a generous 180-day blob TTL caps growth. Add it to `housekeeping()` with a batch `LIMIT` and an index on a real expiry column.
- **Effort:** M
- **Confidence:** high that nothing purges generations; medium on when it bites (depends on real volume and disk headroom, shared with two other projects).

### BEB-07 — Live progress resets backwards when a job is reclaimed and restarted
- **Severity:** P3
- **Location:** `lib/server/jobs.ts:351-359` (`claimJob` sets `progress = 5, step = 'Boshlandi', live_json = NULL` on every claim, including the second one after requeue); `lib/generation/slide-progress.ts:39-60` re-emits `plan` from scratch on restart.
- **Evidence:** After `reclaimStaleJobs` requeues a stale job, the next `claimJob` resets `progress` to 5 and clears `live_json`, so a user who had watched progress climb to e.g. 60% (or a live slide deck fill in) sees it jump back to 5% and the deck reset to the empty plan. `live_seq` keeps incrementing (never reset), so the client's `since` polling still converges — this is a cosmetic regression, not data loss. Worth noting because the brief asks whether "progress goes backwards / duplicates" on reclaim: it goes backwards; it does not duplicate.
- **Reproduction:** Watch a slide job in the UI, kill the worker mid-run, let reclaim requeue it; observe progress reset to "Boshlandi".
- **Proposed fix:** On requeue, preserve the last `progress`/`step` (don't hard-reset to 5 in `claimJob` when `attempts > 1`), or show a "qayta boshlandi" state so the reset reads as intentional.
- **Effort:** S
- **Confidence:** high.

## Checked and OK
- **Double-finish / double-refund guard:** `completeJob`/`failJob`/`setCost`/`setLive` all gate on `WHERE id=$1 AND locked_by=$2 AND status='IN_PROGRESS'` (`jobs.ts:424,468,454,297`); a worker that lost the lock to reclaim gets `won=false` and discards its result + deletes its file/assets (`worker.ts:265-272`). Prevents the stale-worker-overwrites-fresh-result race. (Exception: BEB-01, where the failure is a throw, not `won=false`.)
- **Refund idempotency:** all money moves go through `credits.ts` with a `transactions(kind, reference)` unique index; `refund`/`refundPartial` early-return if a refund row exists (`credits.ts:178-181`), and charge/enqueue are one transaction (`jobs.ts:159-193`). A job gets either full or partial refund, never both (shared `reference`).
- **Charge↔enqueue atomicity:** `enqueueGeneration` wraps `chargeInTx` + INSERT in one `transaction()`; a surrogate-corrupted `values_json` at enqueue would roll BOTH back (clean 402/500, no money lost) — the dangerous split is only post-charge in the worker (BEB-01).
- **COMPLETED-without-file** is generally prevented: `putGenerationFile` runs before `completeJob`, and any earlier throw lands in the catch → `failJob` + refund with no COMPLETED row (only BEB-01 breaks the inverse: a stored file under a FAILED row).
- **LLM JSON robustness:** `parseLlmObject`/`parseLlmJson` (`json.ts`) never throw — truncated/garbage/empty input returns `null`, and callers consistently use `data?.field ?? []` before `.map` (e.g. `write-llm.ts:246-247`, slide/teacher/game engines), so malformed model output degrades to a quality-gate failure + refund rather than a crash.
- **Empty-file guard:** `worker.ts:228` throws on a zero-byte artifact → refund, so an empty file is never delivered as COMPLETED.
- **Partial-delivery refund:** `deliveredCount`→`refundRatio` is a single source (`delivered.ts:117`), full refund when nothing delivered, proportional (price-share) when short; worker applies it only on the `won` branch (`worker.ts:273-295`).
- **Migration safety at boot:** `ensureMigrated` is memoized and re-armable on failure (`db.ts:139-147`); advisory lock serializes concurrent instances (`db.ts:105`).
- **Poll/heartbeat backoff:** loop catches `tick` errors and sleeps 5 s on DB failure instead of hot-spinning (`worker.ts:377-381`); `setProgress`/`setLive`/`heartbeat` refresh `locked_at` to keep healthy long jobs from being reclaimed.
- **Post-processing isolation:** thumbnails (`thumb.ts`) and PDF (`pdf.ts`) are on-demand in the web process, not in `runJob`; `setCost` failure is swallowed (`worker.ts:241`) and never fails a paid job.
- **Research/LLM/TTS calls do have timeouts** (contra scout `generation.md` §7): `research/http.ts:41-46` adds `AbortSignal.timeout`, pipeline/lexuz/googlebooks pass `Math.min(CALL_TIMEOUT, remainingMs)`, TTS adapters use `AbortSignal.timeout(timeoutMs)` — the gap is job-level cancellation (BEB-02), not per-call timeouts.
