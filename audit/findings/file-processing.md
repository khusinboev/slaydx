### FILE-01 — Generated files/assets never purged; `FILE_TTL_HOURS` is dead config → Postgres disk grows unbounded
- **Severity:** P1
- **Location:** `lib/server/migrations/011_no_expiry.sql`, `lib/server/storage.ts:42` (`expires_at` forced NULL on every write), `lib/server/assets.ts:170`, `lib/server/worker.ts:324` (`housekeeping` purges sessions/sources/photos but NOT generation_files/assets), `docker-compose.yml:86` (`FILE_TTL_HOURS: 72`), `lib/server/env.ts` (no `FILE_TTL` read anywhere).
- **Evidence:** Migration 011 dropped the NOT NULL on `generation_files.expires_at`/`generation_assets.expires_at` and set every existing row to NULL; `putGenerationFile` now always writes `expires_at = NULL`, `putAssets` always writes `NULL`. `housekeeping()` calls `purgeExpiredSessions/GameSessions/RateLimits/Tickets/OldSources(30)/OldPhotos(90)` but never deletes `generation_files` or `generation_assets`. `grep -c FILE_TTL lib/server/env.ts` = 0: the compose var `FILE_TTL_HOURS=72` is read by nothing. Files (BYTEA up to `MAX_FILE_BYTES` = 25 MB each) and every image/audio asset are kept forever unless the user manually deletes the generation. On the shared single VPS the Postgres `pgdata` volume is the whole product's disk. **Scale:** 2 000 active users × a few docs/day, average DOCX/PPTX ~0.5–3 MB plus slide/figure assets → tens of GB/month with zero reclamation; when the shared disk fills, every INSERT (jobs, payments, sessions) fails and the whole product plus the two co-tenant projects go down. It also breaks a documented promise: `scripts/seed-demo.mts:6` and `docs/AUDIT-6.md` still assume `FILE_TTL_HOURS` expires old files.
- **Reproduction:** `grep -rn "generation_files\|generation_assets" lib/server/worker.ts` → no purge. Insert N completed generations, watch `SELECT pg_total_relation_size('generation_files')` grow and never shrink across housekeeping cycles. Nothing consults `expires_at` (indexes `generation_files_expires_idx` exist but are dead).
- **Proposed fix:** Decide policy explicitly. Either (a) re-introduce a purge in `housekeeping()` — `DELETE FROM generation_files WHERE created_at < now() - (FILE_TTL_HOURS||' hours')::interval` plus matching assets, and mark the generation as expired (so `ResultView` shows "muddati tugagan", the AUDIT-6 C1 state) — reading `FILE_TTL_HOURS` in `env.ts`; or (b) if indefinite retention is the deliberate product decision, add a per-user/global storage quota and remove the misleading `FILE_TTL_HOURS` from compose and the seed/docs comments. As-is the config lies and disk is unbounded.
- **Effort:** M
- **Confidence:** high

### FILE-02 — OOXML translation/template parsing loads whole file into memory with weak zip-bomb guards; multiple copies held at once
- **Severity:** P2
- **Location:** `lib/generation/translate/xml-scan.ts:233` (`openOoxml`), `lib/generation/translate/xml-scan.ts:224` (`MAX_UNZIPPED_BYTES = 80 MB`), `lib/generation/pptx-template.ts:200` (`parsePptxTemplate` — NO uncompressed budget at all), `lib/generation/render-pptx-template.ts:228,254`, `lib/extract-text.ts:80` (`readEntry` budget), `lib/generation/image-studio.ts` (JSZip).
- **Evidence:** JSZip 3.10.1 `loadAsync(bytes)` holds the entire compressed archive in memory and, per entry, `file.async("string")` inflates the whole entry into a JS string before any length check can run — the `_data.uncompressedSize` pre-check in `openOoxml`/`readEntry` reads the ZIP-declared size (attacker-controlled, can under-declare) but the real defense is only the post-inflation `budget -= text.length`, which is checked *after* the full entry is already in RAM. A single crafted `word/document.xml` that declares a small `uncompressedSize` but inflates to hundreds of MB is fully materialized before the negative-budget throw fires. Worse, `parsePptxTemplate` (the «O'z shablonim» path) applies NO budget: it calls `zip.file(path)?.async("string")` on presentation.xml, master, theme, and *every* slideLayout with no cap. A 20 MB PPTX (the upload limit) with a highly compressible master/layout XML (ratio ~1000:1) inflates to GBs. **Scale:** DEFLATE ratio ~1000:1 means the 20 MB upload cap permits ~20 GB decompressed; with `WORKER_CONCURRENCY=2` plus the web container doing template rasterization, two such jobs can exhaust the shared 14 GB box. The translate path holds compressed archive + inflated `parts` map + re-serialized output simultaneously.
- **Reproduction:** Craft a PPTX whose `ppt/slideLayouts/slideLayout1.xml` is ~50 MB of repeated whitespace, deflated to <1 MB; upload via `/api/uploads/template`. `parsePptxTemplate` inflates it with no budget → RSS spike/OOM. For translate: DOCX with an over-sized `word/document.xml` under-declaring `uncompressedSize`; `openOoxml` inflates the full string before throwing.
- **Proposed fix:** Add a hard cap in `parsePptxTemplate` mirroring `openOoxml`'s budget (and check `file._data.uncompressedSize` sum before inflating). For all sites, prefer streaming/`nodeStream` with an incremental byte counter that aborts mid-inflate, and cap per-entry uncompressed size (e.g. 25 MB) and entry count, rather than only a post-hoc total. Do not trust the declared size as the primary guard.
- **Effort:** M
- **Confidence:** medium — a runtime PoC (crafted archive) would confirm the exact RSS peak; the missing budget in `parsePptxTemplate` is certain by inspection.
### FILE-03 — On-demand PDF conversion has no concurrency cap on the web container → soffice fork-bomb / OOM under load
- **Severity:** P1
- **Location:** `app/api/generations/[id]/file/route.ts:83` (`toPdf` on `?format=pdf`, uncapped), `lib/server/pdf.ts:44` (`toPdf` — per-call 90 s timeout, ~200–400 MB/process, no semaphore), `lib/server/template-upload.ts:87,225` (`rasterizeTemplate`→`toPdf`, uncapped). Contrast `lib/server/thumb.ts:36,84` which *does* cap at `MAX_PARALLEL=2`, but that slot pool is private to thumbnails and does not count the download or template soffice processes.
- **Evidence:** LibreOffice (and pdftoppm) run ONLY in the web container — the worker Dockerfile target (`Dockerfile:80`) installs `fontconfig ttf-liberation font-noto` and NOT `libreoffice`/`poppler-utils`, so `pdfBinary()` returns null in the worker and every soffice spawn happens in `web`. `/api/generations/[id]/file?format=pdf` calls `toPdf` with no global limit and no per-user rate limit (no `limit(...)` in the route). Each call spawns a `soffice` process holding ~200–400 MB. The three soffice entry points (PDF download, thumbnail, template rasterize) have independent/absent limits, so the effective cap is not 2 but unbounded. **Scale:** the box is a shared 14 GB VPS; ~20–40 concurrent PDF downloads (one Telegram burst, or one user scripting downloads across their docs — `TranslationViewer` even auto-loads `?format=pdf` into an `<iframe>` on tab open, so opening several translation results fires several conversions) spawn dozens of soffice processes and OOM the web container plus the two co-tenant projects. nginx `proxy_read_timeout 120s` only drops the client; the node handler keeps the soffice process alive to its own 90 s timeout.
- **Reproduction:** `for i in $(seq 1 30); do curl -s -b "$COOKIE" "https://host/api/generations/$ID/file?format=pdf" >/dev/null & done` → watch `ps aux | grep soffice.bin` climb to ~30 and RSS blow past container memory. Same via opening several Tarjimon "Fayl" tabs.
- **Proposed fix:** Route ALL soffice/pdftoppm work through one shared semaphore (generalize `thumb.ts` `withSlot` into `pdf.ts`, cap e.g. 2 concurrent process-wide), queue or 503 beyond it, and add a per-user rate limit on `?format=pdf`. Set a hard container memory limit in `docker-compose.yml` (`deploy.resources.limits.memory`) so a spike cannot take down co-tenants.
- **Effort:** M
- **Confidence:** high

### FILE-04 — Untrusted PDF parsed page-by-page with no page cap and no timeout; quadratic line grouping → CPU/DoS
- **Severity:** P2
- **Location:** `lib/generation/translate/pdf.ts:234-262` (`pdfToBlocks` loops `for (n=1; n<=doc.numPages; n++)`, no cap), `lib/generation/translate/pdf.ts:66-90` (`toLines` does `out.find(...)` per item → O(items²) per page), `lib/server/source-upload.ts:138-166` (`DEFAULT_COUNTER`/`pdfPages` run at upload), `lib/extract-text.ts:133` (`extractPdfBuffer`). `unpdf`/pdf.js calls have NO timeout anywhere.
- **Evidence:** A translation source PDF (≤20 MB) is fully parsed at upload time inside `/api/uploads/source` and again in the worker. `doc.numPages` is trusted and iterated with no ceiling; each page runs `getTextContent()` (CPU-heavy) and font-object probing. `toLines` groups text items via a linear scan over already-collected lines, so a single page with hundreds of thousands of tiny text runs is O(n²). All char limits (`TRANSLATION_MAX_CHARS`, scanned-PDF check) are applied AFTER `pdfToBlocks` has processed every page, so the cost is incurred before any limit fires. There is no wall-clock abort of pdf.js (it's async but the CPU work isn't cancellable by the deadline). **Scale:** a crafted 5 000-page or many-items PDF within 20 MB pins a core for tens of seconds to minutes; at upload it's bounded only by nginx's client drop (the handler keeps running — `maxDuration:60` is NOT enforced by self-hosted `next start`), at generation it eats the whole job budget and, after budget+30 s, `reclaimStaleJobs` re-queues it (attempts<2) so a second worker repeats the same CPU burn.
- **Reproduction:** Build a PDF with `numPages` ~5000 (or one page with ~200k text runs) under 20 MB; POST to `/api/uploads/source`. Observe a pinned CPU core well past the nominal 60 s and delayed response; enqueue a translation of it and watch it consume the budget then get retried.
- **Proposed fix:** Cap `doc.numPages` (e.g. reject > 300 pages before iterating), cap items-per-page, replace the O(n²) `toLines.find` with a bucketed/sorted grouping, and wrap the whole pdf.js parse in a real timeout (`Promise.race` that also calls `loadingTask.destroy()` to release the worker). Enforce the page cap at upload so the worker never sees an over-size PDF.
- **Effort:** M
- **Confidence:** medium — the missing cap and quadratic scan are certain by inspection; the exact CPU ceiling needs a crafted-PDF proof (orchestrator, serial).

### FILE-05 — Per-request `maxDuration` and the job deadline do not abort in-progress CPU work
- **Severity:** P2
- **Location:** `app/api/generations/[id]/file/route.ts:9` (`maxDuration=60`), `.../thumb/route.ts:7`, `app/api/uploads/template/route.ts:7` (`120`), `app/api/uploads/source/route.ts:11`; worker side `lib/server/worker.ts:189` (`deadline = Date.now()+jobDeadlineMs(job)` passed to `buildArtifact`, but no `AbortController`/`Promise.race` wrapping it).
- **Evidence:** The deployment is `next start` (standalone node `server.js`, `Dockerfile:65`), not a serverless platform, so the `maxDuration` exports are inert — nothing in the node runtime enforces them. The only request ceiling is nginx `proxy_read_timeout` (120 s for `/api/generations/`, 60 s elsewhere per `.claude/deploy.md`), and an nginx timeout drops the client socket but does NOT abort the node handler: a running soffice/pdf.js/translation call continues to completion, holding memory and a CPU. On the worker, the `deadline` is a cooperative value checked only at `await`/loop boundaries (`quality.ts remainingMs`, translate `remaining()`); a synchronous or un-timed-out step (pdf.js parse, `sharp` render, a big regex) runs past the deadline while `reclaimStaleJobs` simultaneously re-queues the "stale" job to a second worker — duplicating the load rather than stopping it.
- **Reproduction:** Trigger a slow PDF conversion (FILE-04 input) via `?format=pdf`; observe the soffice/pdf.js process still running after nginx has returned 504 to the client. On the worker, submit a job whose CPU step exceeds `budget_ms`; watch it get re-claimed (attempts→2) and run twice.
- **Proposed fix:** Wrap external spawns and pdf.js parses in a real timeout that kills the child / calls `loadingTask.destroy()` and rejects; give the worker an `AbortController` tied to the deadline and pass its signal into cancellable steps; ensure `reclaimStaleJobs` grace exceeds the hard kill so a job is never running in two workers at once.
- **Effort:** M
- **Confidence:** medium — maxDuration being inert on self-host is well established; confirm nginx timeouts from the server's untracked `sites-available/slaydx`.

### FILE-06 — soffice timeout may orphan `soffice.bin`; temp profile dir is rm'd out from under it
- **Severity:** P2
- **Location:** `lib/server/pdf.ts:56-87` (`execFile(bin, …, {timeout, maxBuffer})` then `finally rm(dir)`), same pattern `lib/server/thumb.ts:60`, `lib/server/template-upload.ts:94-95`.
- **Evidence:** `execFile` default kill sends SIGTERM to the direct child only. The Alpine `soffice` launcher (`oosplash`) forks the real `soffice.bin`; on timeout the launcher is killed but `soffice.bin` can be orphaned and keep running (a long-standing LibreOffice behavior), still holding ~200–400 MB and the per-call `-env:UserInstallation` profile under `dir`. The `finally` then `rm -rf dir` (including `profile/`) while the orphan may still be writing to it, and because each call uses a fresh mkdtemp profile, orphans accumulate on repeated timeouts (e.g. a pathological DOCX/PPTX that always hits 90 s). Combined with FILE-03's missing concurrency cap, a stream of conversion-timeout inputs leaks soffice.bin processes until OOM.
- **Reproduction:** Feed a DOCX/PPTX that makes LibreOffice hang (or set a tiny timeout) repeatedly; after each timeout check `pgrep -a soffice.bin` — orphans remain after the handler returned and after `dir` was removed.
- **Proposed fix:** Spawn detached in a new process group (`detached:true`) and on timeout `process.kill(-child.pid, 'SIGKILL')` to reap the whole group (launcher + soffice.bin); only remove the temp dir after confirming the process tree is dead. Pair with the FILE-03 semaphore.
- **Effort:** M
- **Confidence:** medium — orphaning depends on the exact Alpine soffice launcher; the missing process-group kill is certain by inspection.

## Checked and OK
- **Temp-file cleanup is correct** on success, failure and timeout: every `mkdtemp` is removed in a `finally { rm(dir, {recursive, force}).catch() }` — `lib/server/pdf.ts:85`, `lib/server/thumb.ts:68`, `lib/server/template-upload.ts:110`. (The residual risk is an orphaned `soffice.bin` still using the dir after rm — see FILE-06.)
- **Temp paths never contain a user-controlled filename**: LibreOffice/pdftoppm inputs use fixed names (`manba.docx`/`d.pdf`/`l.pdf`), so no path traversal / reserved-name issue in temp paths (`pdf.ts:53`, `thumb.ts:58`, `template-upload.ts:92`). Command args are execFile arrays (no shell), so no argument injection.
- **Content-Disposition is injection-safe**: `contentDisposition()` strips non-ASCII and `"`/`\`, and adds `filename*=UTF-8''<pct-encoded>` (`app/api/generations/[id]/file/route.ts:22`). Unicode topics download correctly; header cannot be broken.
- **Extension-lies-about-content is handled everywhere**: all upload paths sniff magic bytes, never trusting `content-type`/extension — `looksLikePptx` (zip sig + `ppt/presentation.xml`, `template-upload.ts:47`), `sniffSourceKind` (magic + extension + NUL check, `source-upload.ts:94`), `sniffImageType`/`imageDims` header-only for photo/logo (`slide-images.ts`), `extract-text.ts sniff()`.
- **`?format=pdf` restricted to convertible MIME** (`file/route.ts:80`): images/zip no longer sent to LibreOffice (would time out at 90 s). PDF input to `toPdf` is size-capped at 30 MB (`pdf.ts:27`) and rejects empty output → clean 502, not a 0-byte file.
- **Zero-byte / partial output guarded**: worker throws on `!file.bytes?.byteLength` before marking COMPLETED (`worker.ts:225`); `putGenerationFile` is a single upsert and rejects > `MAX_FILE_BYTES` 25 MB (→ job FAIL + full refund, no money loss). Corrupt uploads yield 4xx `ApiError` (415/422), not 500 (`source-upload.ts`, `template-upload.ts`, `extract/route.ts`).
- **Translation engine is deadline-aware**: `remaining() < MIN_WAVE_MS` stops issuing waves and marks the rest failed (`translate/engine.ts:351`); LLM waves run under `mapPool(POOL=4)` with per-call `AbortSignal` timeouts; report pairs capped (`PAIRS_MAX=3000`, `PAIRS_MAX_CHARS=700_000`). (CPU-bound steps still aren't hard-aborted — FILE-05.)
- **Audio/MP3 memory is bounded**: podcast ≤5 min, greeting ≤4 min, per-line ≤900 chars, source text ≤24 000 chars (`audio/types.ts`); peak WAV+MP3 held in `mergeToMp3` ~tens of MB — not a hostile vector.
- **`image-studio.ts` JSZip is output-only** (zips generated images), and **`extractAssets` de-dupes** identical bytes by SHA-256 so repeated images aren't stored twice (`assets.ts:20,166`); `data:` URLs are moved to `generation_assets`, keeping `doc_json`/HTML small.
- **Request bodies are capped upstream**: shared nginx `client_max_body_size 32m` (`.claude/deploy.md`, `source-upload.ts:41`) plus per-route header-first `content-length` checks bound formData memory; the chunked-encoding gap (no `content-length`) is bounded by the 32 MB nginx cap and the post-parse `file.size` check → at most ~32 MB buffered before a clean 413. Acceptable.
- **`openOoxml`/`readEntry` have an 80 MB post-inflation budget** and cap PPTX slides at 500 (`extract-text.ts:121`) — a real (if imperfect) zip-bomb guard; the gap is `parsePptxTemplate` having none and the guard firing only after full inflation (FILE-02).
