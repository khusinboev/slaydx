### CONC-01 — Unbounded LibreOffice fan-out in the web container: `GET …/file?format=pdf` has no rate limit and no global concurrency cap
- **Severity:** P1
- **Location:** `app/api/generations/[id]/file/route.ts:33-94` (no `limit()` call; `toPdf` at :83); `lib/server/pdf.ts:44-88` (`toPdf` — one fresh `soffice` process + fresh `-env:UserInstallation` profile per call, 90 s timeout, no semaphore); `lib/server/template-upload.ts:86-95` (`rasterizeTemplate` → `toPdf` + 2× `pdftoppm`, only a per-user 5/600 s limit); `lib/server/thumb.ts:36,81-93` (the only limiter, `MAX_PARALLEL=2`, covers thumbnails only and has an unbounded `waiters` queue); `components/viewers/TranslationViewer.tsx:182,187` (the «Fayl» tab mounts an `<iframe src=…?format=pdf&inline=1>` — every tab open re-runs a conversion, nothing is cached); `docker-compose.yml:20-98` (no `mem_limit`/`cpus` on `web`).
- **Evidence:** `toPdf` is `await run(bin, ["--headless", …, "-env:UserInstallation=file://<tmp>/profile", "--convert-to", "pdf", …], { timeout: 90_000 })` with nothing around it that bounds how many run at once; the file route calls it for every `?format=pdf` request after `requireUser` and never calls `limit()`. N concurrent requests ⇒ N `soffice` processes. A headless LibreOffice conversion typically needs ~150–400 MB RSS and one core for 2–20 s (the fresh profile adds start-up cost every time); large PPTX decks with images more. The web container has no memory limit and the VPS is shared with two other projects and Postgres, so the kernel OOM killer — not the app — decides who dies (Postgres, `web`, or another tenant). Next.js self-hosted ignores `maxDuration`, and when nginx drops the client (60/120 s) the child keeps running until its own 90 s timeout, so retries from impatient users stack on top. Breaks at roughly **10–20 simultaneous conversions** (≈3–6 GB) — reachable by one logged-in user with a shell loop, or organically in exam season (PDF download button + every translation result page view).
- **Reproduction:** with any COMPLETED DOCX/PPTX generation `$ID` and a session cookie: `for i in $(seq 40); do curl -s -o /dev/null -b "slaydx_session=$S" "https://<host>/api/generations/$ID/file?format=pdf" & done; sleep 3; docker exec slaydx-web-1 sh -c 'ps -o rss,comm | grep -c soffice'` → ~40 processes. Unit sketch (no LibreOffice): stub `node:child_process.execFile` with a function that records the number of in-flight calls and resolves after 200 ms; call `toPdf()` 10× via `Promise.all`; assert `maxInFlight <= 2` — fails today (10).
- **Proposed fix:** (1) one process-wide async semaphore inside `toPdf` (shared by file/thumb/template paths), e.g. 2 slots (≈ cores/2), with a bounded wait queue — reject with 503 + `Retry-After` when more than ~20 are waiting; (2) `limit(\`pdf:${user.id}\`, 10, 300)` on the `format=pdf` branch; (3) cache the converted PDF per `(generation_id, file_version)` in `generation_assets` (same pattern as `THUMB_ASSET_ID`) so the translation iframe and repeat downloads do not re-convert; (4) give `web` a `mem_limit` in compose so a spike kills the container, not Postgres/other tenants; (5) medium term, move conversions to the worker queue.
- **Effort:** S (1–2), M (3–5)
- **Confidence:** high for the mechanism (code read end-to-end); medium for the exact breaking point (per-process RSS is an estimate — confirm with `/usr/bin/time -v soffice --headless --convert-to pdf` on a 30-slide deck inside the runner image).
- **Cross-ref:** FILE-03 (same missing cap), INFRA-04 (no container limits), SCALE-07 (thumbnail slots). Merge.

### CONC-07 — Global FIFO claim with no per-user fairness: one account can occupy both worker slots for hours and starve every other user
- **Severity:** P1
- **Location:** `lib/server/jobs.ts:341-380` (`claimJob`: `SELECT id … WHERE status='QUEUED' AND run_after <= now() ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED` — no per-user condition); `app/api/generations/route.ts:33-34` (only `gen:burst` 5/60 s and `gen:hour` 60/3600 s — no cap on how many of a user's jobs may be QUEUED/IN_PROGRESS at once); `docker-compose.yml:155` (`WORKER_CONCURRENCY=2`, one worker process).
- **Evidence:** the whole platform has 2 execution slots, and they are handed out strictly by `created_at`. The rate limits allow one user to enqueue 5 jobs per minute / 60 per hour; each job holds a slot for its real duration (budgets 90–660 s; typical 2–6 min). A user who submits 20 jobs (a teacher generating tests for every class, a reseller, or a script spreading work over a few free Telegram accounts — each gets a 3 000-point signup bonus, `lib/server/auth.ts:15`, enough for one 2 000–3 000 job) puts ≈ 20 × 4 min / 2 slots ≈ **40 minutes** of queue in front of everyone who arrives after them; 60 jobs/h from one account alone is more than the worker's entire hourly capacity (2 slots × 60 min / ~4 min ≈ 30 jobs/h). There is no priority, no per-user running cap and no queue-depth admission control, so under the target load (2 000 active users, 10× bursts) wait times are unbounded and dominated by the heaviest submitters; the client gives up polling after 20 min (UX-05) while the user's credits stay charged.
- **Reproduction:** scratch DB + worker with a stubbed `buildArtifact` that sleeps 60 s: user A enqueues 10 jobs, user B then enqueues 1; B's job starts only after ~5 of A's batches (`SELECT started_at FROM generations WHERE user_id=B`) ≈ 5 min, versus ≤ 60 s with per-user fairness. Or SQL-only: insert 10 QUEUED rows for A then 1 for B and call `claimJob()` twice — both claims return A's jobs.
- **Proposed fix:** (1) fairness in the claim: add `AND NOT EXISTS (SELECT 1 FROM generations r WHERE r.user_id = g.user_id AND r.status = 'IN_PROGRESS')` (at most one running job per user; soft under concurrent claims, which is fine) or round-robin by `user_id` (`ORDER BY (SELECT count(*) … IN_PROGRESS for that user), created_at`); (2) admission control at enqueue: reject with 429 when the user already has ≥ 3 jobs `QUEUED`/`IN_PROGRESS` (count inside the `enqueueGeneration` transaction, after the `users … FOR UPDATE` lock that `chargeInTx` already takes, so it is race-free); (3) expose queue position/ETA (UX-07) and raise worker capacity (separate scalability item).
- **Effort:** S
- **Confidence:** high
- **Cross-ref:** SCALE-05 (same FIFO/no per-user cap), INFRA-03 / SCALE-02 (overall capacity). Merge.

### CONC-09 — Uploaded-document parsing runs on the web process's event-loop thread; pdf.js (unpdf "fake worker") yields only via microtasks, so one large PDF upload can freeze the whole web process for its full parse time
- **Severity:** P1
- **Location:** `app/api/uploads/source/route.ts:6-11,25-29` (the route's own comment: «PDF matn qatlamini o'qish (`unpdf`) katta hujjatda 20–40 s oladi»; limit 20 uploads / 600 s per user); `lib/server/source-upload.ts:299-331` (`uploadSource` → `DEFAULT_COUNTER` → `extractSegments` inside the request) and `:137-148` (`pdfPages` parses the PDF a second time when `extracted.pdf.pages` is missing); `lib/generation/translate/pdf.ts:223-260` (`pdfToBlocks`: `getDocumentProxy` + `getPage`/`getTextContent` for **every** page, no page cap); `lib/extract-text.ts:133-143` (`/api/extract` → `unpdf.extractText`, 8 MB, 20/300 s per user); `lib/extract-text.ts:101-131` (JSZip inflate of up to 80 MB XML + regex passes); `node_modules/unpdf/dist/pdfjs.mjs` (`LoopbackPort.postMessage` delivers via `this.#t.then(…)` with `#t = Promise.resolve()`; the evaluator's `TimeSlotManager` "yield" is `next(Cr)` with `Cr = Promise.resolve()`; `setTimeout` appears only in the XFA helper).
- **Evidence:** `unpdf` bundles pdf.js with its in-thread "fake worker": API↔worker messages, `ReadableStream` text chunks and the evaluator's 20 ms time-slot breaks are all Promise **microtask** continuations. Microtasks run to completion before Node returns to the I/O/timer phases, so the `for (n = 1; n <= pages; n++) { await getPage(n); await getTextContent() }` loop is very likely one uninterrupted stretch of the event loop — the 20–40 s the project measured for a large PDF would be 20–40 s during which the `web` container answers nothing (session lookups, `/api/generations/{id}` polling, payment webhooks, downloads). Even if some macrotask boundary exists, the CPU cost is ~100 % of the single web thread for that time. Upload routes are free and rate-limited only per user (20 per 10 min on `/api/uploads/source`, 20 per 5 min on `/api/extract`), so one ordinary account uploading an ordinary large PDF repeatedly can keep the site frozen most of the time, and at the target load a few students uploading textbooks at once (translation, "test from file", slides from file) do the same by accident. This is the linear baseline; SECB-01 is the super-linear (regex) variant on the same path.
- **Reproduction:** probe (run via `scripts/heavy.sh`): `const h = perf_hooks.monitorEventLoopDelay({resolution: 10}); h.enable(); const t = Date.now(); await DEFAULT_COUNTER("pdf", fs.readFileSync("big-300-pages.pdf")); console.log(Date.now() - t, h.max / 1e6)` — if `max` ≈ total parse time the event loop was blocked for the whole parse (raise to P0). Load test: one `curl -F file=@big.pdf …/api/uploads/source` while `while true; do curl -s -o /dev/null -w '%{time_total}\n' …/api/health; sleep 0.5; done` → health latency jumps to the parse duration.
- **Proposed fix:** run all user-file parsing (`extractSegments`, `extractFromBuffer`, `parsePptxTemplate`, `renderLayoutSheet`) in a `worker_threads` pool (e.g. piscina, 1–2 threads) with a hard per-task timeout (terminate the thread) and a small bounded queue (503 when full); read `numPages` first and reject PDFs above a page cap before any `getTextContent`; reuse the page count from the first parse instead of the second `pdfPages` pass; alternatively make the upload return immediately and measure `chars` in the job worker.
- **Effort:** M
- **Confidence:** medium — in-thread execution, microtask-only yielding and the per-user budget are read from the code/bundle; the actual max event-loop delay must be confirmed with the probe above (if confirmed, this is P0 like SECB-01).
- **Cross-ref:** FILE-04 (PDF page cap/timeout), SECB-01 (super-linear regex variant), FILE-02 (memory). Merge.

### CONC-02 — Payment settlement is not serialized per order: Payme Cancel ∥ Perform keeps credits on a cancelled order; concurrent duplicate Complete/Perform returns an error for a payment that was credited
- **Severity:** P2
- **Location:** `lib/server/payments.ts:276-311` (`settleOrder`: unlocked `findOrder` at :280, `topUp` at :289, then a separate autocommit `UPDATE … WHERE state <> 'cancelled'` at :298-309 whose 0-row result is ignored — still returns `ok: true`); `lib/server/payments.ts:313-325` (`cancelOrder`: `UPDATE payment_orders SET state='cancelled' … WHERE id = $1` — no state predicate); `app/api/payments/payme/route.ts:131-165` (Perform/Cancel both check-then-act on an unlocked read); `app/api/payments/click/route.ts:131-137,145-147`; `lib/server/credits.ts:229-250` (`topUp` checks the idempotency row at :230 **before** taking the user lock at :237).
- **Evidence:** 
  (a) Payme, txn X in state `pending`: T1 `PerformTransaction` reads `pending` → T2 `CancelTransaction` reads `pending` (not `paid`, so allowed) → T1 `topUp` commits `+amount` → T1 `UPDATE … state='paid'` → T2 `cancelOrder` overwrites to `cancelled` unconditionally and answers `state:-1`. Payme treats the transaction as cancelled (payer's money released) while the user keeps the credited balance. Variant: T2's update lands between T1's `findOrder` and T1's `UPDATE` → T1's `UPDATE` matches 0 rows, `settleOrder` still returns `{ok:true}` and Perform answers `state:2` with credits granted on a cancelled order. Same unconditional overwrite in Click `Complete` with `error<0` (click/route.ts:131-133) even for an already `paid` order.
  (b) Duplicate Complete/Perform arriving while the first is still in flight (provider retry after our response was slow): both pass the `SELECT 1 FROM transactions WHERE kind=$1 AND reference=$2` check; T2 blocks on `SELECT … FROM users FOR UPDATE`, T1 commits, T2's `INSERT INTO transactions` hits `transactions_ref_idx` → exception → rollback → Click route returns `error:-7 "Ichki xatolik"` (Payme: `-31008`). No double credit (the unique index holds), but the provider receives a failure for a payment we did credit; for Click an error on Complete means the payment is not confirmed/reversed on their side (verify in Click SHOP-API docs), i.e. credits without money.
  Both windows are small, but they widen exactly when the web process is slow (CONC-01, SECB-01) — the same condition that makes providers time out and retry/cancel.
- **Reproduction:** integration test against a scratch DB: create an order, attach txn, then run `Promise.all([settleOrder(id, Date.now()), cancelOrder(id, Date.now(), 3)])` in a loop with a `pg_sleep(0.05)` injected after `findOrder` (or use two pool clients and interleave manually); assert that a final `state='cancelled'` never coexists with a `transactions(kind='topup', reference='payme:X')` row — fails today. For (b): `Promise.all([topUp(u,{balance:5000},"click:1"), topUp(u,{balance:5000},"click:1")])` → one call rejects with `duplicate key value violates unique constraint "transactions_ref_idx"` (expected: both resolve, one `true`, one `false`).
- **Proposed fix:** make `settleOrder`/`cancelOrder` one transaction each that starts with `SELECT … FROM payment_orders WHERE id=$1 FOR UPDATE`, checks the state under the lock, calls a `topUpInTx(client, …)` variant, and writes `state='paid'` in the same transaction; `cancelOrder` → `UPDATE … SET state='cancelled' WHERE id=$1 AND state <> 'paid' RETURNING id` and map 0 rows to Payme `-31007` / Click `-4`. In `topUp` (and `refundRatio`, credits.ts:178-200) take the `users … FOR UPDATE` lock **before** the idempotency `SELECT`, or replace the check with `INSERT … ON CONFLICT (kind, reference) WHERE reference IS NOT NULL DO NOTHING RETURNING id` and only update the wallet when a row was inserted — a concurrent duplicate then returns `false` instead of throwing.
- **Effort:** S
- **Confidence:** medium — the interleavings are certain from the code; how often Payme/Click actually overlap Perform/Cancel or retry Complete while the first is in flight must be confirmed against their docs/sandbox.
- **Cross-ref:** DB-09 (same Perform∥Cancel interleaving; DB-09 already cross-refs this). Unique here: part (b), the concurrent-duplicate `topUp` unique-violation → provider error response.

### CONC-03 — Worker SIGTERM (every deploy) abandons in-flight jobs to a budget-sized lease: progress freezes up to ~11 min, work is redone from zero, a second interruption fails the job
- **Severity:** P2
- **Location:** `lib/server/worker.ts:408-416` (`shutdown`: `stopWorker(); setTimeout(() => process.exit(0), 2000)` — running `runJob`s are neither awaited, aborted nor released); `lib/server/worker.ts:47` (`WORKER_ID` is new per process, so the old `locked_by` never matches again); `lib/server/jobs.ts:481-521` (`reclaimStaleJobs`: stale only when `locked_at < now() - (budget_ms/1000 + 30 s)`); `lib/server/worker.ts:371-387` (housekeeping only after 60 s of accumulated poll sleeps); `docker-compose.yml:100-156` (no `stop_grace_period`); `.claude/deploy.md` (deploy = `docker compose build && up -d`, which recreates `worker`).
- **Evidence:** `locked_at` is refreshed every 2 s by `progressTicker`, i.e. it is a heartbeat — but the stale threshold is the job's whole budget, not a heartbeat age. After SIGTERM the process exits 2 s later with up to `WORKER_CONCURRENCY` jobs still `IN_PROGRESS`. Nobody touches them until `budget_ms/1000 + 30` s after the last heartbeat: 45-page coursework budget 645 s, pro-slide 30 slides 630 s, 15-page article 480 s → the user watches a frozen progress bar for 8–11 minutes, then the job restarts at 5 % (`attempts=2`) and all LLM/image calls of the first run are paid again. If the second run is interrupted too (another deploy, a crash such as CONC-04, an OOM from CONC-01) the job goes `FAILED 'Ish vaqti tugadi'` + refund. Deploys happen after every sprint, so this hits every job in flight at deploy time.
- **Reproduction:** run the worker against a scratch DB with a stubbed `buildArtifact` that sleeps 10 min; enqueue one job (`budgetMs: 600_000`); once `status='IN_PROGRESS'`, `kill -TERM <worker pid>`; start a new worker; poll `SELECT status, locked_by, locked_at, attempts, step FROM generations WHERE id=$1` every 30 s → stays `IN_PROGRESS` with the dead worker's `locked_by` for ~630 s, then flips to `QUEUED` and restarts from scratch.
- **Proposed fix:** (1) in `shutdown`, before exiting, release own jobs: `UPDATE generations SET status='QUEUED', locked_by=NULL, locked_at=NULL, run_after=now(), attempts=GREATEST(attempts-1,0), step='Qayta navbatga qo''yildi', live_json=NULL WHERE locked_by=$1 AND status='IN_PROGRESS'` (and abort in-flight runs via an `AbortController` passed to `buildArtifact`); (2) decouple liveness from budget: treat a job as dead when its heartbeat is older than a fixed ~60–90 s, and enforce the budget separately as a hard timeout inside `runJob` (`Promise.race` with the deadline + abort) — this also shortens crash recovery from ~11 min to ~1.5 min; (3) optionally `stop_grace_period: 30s` and let jobs within 25 s of completion finish.
- **Effort:** S (1), M (2)
- **Confidence:** high
- **Cross-ref:** DB-05, INFRA-02 (same SIGTERM/lease behaviour). SCALE-11 (no hard per-job limit) is the other half of fix (2).

### CONC-04 — `LiveReporter` promise chains have no rejection handler: one transient DB error during a slide job crashes the whole worker process (both in-flight jobs lost)
- **Severity:** P2
- **Location:** `lib/server/live.ts:113,116` (`this.assetQueue = this.assetQueue.then(() => this.swapImage(…))` → `putAssets` at :124/:140), `lib/server/live.ts:171-184` (`this.writeChain = this.writeChain.then(() => this.doFlush())` → `setLive` at :182), `lib/server/live.ts:205-214` (`stop()` awaits both chains and rethrows); `lib/server/worker.ts:304-307` (`finally { await live?.stop(); stop(); }`); no `process.on("unhandledRejection")` anywhere in the worker (`scripts/worker.ts`, `lib/server/worker.ts`) — related: OBS-01.
- **Evidence:** the promise returned by `.then(() => this.doFlush())` is stored in a field and nobody attaches a handler until the next event or `stop()`. If `setLive`/`putAssets` rejects (pool `connectionTimeoutMillis` 10 s exceeded, `statement_timeout`, Postgres restart → `terminating connection due to administrator command`, `ECONNRESET`), Node 22's default `--unhandled-rejections=throw` turns it into an uncaught exception at the end of the tick and the worker exits with code 1. (The web process is not affected — Next.js installs its own `unhandledRejection` logger, `node_modules/next/dist/server/lib/router-server.js:567`.) Every other DB call in the worker path is caught (`tick` catch + 5 s sleep, `heartbeat(...).catch(() => {})`, `onStage` `.catch`), so this is the path that turns a DB blip that the rest of the worker survives into a process crash: the slide job **and** the unrelated second job are orphaned to the lease (CONC-03, ~8–11 min) and re-run from zero. Secondary bug: if `live.stop()` rethrows in the `finally`, the next statement `stop()` (the `progressTicker` `clearInterval`) never runs, leaking a 2 s `setInterval` that issues an UPDATE forever.
- **Reproduction:** unit test in the `tests/live*.test.mts` style: make the `setLive` seam reject (`() => Promise.reject(new Error("db down"))`), register `process.once("unhandledRejection", spy)`, create `new LiveReporter("g","w")`, call `sink({ type: "plan", … })`, `await new Promise(r => setTimeout(r, 50))`, assert `spy` was not called — fails today. End-to-end: start a pro-slide job, `docker restart slaydx-postgres-1` while slides stream → `slaydx-worker-1` restarts (`docker inspect -f '{{.RestartCount}}'` increments).
- **Proposed fix:** terminate both chains with a handler: `this.writeChain = this.writeChain.then(() => this.doFlush()).catch((e) => { console.warn("[live] setLive", e); this.dirty = true; })` and the same `.catch` on `assetQueue`; make `stop()` never throw; in `runJob`'s `finally` clear the ticker first (`stop(); await live?.stop().catch(() => {})`); add a logging `unhandledRejection` handler in the worker as a safety net (OBS-01).
- **Effort:** S
- **Confidence:** high
- **Cross-ref:** OBS-01 (no global unhandled-rejection handler). This finding is the concrete trigger and the local fix.

### CONC-05 — Status transition and refund are separate transactions with no reconciliation: a crash or DB error between them loses the user's money permanently; one failed refund in housekeeping skips all remaining dead jobs
- **Severity:** P2
- **Location:** `lib/server/worker.ts:301-303` (`if (await failJob(…)) await refund(…)`), `:165-167` (same for unknown tool), `:258-295` (`completeJob` commits `COMPLETED`, then `refundPartial` for a short delivery in a new transaction — if it throws, the `catch` calls `failJob`, which no-ops on a COMPLETED row, so the partial refund is silently lost), `:326-334` (`reclaimStaleJobs()` commits `FAILED` for all dead jobs, then refunds them one by one inside the same `try`; a throw at id k skips k+1…n); `app/api/generations/[id]/route.ts:62-65` (`cancelGeneration` commits `REVOKED`, then `refund` in a new transaction); `lib/server/credits.ts:176-214` (`refundRatio` — own transaction).
- **Evidence:** every "give the money back" path is two commits: (1) `UPDATE generations SET status='FAILED'|'REVOKED'` and (2) `refundRatio` in a separate `transaction()`. If the process dies between them (worker crash CONC-04, OOM, SIGTERM exit timer) or `refund` throws (pool `connect` timeout 10 s under load, Postgres restart), the job is terminal and charged, and **no code path ever revisits it**: `reclaimStaleJobs` only looks at `IN_PROGRESS`, the worker's catch only runs once, and a retried `DELETE` sees `status <> 'QUEUED'` so `cancelGeneration` returns false and `deleteGeneration` then deletes the row — the refund becomes impossible. In `housekeeping` the refund loop has no per-item try/catch, so one failing refund (e.g. `FOR UPDATE` lock wait hitting `statement_timeout`, or the user row deleted) silently drops the refunds of every later dead job in that batch — and those ids are never returned by `reclaimStaleJobs` again.
- **Reproduction:** test with a scratch DB: enqueue 3 jobs, mark them `IN_PROGRESS` with `attempts=2` and old `locked_at`; stub `refund` to throw on the first call; run `housekeeping()`; assert all 3 users have a `refund` transaction — fails (0 of 3; the first throws, the loop aborts). Crash variant: `failJob` then `process.exit()` before `refund` → `SELECT … FROM generations g WHERE status='FAILED' AND NOT EXISTS (SELECT 1 FROM transactions WHERE kind='refund' AND reference=g.id::text) AND EXISTS (SELECT 1 FROM transactions WHERE kind='charge' AND reference=g.id::text)` returns the job forever.
- **Proposed fix:** do the status change and the refund in ONE transaction (`failJobAndRefund(client, …)`, `cancelAndRefund`, and per-row refund inside `reclaimStaleJobs`' transaction using a `refundRatioInTx(client, …)` variant). Add a reconciliation step to `housekeeping` that runs the query above (terminal + charged + no refund + `finished_at < now() - interval '2 min'`) and refunds each id (idempotent by reference), with a per-item try/catch.
- **Effort:** S
- **Confidence:** high
- **Cross-ref:** DB-04 (refund not in the status transaction), DB-10 (housekeeping fragility). Unique here: the lost `refundPartial` after COMPLETED and the per-item loop abort.

### CONC-06 — Job fencing token is the per-process worker id, and the losing run writes then deletes the file/assets unconditionally: a stale run can leave a COMPLETED, paid job with no file and broken images
- **Severity:** P2
- **Location:** `lib/server/worker.ts:47` (`WORKER_ID = pid-uuid8`, one per process, used as the only lock owner token); `lib/server/jobs.ts:263-322,405-473` (`setProgress`/`setLive`/`heartbeat`/`completeJob`/`failJob`/`setCost` guard only `locked_by = $2 AND status = 'IN_PROGRESS'`; the claim's `attempts` value in `ClaimedJob.attempts` is never used as a token); `lib/server/worker.ts:251-256` (`putGenerationFile` + `putAssets` **before** ownership is re-checked; `lib/server/storage.ts:42-50` is an unconditional UPSERT); `lib/server/worker.ts:265-272` (on lost lock: `deleteGenerationFile(job.id, job.userId)` + `deleteAssets(job.id)` — deletes whatever is there, including another attempt's result).

## Checked and OK
- **Charge atomicity / no double-spend:** `chargeInTx` locks the wallet with `SELECT … FROM users … FOR UPDATE` (`lib/server/credits.ts:38-46,99-116`) inside the same transaction as the `generations` INSERT (`lib/server/jobs.ts:159-193`). Under READ COMMITTED a concurrent second `POST /api/generations` blocks on the row lock and re-reads the already-debited wallet → 402; `CHECK (points/quota/balance >= 0)` (`001_init.sql:13-15`) is the backstop. Balance cannot go negative or be double-spent by double-click, two tabs or a scripted burst.
- **No double refund:** `transactions_ref_idx UNIQUE (kind, reference)` (`001_init.sql:130-131`) plus the status-transition predicates (`failJob`/`cancelGeneration`/`reclaimStaleJobs` only succeed once per job) mean at most one refund per job; a concurrent duplicate `refundRatio` errors on the unique index instead of crediting twice (loss-side risk is CONC-05).
- **Cancel vs claim / cancel vs complete:** `cancelGeneration … WHERE status='QUEUED'` (`jobs.ts:246-255`) vs `claimJob`'s `FOR UPDATE SKIP LOCKED` (`jobs.ts:351-367`): the row lock + predicate re-check lets exactly one win; `completeJob` requires `IN_PROGRESS`, so a cancelled job cannot be completed. A double `DELETE` refunds once (the second sees `REVOKED`). Deleting a running job is refused (`jobs.ts:234-243`).
- **Claim loop:** the claim is one atomic `UPDATE … WHERE id = (SELECT … FOR UPDATE SKIP LOCKED)`; `tick()` runs sequentially so the `running` counter has no race (`worker.ts:310-322`). With several worker processes `reclaimStaleJobs`' `UPDATE … RETURNING` hands each dead id to exactly one caller (`jobs.ts:493-520`).
- **Lock-owner guards** on `setProgress`/`setLive`/`heartbeat`/`setCost`/`completeJob`/`failJob` (`locked_by = $2 AND status = 'IN_PROGRESS'`) are correct against a *different* worker process (same-process ABA and the destructive cleanup are CONC-06).
- **Rate limiter:** increment + check is a single atomic `INSERT … ON CONFLICT (bucket, window_start) DO UPDATE SET hits = hits + 1 RETURNING hits` (`lib/server/ratelimit.ts:30-36`); no read-then-write race (fail-open is CONC-13).
- **Doc editing:** optimistic CAS lives in SQL (`… AND doc_version = $6`, `jobs.ts:559-583`); `commitDocOps` re-applies ops to the freshly loaded doc and returns 409 on mismatch (`slide-commit.ts:122-163`); polish and rewrite commit through the same CAS (`doc-polish.ts:401-468`, `commitPolishedDoc` `:378-399`, `article-rewrite.ts:307-366`), so an LLM result can never overwrite a manual edit made meanwhile; first-edit `doc_prev` is protected by `COALESCE` + CAS; restore is a single SQL `doc_json = doc_prev` (`jobs.ts:605-619`).
- **File version is monotonic:** `markFileVersion … WHERE file_version < $3` under `pg_advisory_xact_lock(hashtext(id))` (`slide-commit.ts:238-259`, `jobs.ts:627-641`) — a slower older render cannot replace a newer file (only the duplicate CPU is an issue, CONC-08).
- **No server-side debounce timers:** the rebuild debounce is client-side and auto-save was removed (`components/files/useDocEdit.ts:17-24`); nothing in-memory on the server depends on request timing, so multiple web replicas/restarts are safe; `ensureFreshFile` guarantees a fresh file on download.
- **Payments idempotency after completion:** a duplicate webhook arriving after the first commit is a no-op (`topUp` returns `false`, `credits.ts:229-236`); concurrent `CreateTransaction`/`Prepare` are serialized by `attachTransaction … FOR UPDATE` (`payments.ts:231-259`). In-flight overlap is CONC-02.
- **Auth one-time tokens:** OTP attempt counter and consumption under `FOR UPDATE` in one transaction (`lib/server/auth.ts:186-205`); Telegram login ticket consumed under `FOR UPDATE` (`lib/server/telegram.ts:185-194`); webhook updates de-duplicated atomically with `INSERT … ON CONFLICT DO NOTHING RETURNING` (`telegram.ts:227-228`).
- **Live progress ordering:** `setLive` calls are serialized through `writeChain`, `live_seq` is incremented in SQL, readers use `?since=` (`jobs.ts:213-232,287-308`, `live.ts:171-184`) — no lost or reordered live states (error handling is CONC-04).
- **No cross-job shared mutable state** in `lib/generation`: cost flows through per-call `onCost` closures (`index.ts:619`), the research cache is DB-backed, module-level `/g` regexes are used only with `replace`/`matchAll` or reset `lastIndex` (`essay/review.ts:162`); no runtime `process.env` mutation anywhere in `lib/`/`app/`.
- **No sync fs/exec on request paths** (only `existsSync` on binary paths in `pdf.ts`, `thumb.ts`, `template-upload.ts`); child processes use async `execFile` with timeouts.
- **Every outbound fetch has a timeout:** `research/http.ts` (10 s + `AbortSignal.any`), `llm.ts` AbortController timers, image providers `AbortSignal.timeout(budget)`, `telegram.ts` 15 s, `tts/*` `AbortSignal.timeout`, `slide-research.ts` HEAD `REDIRECT_MS` (scout note "research fetch has no timeout" is outdated).
- **Timeout races don't leak rejections:** the `Promise.race` wrappers in `article|teacher|work|games/*/polish.ts` put `.catch(() => null)` on the call and clear the timer in `finally`; `mapPool` uses `Promise.all`, which attaches handlers to every lane.
- **Fire-and-forget writes carry `.catch`** (`session.ts:231`, `storage.ts:82`, `worker.ts:108,115,185`); the web process also logs any unhandled rejection instead of crashing (`node_modules/next/dist/server/lib/router-server.js:567`).
- **UI double-click on submit:** the button is disabled while `loading` (`components/forms/ToolChrome.tsx:67`) and React flushes discrete-event updates synchronously; the remaining duplicate-charge windows are CONC-10 / FE-09.
- **libuv threadpool:** `UV_THREADPOOL_SIZE` is unset (default 4) and that is not the bottleneck: in `web` the pool serves temp-file fs calls of the PDF/thumb/template paths and `dns.lookup` for new outbound connections (undici keeps them alive); `crypto.createHash`/`randomBytes` calls are synchronous on the main thread; JSZip/pako are pure JS (no zlib); `sharp` runs only in the worker (`lib/generation/figures/png.ts`) and in `web` only for infographic polish (`doc-polish.ts renderPosterFile`). The contended resource is the single main thread (CONC-08, CONC-09, CONC-18) and child-process memory (CONC-01).
- **Lock ordering:** multi-table transactions lock `generations` before `generation_files`/`generation_assets` (rebuildFile, commitPolishedDoc, cascade delete); money transactions lock only the `users` row — no deadlock cycle found.
- **Scout correction:** `audit/scout/server.md` §9 says the worker on SIGTERM "finishes the current job, releases the lock" — it does neither (CONC-03).
- **Out-of-scope observation (hand-off to SEC):** `uploadSlideImage` (`lib/server/slide-image.ts:72`) and `uploadResumePhoto` (`lib/server/resume-photo-commit.ts`, `storeImage`) call `putAssetBytes(id, …)` **before** `commitDocOps` verifies ownership, so any logged-in user who knows another generation's UUID can insert asset rows into it (storage abuse only — not linked or readable, UUIDs are unguessable), and on a 409 the uploaded asset is orphaned.
