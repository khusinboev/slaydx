### SCALE-01 + BEA-07 + FE-05 — Global `/api/:path*` `Cache-Control: private, no-store` overrides the media routes' own caching
- **Verdict:** CONFIRMED
- **Final severity:** P1 — at target load (hundreds–2 000 active users, each Telegram Mini App open = a fresh document), every card/deck/figure image is re-read from Postgres `bytea` through the single web process on every view; the image path alone is estimated at a large fraction of that one core at steady target and saturates it in a 10× burst. Precondition: target-scale traffic; at today's volume it is only waste. (BEA-07 rated P2; the load math in SCALE-01 is sound in order of magnitude, the exact saturation point still needs the curl/load probe.)
- **Evidence:**
  - `next.config.ts:106-110` — `{ source: "/api/:path*", headers: [{ key: "Cache-Control", value: "private, no-store" }] }`.
  - Next 15.5.23 runtime: `node_modules/next/dist/server/lib/router-utils/resolve-routes.js:509-528` accumulates config headers into `resHeaders` (later rule for the same key overwrites earlier); `node_modules/next/dist/server/lib/router-server.js:329-331` `res.setHeader(key, resHeaders[key])` **before** the handler; route handlers (non-ISR) reach `node_modules/next/dist/build/templates/app-route.js:287` → `send-response.js:49-50` `if (headersWithMultipleValuesAllowed.includes(...) || !isHeaderPresent) res.appendHeader(...)` — `cache-control` is not in the multi-value list, so the route's value is silently dropped. Standalone `server.js` uses the same router-server path.
  - Routes that lose caching (all `force-dynamic`, all set their own header only on success): `app/api/generations/[id]/assets/[assetId]/route.ts:29` (`private, max-age=86400, immutable` — slide images, deck logo, custom-template backgrounds, image-tool images, resume photo, article/work/teacher/game figures, owner-side listening audio); `app/api/generations/[id]/thumb/route.ts:27` (`private, max-age=86400` — DOCX/PPTX card thumbs, ~15–25 KB); `app/api/uploads/photo/[assetId]/route.ts:25` (`private, max-age=86400`); `app/api/o/[token]/audio/[assetId]/route.ts:48` (`public, max-age=86400, immutable` — public listening-game clips, a class of students replays them). `…/file` and `?format=pdf` set `private, no-store` themselves — unchanged by design. The same override also drops these routes' own `Content-Security-Policy: default-src 'none'; sandbox` (known, `next.config.ts:116-118`).
  - Asset ids are content hashes (`lib/server/assets.ts:20-22` sha256[:24]; `lib/server/photo.ts:36-37` same), so `immutable` is correct for assets/photos/audio. The thumb id is a constant (`lib/server/thumb.ts:33` `THUMB_ASSET_ID`) and `lib/api-client.ts:319-321` builds `/api/generations/${id}/thumb` with no version.
  - Per request cost: `requireUser` → 1 session SELECT (`lib/server/session.ts:219`), `getAsset` → 1 JOIN SELECT returning the whole `bytea` (`lib/server/assets.ts:225-237`), node-pg text protocol → hex string 2× the size → `postgres-bytea` `Buffer.from(hex,'hex')` → `new Uint8Array(asset.bytes)` copy (`assets/[assetId]/route.ts:24`).
  - Per page view: home list renders every card (no pagination, `components/home/HomeFiles.tsx:78+`); each completed deck card is a `SlideCanvas` whose `<img>` has no `loading="lazy"` (`components/viewers/SlideCanvas.tsx:170-174`, via `components/home/FilePreview.tsx:126-163`) and loads the **full-size** first-slide image (Pexels `large2x` / 1K Gemini JPEG, ~0.3–0.9 MB). A user with 20 decks ⇒ ~20 bytea reads / ~6–18 MB per home load; opening a 10–21-image deck ⇒ 10–21 reads / ~5–19 MB (`docs/AUDIT-9.md:118`). DOCX/PPTX thumbs are lazy and small (`FilePreview.tsx:171-189`) — cheap per request but still 2 queries each, every load.
- **Duplicates / related:** BEA-07 and FE-05 are the same root cause (merge). Amplifies SCALE-08 / DB-06 (whole-bytea materialisation), SCALE-09 (single web process). Thumb staleness interacts with DB-14 / CONC-15 (thumb cache has no version key).
- **Fix scope:** `next.config.ts` (**SHARED**) — narrow the `/api/:path*` rule so it does not match the four media routes; `lib/api-client.ts` (`thumbUrl(id, fileVersion)` → `?v=`); `components/home/FilePreview.tsx` (pass `gen.fileVersion`; optional `loading="lazy"` on card images). Tests: `tests/csp-headers.test.mts` (or a new `tests/cache-headers.test.mts`).
- **Fix notes:** Prefer the auditors' option "negative lookahead" (e.g. `source: "/api/:path((?!generations/[^/]+/assets/|generations/[^/]+/thumb|uploads/photo/|o/[^/]+/audio/).*)"`) so the **route** decides, and it sets the long cache only on 200. Do NOT instead add later config rules that set `max-age … immutable` for those paths: config headers apply to every status, so a transient 404/401 on an asset URL would be cached by the browser for a day/year (broken image stuck). Option "set no-store in `json()/fail()`" is larger and misses routes that build `NextResponse`/`Response` directly. Thumb must get a version query (`fileVersion`) before it becomes cacheable, otherwise an edited deck/document shows the old card for 24 h (breaks "ko'rdim = oldim"); note polish paths that rewrite the file without bumping `file_version` (DB-14) would still be stale. ETag/304 is a nice-to-have, not required. Real card thumbnails (small JPEG of slide 1) are a separate M-size perf item, not part of the minimal fix.
- **Regression test:** pure, no Postgres — in `tests/csp-headers.test.mts` load `next.config.ts` `headers()`, compile each rule's `source` with Next's own `getPathMatch` (`next/dist/shared/lib/router/utils/path-match`), merge matching rules in order (last wins, as `resolve-routes.js:527`), and assert: effective `Cache-Control` is **undefined** for `/api/generations/<uuid>/assets/<hex24>`, `/api/generations/<uuid>/thumb`, `/api/uploads/photo/<hex24>`, `/api/o/<token>/audio/<hex24>`, and is still `private, no-store` for `/api/generations`, `/api/generations/<uuid>`, `/api/auth/session`. ### SCALE-02 + INFRA-03 — Generation capacity ~30–50 jobs/h vs target ~1 200–2 400 jobs/h; no admission control / backpressure
- **Verdict:** CONFIRMED (architecture item)
- **Final severity:** P1 — at the target load the queue grows without bound: every job is charged at enqueue and then waits hours with no ETA, no cap and no QUEUED timeout. Precondition: sustained demand above ~1 job/min (≈ a few % of 2 000 active users per hour); any Telegram-post burst reaches it.
- **Evidence:**
  - Supply: one worker container (`docker-compose.yml:100-156`), `WORKER_CONCURRENCY: ${WORKER_CONCURRENCY:-2}` (`:155`), `lib/server/env.ts:200` default 2; `lib/server/worker.ts:310-322` `tick()` claims only while `running < env.worker.concurrency`.
  - Service time (upper-bound budgets, `lib/generation/budget.ts`): slide `120 s + 11 s/slide` (`:61-62`) → 10 sl. 230 s, 20 sl. 340 s; pro-slide `150 s + 16 s/slide` (`:69-70`) → 30 sl. 630 s (comment `:64-66` estimates ~570 s real); coursework/referat/mustaqil ish `150+90+9 s/page` (`:121-123`, `:304-307`) → 45 p. 645 s (measured ~420 s, `:28-29`); translation `60 s + 2.5 s/1 000 chars` (`:87-88`) → 200 k chars 560 s; article `150+90+16 s/page` (`:102-104`); image 90 s, resume 150 s (`:36-44`); everything capped at `WORKER_JOB_TIMEOUT_MS` 660 s. Real times are ~60–70 % of budget per the measured comments ⇒ a plausible mix averages **~150–240 s**.
  - Arithmetic: 2 slots × 3 600 s ÷ 150–240 s = **30–48 jobs/h**. Demand: even 1 job per active user per hour at 2 000 active = 2 000 jobs/h (SCALE-02's 10–20 %/10 min = 1 200–2 400/h) ⇒ 25–80× supply. Little's law: slots = λ·S = 0.33–0.67/s × 150–240 s ≈ **50–160 concurrent slots**. Arithmetic re-checked, correct.
  - No backpressure: `app/api/generations/route.ts:29-51` goes validate → `priceFor` → `enqueueGeneration` (charge + insert in one tx, `lib/server/jobs.ts:159-193`) with only per-user limits `5/60 s` and `60/3600 s` (`route.ts:33-34`); no queue-depth check. `claimJob` is global FIFO `ORDER BY created_at` (`jobs.ts:360-366`). `reclaimStaleJobs` only touches `IN_PROGRESS` (`jobs.ts:495-517`) — a `QUEUED` row never expires. `queueDepth()` returns counts only (`jobs.ts:523-531`). New accounts get 3 000 free points (`lib/server/auth.ts:15`) = one immediate ≤20-slide deck/referat each.
  - **Multi-process safety (verified):** `claimJob` uses `FOR UPDATE SKIP LOCKED` (`jobs.ts:365`); every write after claim is fenced by `locked_by = $workerId AND status='IN_PROGRESS'` (`setLive :297`, `heartbeat :319`, `completeJob :424`, `failJob :468`, `setCost :454`); `WORKER_ID = pid + random uuid` (`worker.ts:47`) so identical container PIDs cannot collide; `reclaimStaleJobs` is one transaction of two `UPDATE … WHERE status='IN_PROGRESS'` — a concurrent second run re-evaluates the predicate and returns each dead id only once, so the refund loop (`worker.ts:326-334`) cannot double-refund; purges are idempotent; migrations take an advisory lock. No job-scoped module-level state in `lib/generation`/`lib/server` (only `thumb.ts` slot counter and the source-cache store). ⇒ `--scale worker=N` and a higher `WORKER_CONCURRENCY` are code-safe, with the caveats below.
- **Duplicates / related:** INFRA-03 = SCALE-02 (merged). Per-user fairness SCALE-05 = CONC-07; provider limiter SCALE-06; deploy kills in-flight jobs INFRA-02 = CONC-03 = DB-05; pool sizing DB-08 / SCALE-14; queue observability OBS-12; client 20-min give-up (FE/UX findings).
- **Fix scope:** (a) no-new-infra part: `app/api/generations/route.ts` (admission check before `enqueueGeneration`), `lib/server/jobs.ts` (`queueDepth` + oldest-queued age / queue position; QUEUED TTL + refund in `reclaimStaleJobs`), `lib/server/worker.ts` (refund of expired QUEUED rows in `housekeeping`), `lib/api-client.ts` + result UI (show 429/`Retry-After` and position/ETA); config: `docker-compose.yml` (**SHARED** — `WORKER_CONCURRENCY` value, pass `DATABASE_POOL_MAX` to both services, optional `stop_grace_period`) and `/opt/slaydx/.env` on the box. (b) design part: none in repo until decided.
- **Fix notes:** What works **without new infrastructure** (in order): (1) admission control — reject with 429 + `Retry-After` and an ETA **before charging** when `queued × meanService ÷ totalSlots` exceeds ~15 min (and cap per-user in-flight at ~2, SCALE-05); (2) QUEUED TTL (e.g. 30 min → FAILED + refund, in the same tx — see CONC-05/DB-04 for the refund-atomicity caveat); (3) raise `WORKER_CONCURRENCY` to ~6–8 on the existing container after measuring per-job peak RSS per tool (pro deck/translation are the heavy ones, SCALE-02's 100–400 MB estimate is unmeasured) — jobs are mostly LLM-I/O-bound, but some steps are CPU on the one worker event loop (crossword grid ≤20 s, `budget.ts:196-198`; pdf.js parse FILE-04) and will stall the other jobs' timers/heartbeats while they run; keep pool ≥ concurrency+4 (default pool 10; compose does not forward `DATABASE_POOL_MAX`, `connectionTimeoutMillis` 10 s turns pool starvation into job errors); (4) `--scale worker=2–3` is code-safe but each process adds a 10-connection pool (stock `max_connections=100`) and ~300 MB+ baseline (tsx + full devDeps, INFRA-12), and scale-in/deploy still kills in-flight jobs until INFRA-02 is fixed. Realistic ceiling on the shared box: ~10–20 slots ≈ 150–480 jobs/h — still 3–10× short of the target. **OWNER DECISION** needed for the rest: separate/bigger worker host (the VPS is shared with two other projects, no container limits — INFRA-04), provider quota tiers (Gemini/Anthropic RPM/TPM — 50–160 slots × `mapPool(3)` ≈ 150–500 concurrent LLM calls; SCALE-06 shows retries do not ride out 429), PgBouncer beyond ~8 processes, and whether the 3 000-point signup bonus should run at lower priority during overload (pricing/money policy).
- **Regression test:** (Postgres, scratch DB) `tests/admission.test.mts`: seed `QUEUED` rows until the estimated wait exceeds the threshold, call the `POST /api/generations` handler → assert 429 with `Retry-After`, **balance unchanged** and no new `generations` row (fails today: 202 + charge). Pure part: a `admissionDecision({queued, slots, meanServiceSec, limitSec})` function unit-tested for the boundary. `tests/jobs-queued-ttl.test.mts` (Postgres): a `QUEUED` row with `created_at = now()-31 min` → after `housekeeping()` it is `FAILED` and refunded exactly once, even when two `housekeeping()` calls run concurrently. Capacity itself: measure with SCALE-02's two prod SQL queries (read-only) — config, not unit-testable.
