### FE-03 — Viewer editor loses ALL unsaved edits on any save failure; >50 queued ops is rejected deterministically
- **Verdict:** CONFIRMED
- **Final severity:** P1. Losing work is certain once a user makes 51 or more edits between two saves. It hits every editable viewer (slide/pro-slide, resume, article/thesis, essay, coursework/referat/mustaqil-ish, 5 teacher tools), which is a core flow, and the UI gives no warning before the limit.
- **Evidence:**
  - Client queue has no cap and no coalescing: `components/files/useDocEdit.ts:387` `queueRef.current.push(...ops)`. Undo/redo also push their inverse ops (`:403`, `:411` → `push`).
  - The whole queue goes out in one PATCH: `:331` `patchGenerationDoc(genId, versionRef.current, ops)`.
  - Every error drops the queue: `:334-340` `catch (e) { setError(...); queueRef.current = []; setPending(0); await reload(); }`. There is no status discrimination; network (0), 400, 413, 429 and 5xx are all treated the same as 409.
  - The server rejects before any DB access: `lib/server/edit-adapters.ts:225` `MAX_EDIT_OPS = 50`, `:239-240` → `lib/server/slide-commit.ts:313-314` `throw new ApiError(pre.error, 400)`. The per-language parsers repeat the same cap: `slide-edit.ts:1022,1152`, `resume/edit.ts:450,503`, `article/edit.ts:46,792`, `work/edit.ts:43,684`, `teacher/edit.ts:88,1164`. The body cap is `DOC_PATCH_MAX_BYTES = 300*1024` (`slide-commit.ts:57,303`, 413).
  - Each committed field is ≥1 op (`ArticleEditor.tsx:632`, `ResumeEditor.tsx:69-195`, one op per action), so "51 edits without pressing Saqlash" is enough.
  - Secondary effects: (a) if `reload()` also fails (`useDocEdit.ts:285-287` swallows it), the unsaved optimistic doc stays on screen with `pending=0`. «Saqlash» and the `beforeunload` guard (`:266-276`) disappear, and a download returns the server file without those edits, breaking «ko'rdim = oldim». (b) A 413 shows «Fayl juda katta — 5 MB gacha rasm yuklang.» (`lib/api-edit.ts:42`), which is wrong for a PATCH. (c) A 429 shows «qaytadan urinib ko'ring» after the edits have already been discarded.
- **Is it deterministic for long sessions?** Yes. The existing UI tests never exercise it because the stub server in `tests/ui/slide-viewer-edit.test.mts:81-92` does not enforce the 50-op cap.
- **Duplicates / related:** FE-14 (no fetch timeout, so a hung PATCH blocks all later saves through `inflightRef`), FE-07 (a double-click on «Asliga qaytarish» discards the queue). No other auditor filed the op cap.
- **Fix scope:** `components/files/useDocEdit.ts` (main change); `lib/api-edit.ts` (413 text, and optionally export a retryable-error predicate); new pure `lib/generation/edit-limits.ts` exporting `MAX_EDIT_OPS`, imported by `lib/server/edit-adapters.ts` and the 5 op parsers (optional but prevents drift); tests below. No SHARED files.
- **Fix notes:** The auditor's 3-part fix is correct. Refinements:
  1. Chunk the queue into slices of ≤`MAX_EDIT_OPS`, sent sequentially. Each chunk uses the `docVersion` returned by the previous one, and `doRebuild()` runs once at the end. Chunks are applied in order, so replaying the ops unchanged is semantically identical.
  2. Remove only acknowledged ops from the queue: `queueRef.current = queueRef.current.slice(sent.length)`. Never clear the queue before the response arrives. Ops the user makes during the save are appended, so the current code's `queueRef.current = []` at `:323` must become "take a snapshot of N ops, and drop N on success".
  3. Discard the queue and reload only on 409 (`editErrorCode`) or 422. On 0/429/5xx/413, keep the queue and the undo stacks and show «Saqlanmadi — qayta urinib ko'ring».
  4. A partial success (chunk 1 committed, chunk 2 gets 409) is acceptable: reload shows what landed.
  5. Coalescing ops is optional and riskier, because inverse ops depend on order. Skip it.
  6. The per-user limit `edit:${user.id}` 120/min (`doc/route.ts:32`) easily covers chunked saves. Its comment still refers to the removed 400 ms autosave.
  No owner decision needed.
- **Regression test:** `tests/ui/slide-viewer-edit.test.mts`, using the existing `Harness`/`stubServer`. This is pure jsdom, with no Postgres.
  1. The stub returns `400` when `body.ops.length > 50` (mirroring `preParseOps`). The test runs 51 `text` ops through `hook.run`, then `await hook.save()`. It asserts every `s.patches[i].body.ops.length <= 50`, `s.doc` contains the 51st edit, and `hook.pending === 0`. It fails today: one 51-op PATCH gets 400 and the edits are lost.
  2. Set `s.failNext` to a 503 variant (extend the stub to return any status). After `save()`, assert `hook.pending === 1`, the edited title is still in `hook.doc`, and `hook.canUndo === true`. It fails today because pending becomes 0.
  3. PATCH returns 503 and GET rejects. Assert `hook.pending > 0` so that `beforeunload` is still armed.
  Keep the existing "409 → qayta yuklanadi" test unchanged: it must still pass. Mutation check: revert the status discrimination and test 2 must fail. Use `assert.ok(...)` only; never compare DOM nodes.

### FE-02 + UX-05 — Result page freezes silently when `pollGeneration` gives up
- **Verdict:** CONFIRMED, with one correction: not *every* 4xx causes a freeze (see triggers).
- **Final severity:** P1 at target load. When the queue wait passes 20 min (SCALE-02: capacity ≈30–48 jobs/h against 1 200–2 400/h demand), every user watching a job sees a frozen page and gets no message. The natural reaction is to submit again, which creates a new paid job. Without load it is P2: it needs a web or DB outage longer than ~30 s.
- **Evidence:**
  - The deadline is counted from page mount, not from job start: `lib/api-client.ts:373` `const deadline = Date.now() + 20 * 60_000`. It is checked only after a tick that is still running (`:400-404`, throws `ApiError(…,504)`).
  - Retry budget: `:390-393` retries only `status === 0 || >= 500` while `networkErrors < 5`, with waits of 2+4+6+8+10 s = 30 s. The 6th consecutive failure throws. Any other status throws at once (`:395`).
  - The error is set and then hidden: `components/files/ResultView.tsx:80-84` `setError(...)`. `:412` still renders `{running ? <RunningPanel gen={gen}/> : null}` because `gen.status` is frozen at QUEUED/IN_PROGRESS, and `:428` `{error && completed ? <p role="alert">…` never renders for a running job. `RunningPanel` (`:557-590`) has no error slot and still says «Sahifani yopsangiz ham ish davom etadi». For live slide decks, `SlideViewer` simply stops receiving slides.
- **Triggers, as verified:**
  1. **20 min on the page.** This is the main trigger at load.
  2. **Web/DB unavailable for more than ~30 s.** This covers nginx 502 during a `web` restart, DB pool exhaustion returning 5xx from `requireUser`, and the OOM restart (INFRA-04). It kills every open poll at once.
  3. **4xx:** only 404 (job deleted in another tab), 400 (unreachable) and a 429 that could only come from nginx `limit_req`. The app itself has no limit on `GET /api/generations/[id]` (`app/api/generations/[id]/route.ts:28-44`). **401 does *not* freeze the page:** `request()` calls `onUnauthorized` (`api-client.ts:72`) → `lib/store.ts:55-64` sets `loggedIn:false` → `ResultView.tsx:210-213` renders «Kirish talab qilinadi».
  If the failure happens before the first successful tick (`gen === null`), the user sees «Fayl topilmadi» with the error as hint, which is visible but misleading.
- **How common at target load:** the wait exceeds 20 min when more than roughly (20 min ÷ 2.5–4 min per job) × 2 slots ≈ 10–16 jobs are ahead in the FIFO. Per SCALE-02, a 10-minute burst leaves 200–400 queued jobs, so essentially every burst-time submitter freezes. Even a normal evening with ~15 queued jobs triggers it. The home list (`HomeFiles` 3 s interval) keeps updating, so only the result page freezes. Reloading the page restarts the 20-minute deadline, but nothing in the UI suggests reloading.
- **Duplicates / related:** UX-05 (the same bug, 20-min trigger only). FE-14 (a hung fetch freezes the page the same way with no throw). UX-07 (no queue position shown). SCALE-02/INFRA-03 are the capacity root cause; this finding is the UX amplifier. FE-06/CONC-10 cover the duplicate-charge consequence of resubmitting.
- **Fix scope:** `lib/api-client.ts` (`pollGeneration`); `components/files/ResultView.tsx` (error UI while running, plus a retry key). No SHARED files.
- **Fix notes:** The auditor's fix is correct and small. Minimal version:
  1. `pollGeneration`: after 20 min, switch to a slow cadence (30–60 s) instead of throwing. Treat 0/429/5xx as retryable with a capped back-off (≤30 s), with no hard stop, honouring `Retry-After`. Throw only on 404/400.
  2. `ResultView`: render `error` while `running` as a banner «Holat yangilanmay qoldi» with a «Qayta tekshirish» button that bumps a `pollKey` in the effect deps. Also change `:428` to `{error && !running …}` or render it in both places.
  Optionally resume immediately on `visibilitychange`/`online`. Do **not** simply delete the deadline without a slower cadence: 400 waiting tabs × 5 s polls is itself load (SCALE-02 math). No owner decision needed.
- **Regression test:**
  1. `tests/api-client-live.test.mts` (pure, `fetch` stub, fake `Date.now` via `t.mock.timers`): the stub always returns `{generation:{status:"QUEUED"}}`. Advance past 20 min and assert that `pollGeneration` has **not** rejected and keeps issuing requests at ≥30 s spacing. It fails today, because it rejects with 504.
  2. The same file: the stub returns 502 six times and then COMPLETED. Assert the promise resolves COMPLETED. It fails today, because it throws after the 6th 502.
  3. `tests/ui/` new `result-view-poll.test.mts` (jsdom): render `ResultView` with the store `sessionChecked/loggedIn`, and a `fetch` whose first GET returns QUEUED and whose later GETs return 404. Assert `screen.queryByRole("alert")` is truthy (`assert.ok`). It fails today because of the `completed` gate. Mutation check: restore the `completed` gate and test 3 must fail.

### SCALE-10 + ABUSE-05 + SECA-03 (+ BEA-15) — IP-keyed rate limits: NAT lockout, and trust in the XFF last hop
- **Verdict:** CONFIRMED-UPGRADE (login path → P1). The game-submit part stays P2. One correction to SCALE-10/BEA-15: the `tg:${ip}` Mini App scenario is **not reachable today**. `telegram-web-app.js` is never loaded and no widget exists (grep for `telegram-web-app|TelegramLoginWidget` returns 0; `LoginModal.tsx:77-88` never fires; this is FE-10). The live login path is ticket → bot → enter.
- **Final severity:** P1, on the precondition that during a Telegram-post burst more than 10 login starts per 5 min arrive from one carrier CGNAT egress IP. That is the burst the brief assumes, on Uzbek mobile networks where IPv4 CGNAT is the norm. New users then get 429 at the first step of the only production login flow, and keep getting it while the burst lasts, because others behind the same IP refill the window. Separately, **if prod `TRUST_PROXY` is effectively false, or nginx sets no XFF/X-Real-IP, every user shares one bucket.** The whole site would then be capped at 10 login starts per 5 min: a login outage (P0-class) at modest load. The owner must check this (see below).
- **Evidence (every limit keyed by client IP, from `grep -rn "limit(\`" app lib` plus `rateLimit(`/`clientIp`):**

  | Bucket | Limit / window | Where | Live in prod? | Notes |
  |---|---|---|---|---|
  | `ticket:new:${ip}` | **10 / 300 s** | `app/api/auth/telegram/ticket/route.ts:30` | **yes: step 1 of the only web login** | = 2 login starts/min per public IP; every «Telegram orqali kirish» click (including retries after expiry) creates a ticket |
  | `enter:${ip}` | 30 / 300 s | `app/api/auth/telegram/enter/route.ts:39-41` | yes (step 3, magic link) | checked **before** redeeming the 256-bit single-use token; failure shows `/uz/login?xato=Juda ko'p urinish` |
  | `tg:${ip}` | 20 / 300 s | `app/api/auth/telegram/route.ts:32-33` | UI path dead (FE-10); endpoint reachable by script | counted **before** signature verification and on success |
  | `o:submit:${ip}` | 30 / 60 s, **shared by all games** | `app/api/o/[token]/submit/route.ts:13,33-34` | yes (public `/o/[token]`, no login) | on 429 the Player keeps the answers and shows «Qayta yuborish» (`components/game/Player.tsx:98-102,238`), so it is recoverable |
  | `otp:ip:${ip}` / `otp:verify:ip:${ip}` | 15 / 600 s, 30 / 600 s | `app/api/auth/otp/route.ts:57,69` | **no**: prod returns 503 before the limits (`:38-43`, `devLoginEnabled`) | |

  All other `limit()` calls are keyed by `user.id` (the `gen`, `edit`, `draft`, `polish`… buckets), which is correct. `clientIp` (`lib/server/ratelimit.ts:78-95`): `!env.trustProxy → "direct"` (one global bucket). Otherwise the **last** XFF element, then `cf-connecting-ip`, then `x-real-ip`, then `"unknown"` (one global bucket). The windows are fixed and aligned to wall-clock time (`:27`).
- **Brute-force value of these IP limits is ~zero in prod.** OTP is disabled; the ticket nonce is 24 random bytes (`lib/server/telegram.ts:94`); the enter token is 32 bytes, hashed, single-use, 5-min TTL; initData/widget are HMAC-verified. There is no guessable secret, so the IP buckets only guard against DB/bot flooding. They can be raised a lot without weakening authentication.
- **Real-world impact (Uzbekistan):**
  - (a) *Telegram-post burst on mobile.* The ticket bucket breaks once the new logins per 5 min divided by the number of carrier egress IPs they land on exceeds 10. CGNAT pools typically put tens to hundreds of active subscribers behind one IPv4, so a burst of a few thousand logins in minutes concentrated on a few carriers will exceed this. Affected users see «Juda ko'p so'rov. N soniyadan keyin urinib ko'ring.», and those that retry consume more tickets.
  - (b) *School lab / classroom Wi-Fi* (one IP): the 11th student starting login within a window is blocked for up to 5 min.
  - (c) *Classroom game via `/o/[token]`*: a class of 35, or two classes on one school IP, finishing in the same minute: every submit after the 30th in that minute gets 429. The answers are kept and a retry after ≤60 s works, which is why this part is P2.
  - Fan-in can be measured without prod code changes: `SELECT ip_hash, count(DISTINCT user_id) FROM sessions WHERE created_at > now()-interval '30 days' GROUP BY 1 ORDER BY 2 DESC LIMIT 20;` (`sessions.ip_hash` = `hashIp(clientIp)`, `lib/server/session.ts:160-179`). **If this returns one hash for almost everyone, prod is in the global-bucket failure mode.**
- **XFF last-hop question:** yes, the last element is trustworthy, provided that (i) nginx terminates the client TCP connection (no CDN or other proxy in front), and (ii) *every* `location` that proxies to `127.0.0.1:3000` effectively has `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;`. nginx then sends `<client-supplied XFF>, $remote_addr`, so a client can only *prepend* values and `.pop()` returns `$remote_addr`. Setting `$remote_addr` directly is equally safe. **Owner must verify on the box:**
  1. `grep -n "proxy_set_header\|location\|real_ip" /etc/nginx/sites-available/slaydx`. Pitfall: a `location` that declares **any** `proxy_set_header` of its own (for example the §2a `location /api/generations/` block, or an Upgrade/Connection pair) does **not** inherit the server-level ones, so XFF can be silently missing on exactly those routes.
  2. Check whether Cloudflare/another proxy is in front. If so, `$remote_addr` is the CDN edge and all users share a few buckets; the fix is `set_real_ip_from <CDN ranges>; real_ip_header CF-Connecting-IP;`.
  3. `TRUST_PROXY` in `/opt/slaydx/.env`. `.env.example:36` ships `TRUST_PROXY=false`, and compose's `${TRUST_PROXY:-true}` (`docker-compose.yml:91`) takes the `.env` value if the file was copied from the example. `GET /api/health` reports `features.trustProxy` (`app/api/health/route.ts:74`).
  4. A spoof test: `for i in $(seq 12); do curl -s -o /dev/null -w "%{http_code} " -X POST -H "Origin: https://slaydxx.uz" -H "X-Forwarded-For: 10.9.8.$i" https://slaydxx.uz/api/auth/telegram/ticket; done`. The 11th and 12th must be 429; if all return 200, the header is spoofable. The test uses the tester's own bucket only.
  5. If the site has AAAA/IPv6, key on the /64. Otherwise a single IPv6 host can rotate addresses and bypass the limits.
- **Duplicates / related:** SCALE-10, BEA-15 (the NAT half) = ABUSE-05, SECA-03 (the XFF half) — one root: `clientIp` as the sole key. Also FE-10 (reviving the Mini App login activates `tg:${ip}`), UX-02/UX-01 (login funnel), UX-06 (submit dedupe), test-coverage `ratelimit.test.mts` gap.
- **Fix scope:** `app/api/auth/telegram/ticket/route.ts`, `app/api/auth/telegram/enter/route.ts`, `app/api/auth/telegram/route.ts`, `app/api/o/[token]/submit/route.ts`, `lib/server/ratelimit.ts` (`clientIp`: IPv6 /64 normalisation; drop the `cf-connecting-ip`/`x-real-ip` fallbacks unless configured; log a boot warning in prod when `trustProxy` is false), `lib/server/telegram.ts` (per-Telegram-id cap in the `/start <nonce>` handler), `.env.example` (SHARED-ish: set `TRUST_PROXY=true` with a comment), `.claude/deploy.md` (committed nginx snippet). - **Fix notes (proposed limits: identity first, IP only as a flood ceiling):**
  - **ticket:** `ticket:new:${ip}` **300 / 300 s**. Add a per-browser key: an httpOnly random `lt` cookie set on the first ticket, `ticket:c:${cookie}` 10 / 300 s. Add a per-identity cap where the identity first appears: the bot `/start <nonce>` handler, `tgstart:${from.id}` 10 / 300 s, which also stops bot-message spam to one account.

### FE-06 + CONC-10 — Duplicate paid job from re-click after enqueue, or retry after a post-commit 5xx/timeout (no idempotency key)
- **Verdict:** CONFIRMED
- **Final severity:** P2. The user is charged twice and gets two documents. The duplicate is refundable by deleting it while still QUEUED (`app/api/generations/[id]/route.ts:62-65`, `cancelGeneration` → `refund`), which is the common state at load (SCALE-02). Once it has started, the charge stands. That is real but bounded, user-recoverable money friction. It is not a P0 money loss (value is delivered) and not a P1 broken flow. It becomes much more frequent at target load: CONC-01/CONC-09 event-loop stalls, deploy 502s, and FE-02 resubmits.
- **Evidence:**
  - **Client window.** All 13 submit paths use `setLoading(true); try { const id = await runGeneration(...); router.push(...) } … finally { setLoading(false) }`. Examples: `components/forms/SlideComposer.tsx:175-185`, `ToolWorkspace.tsx:225-233`. `setLoading(false)` also appears at `ArticleComposer.tsx:391`, `MediaComposer.tsx:221`, `EssayComposer.tsx:282`, `teacher/TeacherComposer.tsx:186`, `TranslationForm.tsx:151`, `ImageStudio.tsx:77`, `InfographicComposer.tsx:152`, `ResumeComposer.tsx:280`, `GameComposer.tsx:305`, `WorkComposer.tsx:446`. The button's only guard is `disabled={disabled || loading}` (`ToolChrome.tsx:66`). A double-click *during* the POST is blocked, because React flushes `loading=true` before the next discrete event. The open window is *after* the 202: `router.push` returns immediately (transition) while the `/uz/files/[id]` RSC request is pending. `finally` re-enables «Yaratish · N tanga», so a second click sends a second POST. This window is certain; its length (sub-second normally, seconds under load) is the only uncertainty.
  - **Server.** No dedupe: `lib/server/jobs.ts:159-160` `const id = randomUUID()` per call becomes the charge `reference`. So the `alreadyCharged` idempotency in `lib/server/credits.ts:81-96` can never trigger. The only guard is `gen:burst:${user.id}` 5/60 s (`app/api/generations/route.ts:33`). CONC-10's post-commit failure path is also real: after the tx commits, a 502/504 or a dropped connection makes `request()` show «Server javob bermadi. Birozdan keyin urinib ko'ring.» (`lib/api-client.ts:77-79`), which invites a resubmit of an already-charged job.
- **Duplicates / related:** FE-06 (the client half) = CONC-10 (the server half; its cross-ref "FE-09" refers to an older numbering and means FE-06). Related: FE-02 (a frozen result page drives resubmits), FE-18 (price check on the same POST), UX-06 (the same idempotency pattern for game submits).
- **Fix scope:** `app/api/generations/route.ts` (read `Idempotency-Key`); `lib/server/jobs.ts` (`enqueueGeneration` accepts `id`); `lib/api-client.ts` (`createGeneration(slug, values, key)` sends the header); `components/forms/runGeneration.ts` (take the key); a shared `useSubmit` hook (new, e.g. `components/forms/shared/useSubmit.ts`) or 13 composer edits (`ToolWorkspace`, `SlideComposer`, `ResumeComposer`, `ArticleComposer`, `WorkComposer`, `EssayComposer`, `MediaComposer`, `GameComposer`, `InfographicComposer`, `ImageStudio`, `TranslationForm`, `teacher/TeacherComposer`). No migration: `generations.id` is already the PK and `transactions.reference` is already checked.
- **Fix notes:** The auditors' fix is right. Make it concrete and safe:
  - The client creates `key = crypto.randomUUID()` per *submit intent*, kept in a ref and regenerated only after an explicit error the user corrects, or when the form values change. It is sent as `Idempotency-Key`.
  - The server validates it as a UUID and uses it **as the generation id**. Inside the tx: `SELECT user_id, status FROM generations WHERE id=$1`. If it exists for the same user, return `{id}` with 202 and **no charge**. If it exists for another user, return 409. Otherwise charge with `reference = key` and insert. A PK race between two concurrent retries is settled by `INSERT … ON CONFLICT (id) DO NOTHING` plus the `alreadyCharged` branch, which is already idempotent by `reference`. Validate `values` equality loosely or not at all; the key is per intent.
  - Client: reset `loading` only in `catch`, and add a `submittedRef` so a second `submit()` after success is a no-op until navigation unmounts the form. That alone closes the FE-06 window.
  No owner decision needed.
- **Regression test:**
  1. `tests/ui/slide-composer.test.mts` (jsdom): mock `next/navigation` `useRouter().push` as a no-op (navigation pending), stub `POST /api/generations` → 202 `{id,price,status}`, click submit, await. Assert the submit button is still `disabled` (`assert.ok(btn.disabled)`), and that a second click sends no second POST (count fetch calls). It fails today.
  2. `tests/generations-idempotency.test.mts` (**needs Postgres**): call `enqueueGeneration` twice with the same `id`/key for the same user, and assert one `generations` row, one `transactions` charge and a wallet debited once. It fails today because the function mints its own UUID and does not accept an id. Mutation check: drop the existence check and the test must fail.
