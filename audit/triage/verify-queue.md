### BEB-02 + FILE-05 + SCALE-11 — Job deadline is advisory only; an overrunning job keeps its slot (it is NOT re-claimed while its process lives)
- **Verdict:** CONFIRMED-DOWNGRADE (BEB-02's "a second copy is requeued" and FILE-05's "re-claimed by a second worker" are wrong for the deployed topology; SCALE-11's reading is correct)
- **Final severity:** P2 — an overrunning job wastes a slot and provider spend, and in theory a hung job holds a slot forever. But every outbound call has its own timeout (per SCALE-11), and no hang path that never settles was found, so the load impact is bounded. Precondition: an engine step overruns `deadline`.
- **Evidence (what actually happens on overrun):**
  - `lib/server/worker.ts:189` `const deadline = Date.now() + jobDeadlineMs(job);` is a plain number (`jobDeadlineMs` = `max(30 s, budget − 15 s)`, `:137-139`). `buildArtifact(tool, job.values, { deadline, … })` (`:216`) is awaited with no `Promise.race`/`AbortController`. Engines only poll `remainingMs(deadline)` (`lib/generation/quality.ts:126-129`) between steps. The image tool gets no deadline at all (`lib/generation/index.ts` `buildImageArtifact(tool, values)`). **Nobody stops the job.** The engine stops itself at its next check, or finishes.
  - Lease: `progressTicker` (`worker.ts:104-116`) runs `setInterval(…, 2000)` for the whole of `runJob`. It calls `setProgress`/`heartbeat` (`lib/server/jobs.ts:269-274, 315-321`: `SET locked_at = now() WHERE id=$1 AND locked_by=$2 AND status='IN_PROGRESS'`). It is only cleared in `finally` (`worker.ts:304-307`). `LiveReporter.setLive` also bumps `locked_at` (`jobs.ts:296`).
  - Reaper: `reclaimStaleJobs` (`jobs.ts:492`) matches only `locked_at < now() - (budget_ms/1000 + 30 s)`. A job with a live event loop and a reachable DB therefore gets a fresh `locked_at` every 2 s and is **never** requeued, however far past its budget it runs. When it finishes, `completeJob` (`jobs.ts:424` `locked_by=$2`) still succeeds, so the user just gets a late result.
  - Slot: `running--` happens only in `runJob(...).finally` (`worker.ts:316-320`). The slot frees only when `buildArtifact` settles. A promise that never settles is a permanent slot leak: no refund, and it is invisible (INFRA-06). Two such jobs stop all generation until a restart.
  - Re-claim while alive: the deployed topology is ONE worker process (`docker-compose.yml`, where web sets `WORKER_INLINE: "false"`). The reaper lives in that same process, so a synchronous event-loop stall freezes the heartbeat and the reaper together. When the loop resumes, the 2 s heartbeat (one round-trip UPDATE) almost always commits before the 60 s-cadence reaper transaction (BEGIN + UPDATE). A re-claim of a live job needs either (a) two worker processes (scale-out, or `WORKER_INLINE` left at its default `true` — CONC-17) with a stall or partition longer than budget + 30 s in one of them, or (b) a DB outage longer than budget + 30 s that the run survives, followed by the reaper landing before the next heartbeat. Both are rare today; case (a) becomes realistic after scale-out. See CONC-06 for the damage when it happens.
- **Duplicates / related:** CONC-03/DB-05 fix (2) (separate liveness from budget), CONC-06 (consequence of a double run), CONC-17, INFRA-06, FILE-04 (a CPU-bound PDF parse in the worker is exactly the kind of stall that heartbeats cannot cover).
- **Fix scope:** `lib/server/worker.ts` (runJob: `AbortController` + hard timer at `jobDeadlineMs + grace`, stop the ticker, `failJob` + refund on expiry), `lib/generation/index.ts` (`BuildOptions.signal`), then the signal plumbed into `lib/generation/llm.ts`, `lib/generation/llm/chain.ts`, image providers (`image-provider-*.ts`), `lib/generation/research/http.ts`, `lib/generation/tts/*`. That is a large fan-out. Optionally `lib/server/jobs.ts` `reclaimStaleJobs` (fixed heartbeat age, for example 60–90 s, plus a separate `started_at + budget` hard limit). No shared files.
- **Fix notes:** The minimal fix is small: `Promise.race(buildArtifact, timeout(jobDeadlineMs + 30 s))` → `failJob` + refund → release the slot (`running--`). Keep a flag so the orphaned promise's later result is discarded. The orphaned run must NOT reach `putGenerationFile`/`deleteGenerationFile` (see CONC-06), so gate those on "not timed out". Full AbortSignal plumbing (BEB-02's proposal) is correct but L-effort. Do it incrementally, LLM `fetch` first because that is where the spend is. Note: a race does not stop CPU-bound work (pdf.js, regex). Only the worker_threads isolation (item 5 cluster) or a process kill does. Caution with BEB-02's "extend heartbeat semantics" wording: the heartbeat already prevents re-claim.
- **Regression test:** `tests/worker-deadline.test.mts` (needs Postgres, `tests/queue.test.mts` style). Register a stub tool whose `buildArtifact` awaits `new Promise(()=>{})` with `budgetMs: 1000` (min clamp permitting, or inject the deadline), run one `tick()`, and within 45 s assert: row `FAILED`, refund transaction exists, `running` is back to 0. Fails today (row stays `IN_PROGRESS` with a fresh `locked_at`; `reclaimStaleJobs()` returns `[]`). Pure unit variant: inject a fake clock into `runJob`'s race helper.

### CONC-06 (+ orchestrator note) — Fencing token is the process-wide WORKER_ID; the losing run writes, then deletes the file/assets by job id
- **Verdict:** CONFIRMED
- **Final severity:** P2 today, P1 once there are ≥2 worker processes. When it fires it is data loss on a paid job (COMPLETED, charged, no file, broken images, no refund). But with one worker process, the precondition (a live run losing its lease) is rare (see BEB-02 block). The documented scale-out (`npm run worker` in more containers, which is SCALE-02's likely fix) plus event-loop stalls in the worker (SECB-01 regexes / FILE-04 PDF parse on the translation path) make it reachable.
- **Evidence:**
  - `worker.ts:47` `WORKER_ID = \`${process.pid}-${randomUUID().slice(0,8)}\``, one per process. Every guard is only `locked_by=$2 AND status='IN_PROGRESS'` (`jobs.ts:272,297,319,424,454,468`). `ClaimedJob.attempts` (`jobs.ts:330,377`) is returned but never used as a token.
  - Order in `runJob`: `putGenerationFile` (`worker.ts:251`, an unconditional UPSERT, `storage.ts` `ON CONFLICT (generation_id) DO UPDATE SET bytes=…`), then `putAssets` (`:256`), then `completeJob` (`:258`). If that is `!won`: `deleteGenerationFile(job.id, job.userId)` + `deleteAssets(job.id)` (`:269-272`). `deleteAssets` is `DELETE FROM generation_assets WHERE generation_id = $1` (`assets.ts:241-243`), which removes **all** assets of the job, whichever run wrote them.
  - **Can a stale run delete a newer run's completed file? Yes:**
    - Two processes: W2's run R2 completes (file F2, assets A2, `doc_json` → A2). Then stale R1 (W1) finishes: it UPSERTs F1 over F2, `completeJob` fails, and it deletes the file row and every asset. The result is COMPLETED with no file (`GET …/file` → 404 "Fayl topilmadi", `ensureFreshFile` only rebuilds when `file_version < doc_version`, `slide-commit.ts:285-288`) and broken images. If R1 instead finishes *before* R2 completes, R1 still wipes assets R2 wrote mid-run (listening-game TTS via `putAssetBytes`, referenced by id in R2's doc). Slide images survive because R2's final `extractAssets` re-inserts them from `data:` URLs.
    - Same process (ABA): after a reclaim, W1 can re-claim its own job (`attempts=2`) while R1 is alive. Both runs then carry `locked_by=W1`, so R1's heartbeats and `completeJob` succeed against R2's claim. Whichever run finishes second deterministically deletes the winner's file and all assets, unless the loser throws first (then `failJob` returns false: no damage, no refund).
  - **Likelihood today:** requires a live run to miss heartbeats for ≥ budget + 30 s (≥ 120 s) *and* the reaper to run before the next heartbeat. With one process that needs a DB outage longer than 2 min that the run survives (but a DB error in a slide job likely crashes the worker first, CONC-04), with the reaper then landing inside the ≈2 s window before the next heartbeat. Rough estimate: well under 1 per month. With 2+ processes, any stall longer than budget + 30 s in one process is sufficient.
- **Duplicates / related:** BEB-02/FILE-05/SCALE-11 (same lease model), BEB-01 (same "file stored before `completeJob`, cleanup only on one branch" ordering flaw: its catch branch leaves a FAILED job's file downloadable), CONC-03/DB-05/INFRA-02 (lease release on shutdown must use the same token), SECB-03 (asset insert before ownership check, same "write first, check later" pattern).
- **Fix scope:** `lib/server/jobs.ts` (claim sets a token; every worker-side UPDATE adds `AND attempts=$n`, or better a new `claim_token uuid` column), `lib/server/worker.ts` (pass the token; remove the post-hoc delete; write file + assets + COMPLETED in one transaction), `lib/server/storage.ts` / `lib/server/assets.ts` (accept a `PoolClient`; `putGenerationFile` already does), `lib/server/live.ts` (`setLive` token). **SHARED:** a new migration `lib/server/migrations/0NN_claim_token.sql` if a column is added. Using `attempts` needs no migration.
- **Fix notes:** The auditor's fix is correct. Minimal version: (1) add `AND attempts = $3` to `setProgress/heartbeat/setLive/setCost/completeJob/failJob` (no migration; attempts increments on every claim, so it is a valid fencing token); (2) do `putGenerationFile` + `putAssets` + the COMPLETED update inside one `transaction()` that first runs `SELECT … FOR UPDATE WHERE id=$1 AND locked_by=$2 AND attempts=$3 AND status='IN_PROGRESS'` and rolls back if the row is gone; (3) delete the `!won` cleanup branch. This also fixes BEB-01's "file stored, then completeJob throws" (rollback removes the file) — coordinate the two. Asset-per-run pitfall: TTS assets written mid-run (`putAssetBytes`) are outside that transaction. Leave them; they are content-addressed and harmless once the destructive `deleteAssets` is gone.
- **Regression test:** `tests/queue-fencing.test.mts` (needs Postgres). Enqueue J; `claimJob("W")` → token 1; force `locked_at = now() - interval '1 hour'`; `reclaimStaleJobs()`; `claimJob("W")` → token 2; complete with token 2 (file F2 + one asset). Then drive the stale path with token 1 (`completeJob`/commit helper). Assert: token-1 commit returns false, `generation_files` still holds F2's bytes, asset count unchanged, status COMPLETED. Today it fails: the token-1 `completeJob` succeeds (same `locked_by`), or the loser's cleanup deletes F2.

### CONC-07 + SCALE-05 — Global FIFO claim, no per-user in-flight cap: one account can hold both worker slots
- **Verdict:** CONFIRMED (CONC-07 P1 kept; SCALE-05's P2 raised to match)
- **Final severity:** P1 — at the target load a single paying (or bonus-funded) account can push every other user's wait past the client's 20-min polling cutoff (UX-05). Not P0: it costs the attacker real money for every job that runs, and victims are delayed, not refused. Precondition: an authenticated account with credits.
- **Evidence:**
  - `lib/server/jobs.ts:360-366`: `SELECT id FROM generations WHERE status='QUEUED' AND run_after <= now() ORDER BY created_at LIMIT 1 FOR UPDATE SKIP LOCKED` has no user predicate.
  - `lib/server/worker.ts:311` `if (running >= env.worker.concurrency) return true;` with `WORKER_CONCURRENCY` defaulting to 2 (`docker-compose.yml`), one worker container.
  - Enqueue limits (`app/api/generations/route.ts:33-34`): `limit(gen:burst, 5, 60)` and `limit(gen:hour, 60, 3600)`. Both are **fixed windows** (`lib/server/ratelimit.ts`: `windowStart = floor(now/window)*window`), so 10 jobs can land within about 1 s across a minute boundary. They also fail open on DB errors (CONC-13). There is no count of the user's QUEUED/IN_PROGRESS rows in `enqueueGeneration` (`jobs.ts:159-193`).
- **Quantification** (budgets from `lib/generation/budget.ts`):
  - Budgets: `MIN_BUDGET_MS` 90 s; 2 000-tanga tools (games, image, 1-page essay) 90–340 s (e.g. listening `160 000 + 20×9 000`); coursework 45 pages ≈ 645 s; pro-slide 30 ≈ 630 s; capped at 660 s. Budgets are upper bounds, and live measurements in the file comments put real runtimes around 40–420 s, so take ≈ 3–4 min as typical.
  - Platform capacity is 2 slots ≈ 30–40 jobs/h. One account may enqueue 60/h, i.e. **1.5–2× the whole platform's capacity**.
  - Burst example: 10 jobs in ~1 s × ~4 min ÷ 2 slots ≈ **20 min** of head-of-line blocking for everyone who submits after them. 10 maximum-size courseworks (~7–10 min each) ≈ 35–50 min.
  - Sustained: 60 cheap 2 000-tanga jobs/h ≈ 120 000 so'm/h (1 tanga = 1 so'm, `payments.ts:115`) ≈ US$9–10/h. The backlog grows by ≥ 30–60 min per hour, and every later job waits behind it. With 2 accounts it doubles. Each new Telegram account's `SIGNUP_BONUS_POINTS = 3000` (`auth.ts:15`) buys one free 2 000-tanga job.
  - Cancelling a QUEUED job refunds in full (`app/api/generations/[id]/route.ts:62-64`), so queue-stuffing that never runs costs nothing (it only matters once claimed).
  - Honest version: one teacher generating a test per class (10–20 jobs) delays everyone else by 20–40 min.
- **Duplicates / related:** SCALE-05 (same finding — merge), INFRA-03/SCALE-02 (overall capacity and no backpressure, the larger root problem), UX-05 (20-min client cutoff), UX-07 (no queue position), CONC-13 (limiter fails open).
- **Fix scope:** `lib/server/jobs.ts` (`claimJob` per-user in-flight cap; `enqueueGeneration` cap on queued rows per user, counted inside the existing transaction after `chargeInTx`'s `users … FOR UPDATE`), `app/api/generations/route.ts` (map the new result to 429), `lib/server/env.ts` (**SHARED**, optional `WORKER_PER_USER_CAP`/`QUEUE_PER_USER_MAX`), **SHARED** migration for a partial index `ON generations(user_id) WHERE status IN ('QUEUED','IN_PROGRESS')` (recommended; the claim subquery runs every 150 ms under load).
- **Fix notes:** Both auditors' fixes are correct. Minimal version: claim filter `AND NOT EXISTS (SELECT 1 FROM generations r WHERE r.user_id=g.user_id AND r.status='IN_PROGRESS')`. This is a soft cap (two concurrent claims can exceed it by one, which is fine with `SKIP LOCKED`). Add an enqueue cap of about 3 QUEUED+IN_PROGRESS per user. Pitfalls: (1) move the `FOR UPDATE SKIP LOCKED` subquery to alias `g` so the correlated predicate is on the right row; (2) the cap must not starve a user's second job forever when it is the only job in the queue (a cap of 1 running is fine, since the slot simply stays free for others); (3) the enqueue cap must count before charging, or the user gets a 429 after being charged. **OWNER DECISION:** cap values, and whether pro/paying plans get a higher cap or priority.
- **Regression test:** `tests/queue-fairness.test.mts` (needs Postgres). Insert 5 QUEUED rows for user A (older `created_at`), then 1 for B. `claimJob("w")` twice; assert the second claim returns B's job. Plus: with 3 queued rows for A, `enqueueGeneration` for A returns `{ok:false, reason:"busy"}` and A's balance is unchanged. Fails today (both claims return A's rows; the enqueue succeeds).

### INFRA-02 + CONC-03 + DB-05 — Worker SIGTERM exits after 2 s and abandons in-flight jobs to a budget-sized lease on every deploy
- **Verdict:** CONFIRMED-DOWNGRADE (P1 → P2; CONC-03 and DB-05 already rate it P2)
- **Final severity:** P2 — every deploy (`deploy.sh` runs `docker compose -p slaydx build && up -d`, per `.claude/deploy.md`, which recreates the worker) abandons up to 2 in-flight jobs. They freeze for 2–12.5 min, are re-run from scratch (provider cost paid twice), and fail with a refund if interrupted twice. That is degraded UX plus waste on a rare-per-user path, with no money or data loss for the user. The one exception (first attempt frozen near 12.5 min + a re-run up to 11 min overruns the 20-min client poll) is covered by UX-05.
- **Evidence:**
  - Shutdown: `lib/server/worker.ts:409-415` `shutdown = () => { stopWorker(); setTimeout(() => process.exit(0), 2000); }`. `stopWorker` only sets `stopped = true` (`:403-405`). In-flight `runJob`s were started fire-and-forget (`void runJob(job)`, `:316`) and are neither awaited, aborted nor released.
  - Signal delivery is real: the container's PID 1 is `tsx` (`Dockerfile` worker `CMD ["./node_modules/.bin/tsx", …, "scripts/worker.ts"]`). tsx 4.23.12's `relaySignals` forwards SIGTERM to the child, and its preflight reports receipt back, so the parent does not SIGKILL. The child runs `shutdown`, exits 0 after 2 s, and the parent follows (`D.on("close", … process.exit(l))` in `node_modules/tsx/dist/cli.mjs`). Compose has no `stop_grace_period` for `worker` (Docker default 10 s), so the app's 2 s timer is what fires.
  - After exit: the row stays `IN_PROGRESS`, `locked_by` = the dead `WORKER_ID`, `locked_at` = the last heartbeat (≤ 2 s old). The new process has a new `WORKER_ID` (`:47`) and its reaper requeues only when `locked_at < now() - (budget_ms/1000 + 30 s)` (`jobs.ts:492`), with housekeeping every ≈ 60 s of accumulated loop waits (`worker.ts:50,383-387`). So the job freezes for **budget + 30 s … budget + 90 s**: 2–2.5 min for 90 s jobs, up to ≈ 11.5–12.5 min at the 660 s cap.
  - Then `status='QUEUED', run_after = now()+5 s, step='Qayta navbatga qo''yildi', live_json=NULL` (`jobs.ts:496-503`). The re-claim sets `attempts=2`, `progress=5`, `step='Boshlandi'` (`:351-359`) and runs from zero.
  - A second interruption: `attempts >= 2` → `FAILED 'Ish vaqti tugadi'` + `refund` in housekeeping (`jobs.ts:507-518`, `worker.ts:326-334`; BEB-04 race applies).
  - **What the user sees:** a progress bar frozen at its last value (the fake curve or the live deck), then a jump back to 5 % "Qayta navbatga qo'yildi" → "Boshlandi", then a normal run. Total can reach ≈ 12.5 + 11 min, beyond the client's `20 * 60_000` poll deadline (`lib/api-client.ts:373`), after which UX-05 hides the message and the bar freezes for good even though the job later completes.
  - Side effects: the abandoned run's mid-run assets (LiveReporter/TTS) stay as orphans (harmless, content-addressed). The abandoned run's provider spend is lost.
  - Frequency: with 2 slots permanently busy at target load, **every** deploy hits 2 jobs.
- **Duplicates / related:** CONC-03, DB-05 (same root cause — merge into one cluster), BEB-03/CONC-04 (worker crashes produce the same abandonment), BEB-02/SCALE-11 (liveness vs budget), CONC-06 (the release UPDATE must respect the fencing token), UX-05, INFRA-06.
- **Fix scope:** `lib/server/worker.ts` (`shutdown`: stop claiming; wait for `running === 0` up to ~20 s; then release own jobs with `UPDATE generations SET status='QUEUED', locked_by=NULL, locked_at=NULL, run_after=now(), attempts=GREATEST(attempts-1,0), step=…, live_json=NULL WHERE locked_by=$1 AND status='IN_PROGRESS'`, then exit), `lib/server/jobs.ts` (the `releaseOwnJobs(workerId)` helper; optionally the fixed-age stale test from DB-05), **SHARED** `docker-compose.yml` (`stop_grace_period: 30s` on `worker`, longer than the in-app wait).
- **Fix notes:** Releasing the lease is the real win: the new container claims within ≈ 1.5 s instead of budget + 30–90 s. Pitfalls:
  - (1) The still-running `runJob` in the dying process may reach `completeJob` after the release. It fails (`locked_by` NULL) and then runs the destructive `deleteGenerationFile/deleteAssets` cleanup. Harmless only because compose stops the old container before starting the new one. Fix CONC-06 first or skip that cleanup when `stopped`.
  - (2) Waiting for whole jobs is not viable (up to 11 min). Wait briefly, then release.
  - (3) Decrementing `attempts` means deploy interruptions never exhaust retries. **OWNER DECISION:** whether a deploy should count as an attempt.
  - (4) Also abort in-flight LLM calls (AbortController from the BEB-02 fix) so abandoned provider spend stops.
  - Nice-to-have: also switch the reaper's stale test to a fixed heartbeat age (≈ 60–90 s), so crashes (not only clean SIGTERMs) recover in ~1.5 min.
- **Regression test:** `tests/worker-shutdown.test.mts` (needs Postgres). Claim a job as worker id `W` (stub build that never resolves), call the exported release helper, and assert the row is `QUEUED`, `locked_by IS NULL`, `run_after <= now()`, and `attempts` unchanged from before the claim. A pure unit check can assert `runWorkerProcess`'s shutdown calls the release before `process.exit` (inject `exit`). Plus `tests/compose-env.test.mts`-style assertion that `worker.stop_grace_period` is set. Fails today (no helper; the row stays `IN_PROGRESS`).

### CONC-09 + SECB-04 + FILE-04 — Uploaded PDFs are parsed on the web event loop (pdf.js "fake worker"), with no page cap or timeout, and the upload path grows super-linearly
- **Verdict:** CONFIRMED-UPGRADE (measured). CONC-09 P1 → **P0**; SECB-04 and FILE-04 (P2) merged in.
- **Final severity:** P0 — one ordinary authenticated request (free, `source:` 20 per 10 min) with an **841 KB** PDF froze the event loop of the process parsing it for **28.2 s continuously**. In prod that is the single `web` process, which serves every page, poll, login and payment/Telegram webhook. The cost grows super-linearly with page count, and the 20 MB cap allows far larger inputs. Precondition: a Telegram-login account (free). Same class as SECB-01 (confirmed P0).
- **Probe (the one allowed run):** `scripts/heavy.sh -m 1G -t 120 ./node_modules/.bin/tsx scratchpad/probes/pdf-eventloop.mts`. It generates a plain textbook-like PDF (Helvetica, 55 lines × ~85 chars per page, Flate, no sentence punctuation), then calls the **real** functions: `extractSegments("pdf", …)` (the `/api/uploads/source` path via `DEFAULT_COUNTER`) and `extractFromBuffer("x.pdf", …)` (the `/api/extract` path). A 10 ms `setInterval` ticker records the longest gap.

  | pages (bytes) | upload path total / longest block | `/api/extract` total / longest block |
  |---|---|---|
  | 50 (70 KB) | 384 ms / 144 ms | 113 ms / 103 ms |
  | 200 (280 KB) | 2 984 ms / 2 586 ms | 391 ms / 364 ms |
  | 600 (841 KB) | **29 438 ms / 28 211 ms** (96 % one block) | 1 081 ms / 987 ms (91 %) |

  (a) CONC-09's mechanism holds: the timer got ≤ 3 ticks during an unpdf parse, so the whole parse is effectively one uninterrupted stretch of the event loop. This matches `LoopbackPort.postMessage` → `this.#t.then(…)` with `#t = Promise.resolve()` and the evaluator's `next(Cr)` time-slot "yield", both microtasks, in `node_modules/unpdf/dist/pdfjs.mjs`.
  (b) `/api/extract` is roughly linear (~1.8 ms per page, fully blocking). A 20 MB PDF of this density (~14 000 pages) ≈ 25 s of freeze.
  (c) The upload path is **super-linear**: 3× the pages gave ~10× the time. The loop in `toBlocks` (`lib/generation/translate/pdf.ts:199-214`) keeps extending one paragraph string (`text += " " + next.text`, `:213`) and re-tests it with `/[-­]$/.test(text)` (`:212`) on every line. Each test flattens and scans the whole growing string, so the cost is O(total chars²) whenever lines are not split into paragraphs (probe: `segs=1`). No split happens when there is no sentence-final punctuation, indentation or font change, which any attacker can produce and some real documents (verse, all-caps, lists without markers) partly produce. Extrapolated: 1 200 pages ≈ 2 min; the 20 MB cap allows hours. FILE-04's suspected quadratic, `toLines` `out.find`, is per page and small for normal pages; the measured blow-up is in `toBlocks`. FILE-04's per-page `out.find` quadratic remains a secondary risk on pages crafted with many items.
  (d) All limits run *after* the parse: `chars > TRANSLATION_MAX_CHARS` (200 000, `lib/tools.ts:1103`) is checked at `source-upload.ts` only after `DEFAULT_COUNTER`. The probe's 600-page file was 2.9 M chars, so it would have been rejected with 422 only after freezing the site for 28 s.
- **Evidence (call path):** `app/api/uploads/source/route.ts` (`maxDuration = 60`, which does nothing under `next start`) → `uploadSource` → `DEFAULT_COUNTER` (`lib/server/source-upload.ts`) → `extractSegments` → `extractPdf` → `pdfToBlocks` (`translate/pdf.ts:217-262`: `for (let n = 1; n <= pages; n++) { await doc.getPage(n); … await page.getTextContent() }`, no page cap, no timeout). The second pass `pdfPages()` only runs if `extracted.pdf.pages` is missing, and `extractPdf` sets it, so there is no double parse today. `/api/extract` → `extractFromBuffer` → `extractPdfBuffer` (`lib/extract-text.ts:133-142`, `unpdf.extractText(…, {mergePages:true})`, all pages). The worker re-parses the file for translation jobs, but only files that passed the 200 000-char upload gate, so that path is bounded.
- **Duplicates / related:** SECB-01 (same web-event-loop parsing, regex variant, P0), SECB-02/FILE-02 (same entry points, memory variant), FILE-05 (`maxDuration` inert), SCALE-04/SCALE-09 (single web event loop), SECB-05 (size pre-check bypass).
- **Fix scope — one "user-file parsing isolation" cluster covering SECB-01 + this + SECB-02/FILE-02:**
  - New `lib/server/parse-pool.ts`: a `worker_threads` pool of 1–2 threads, each job run with a hard wall-clock timeout (`worker.terminate()` on expiry), `resourceLimits: { maxOldGenerationSizeMb: ~512, maxYoungGenerationSizeMb, stackSizeMb }`, and a small bounded queue that returns 503 when full.
  - New `lib/server/parse-worker.ts` (thread entry) dispatching `extractFromBuffer`, `extractSegments`, `parsePptxTemplate`.
  - Call sites switch to the pool: `app/api/extract/route.ts`, `lib/server/source-upload.ts` (`DEFAULT_COUNTER`, `pdfPages`), `lib/server/template-upload.ts` (`parsePptxTemplate`; `renderLayoutSheet` too if it stays in web).

### SECB-02 + FILE-02 — The ZIP inflate budget trusts archive metadata; `parsePptxTemplate` has no budget at all
- **Verdict:** CONFIRMED (SECB-02's P1 holds; FILE-02's P2 is too low). One correction to SECB-02's memory reasoning, below.
- **Final severity:** P1 — one authenticated upload (`/api/extract` ≤ 8 MB, 20 per 5 min; `/api/uploads/source` ≤ 20 MB, 20 per 10 min; `/api/uploads/template` ≤ 20 MB, 5 per 10 min) can drive the single web process's V8 heap to its limit. From source reading the outcome is a heap-exhaustion abort and container restart, which would make it P0 like SECB-01 and item 5. Kept at P1 only because it is not measured: **orchestrator check** — run SECB-02's bounded fixture test with a small `--max-old-space-size`, and upgrade to P0 if the process aborts instead of rejecting. Precondition: a free Telegram-login account.
- **Evidence:**
  - Budgeted readers check the *declared* size, inflate fully, then count: `lib/extract-text.ts:89-97` (`readEntry`) and `lib/generation/translate/xml-scan.ts:241-248` (`openOoxml`), both `if (declared > budget) throw; const text = await file.async("string"); budget -= text.length`. `declared` is `_data.uncompressedSize`, read from the archive's own central directory.
  - `lib/generation/pptx-template.ts:199-247` `parsePptxTemplate` calls `zip.file(p)?.async("string")` on `presentation.xml`, its rels, the master, master rels, theme and **every** layout named in the rels (the count is also unbounded), with no size check at all. It is reached from `lib/server/template-upload.ts` `uploadTemplate` in the web process.
  - JSZip 3.10.1 internals:
    - `async("string")` → `internalStream` (`lib/zipObject.js:39-66`) pipes loaded (binary) entries through `Utf8DecodeWorker`, and each chunk becomes a JS string via `Buffer#toString("utf-8")` (`lib/utf8.js:184-187`).
    - `accumulate` (`lib/stream/StreamHelper.js:79-107`) pushes every chunk into `dataArray` and only joins on `"end"` (`case "string": return dataArray.join("")`).
    - The actual-vs-declared length check fires only in the `"end"` handler (`lib/compressedObject.js:36-38`, "uncompressed data size mismatch"), after everything has been inflated and retained.
    - `DataWorker` yields between 16 KB *compressed* blocks via `setImmediate` (`lib/stream/DataWorker.js:8,59`; `utils.delay`), so memory grows block by block with nothing checking it.
  - **Correction to SECB-02:** for these call sites the retained data is **on the V8 heap** (decoded string chunks), not external `ArrayBuffer` memory. Growth is therefore bounded by the process heap limit (Node 22 default depends on host RAM; 2 096 MB on this 14 GB laptop), not by host RAM. A few MB of highly compressible DEFLATE data can exceed that. This matters for the fix: a `worker_threads` `resourceLimits.maxOldGenerationSizeMb` **does** contain this failure (the thread dies with `ERR_WORKER_OUT_OF_MEMORY` and the main thread survives), whereas `--max-old-space-size` on the main process only decides when the whole server dies.
  - FILE-02's "multiple copies held at once" is also right: in `openOoxml` the compressed archive, the `parts` map and later the re-generated output coexist. That path runs in the worker for translation jobs, but only after the web upload path (`extractSegments` → `extractDocx/Pptx/Xlsx` → `openOoxml`) has already inflated the same archive.
- **Duplicates / related:** item-5 cluster (CONC-09/SECB-04/FILE-04), SECB-01 (same entry points), SECB-05 (Content-Length pre-check bypass lets a larger body through), INFRA-04 (no `mem_limit` on `web`; with a container memory limit the effect is still a restart, just contained to this project), BEB-03 (the worker's `openOoxml` path has the same issue and no crash handler).
- **Fix scope:** the same isolation cluster as item 5 (new `lib/server/parse-pool.ts` + `lib/server/parse-worker.ts`; call-site changes in `app/api/extract/route.ts`, `lib/server/source-upload.ts`, `lib/server/template-upload.ts`; **SHARED** `next.config.ts`/`Dockerfile` for tracing the thread entry). Plus the in-library guard: new shared helper `readZipEntryCapped(zip, name, budget)` (e.g. in `lib/generation/translate/xml-scan.ts`, exported) used by `lib/extract-text.ts` `readEntry`, `xml-scan.ts` `openOoxml`, `lib/generation/pptx-template.ts` (all reads, with a total budget of e.g. 40 MB and a layout-count cap), and `lib/generation/render-pptx-template.ts` (`:151-158` reads of the user template in the worker). An entry-count cap before iterating `zip.files`. No `package.json` change unless switching to `fflate`.
- **Fix notes:** SECB-02's fix is correct and minimal. The capped reader should consume `file.internalStream("uint8array")` and count bytes in the `on("data")` handler, calling `.pause()` and rejecting once the running total passes the budget, then decode the kept bytes once with `TextDecoder`. That bounds memory at the budget regardless of metadata. Keep the declared-size pre-check as a cheap early reject. FILE-02's "prefer streaming with an incremental counter" is the same fix. Do not rely on thread isolation alone: the job worker (translation, `renderPptxWithTemplate`) also parses these archives, so the capped reader is needed there too. Pitfall: `saveOoxml`'s `generateAsync` reuses compressed bytes for untouched entries, so it does not re-inflate media and needs no cap.
- **Regression test:** SECB-02's proposed test is right; name it `tests/zip-budget.test.mts` (pure, no Postgres, run via `scripts/heavy.sh -m 1G`). Use a small fixture whose central-directory size for one XML entry understates its real inflated size (~10 MB real). For each of `extractFromBuffer("x.docx")`, `extractSegments("docx")` and `parsePptxTemplate` (pptx fixture), assert: it rejects with «juda katta» / `TemplateError`, and the peak growth of `process.memoryUsage().heapUsed` sampled during the call stays under the budget plus a margin. Today the readers inflate everything before failing, and `parsePptxTemplate` accepts any size.
